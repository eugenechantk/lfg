### 2026-07-31 — `/design-sync` invoked for the reverse direction

**What happened:** Eugene ran `/design-sync` asking to implement a native view *from* a Claude Design file. `design-sync` does the opposite — it uploads a design-system repo *to* claude.ai/design. The correct skill was `implement-claude-design`.
**Why this matters:** The two skill names are near-synonyms to a reader ("sync a design"), and only one of them is about consuming a design. Cost was small (I caught it on the first message) but the ambiguity will recur.
**What better looks like:** When a design-related skill is invoked, check the *direction* of the request (producing vs consuming a design) against the skill's purpose before running it. Consider a note in `implement-claude-design`'s description clarifying it is the design→code direction.

### 2026-07-31 — `GetFile` RPC found after both documented download paths failed

**What happened:** The skill documents two ways to get design assets: (1) right-click → Download in the browser UI, (2) `MintPreviewToken` → fetch from `<projectId>.claudeusercontent.com`. Path 2 returned 404 for every path tried (root, entry HTML, support.js) both via curl and same-origin fetch. Path 1 needs UI clicking. I probed RPC method names and found `OmeletteService/GetFile` `{projectId, path}` → `{content: base64}`, which works headlessly and cost zero context (blob download → browser download dir).
**Also learned:** Chrome silently blocks *consecutive* programmatic blob downloads — the 2nd and 3rd never landed. One download per `javascript_tool` call works.
**Also learned:** the `claude-design` MCP `read_file` truncates at 256 KiB, so a large entry HTML read that way is silently incomplete (a concurrent session's copy of the same file was 262144 bytes = truncated; mine via GetFile was the full 280145).
**What better looks like:** Try `GetFile` first — it is the cheapest and most reliable path. Update the skill's "Alternative" section with it, and note the consecutive-download and 256 KiB truncation traps.

### 2026-08-01 — `flowdeck run -S <udid>` cannot target a simulator at all

**What happened:** Tried three ways to install onto a specific simulator: `flowdeck run -S <udid>`, `flowdeck run --no-build -S <udid>`, both silently used the saved project target instead. Only `flowdeck config set --simulator` actually redirects.
**Why this matters:** The config is shared per project path, so "install to a specific sim" is inherently a global mutation in a repo with concurrent agents. The working pattern is: set config → run → set config back.
**What better looks like:** Treat `flowdeck config set --simulator` as the only targeting mechanism, and bracket it (set → install → restore). For durable isolation use a git worktree, which gets its own flowdeck config and derived data.

### 2026-08-01 — Three FlowDeck guard traps in one sitting

### 2026-08-01 — SwiftUI container accessibilityIdentifier swallows every descendant

**What happened:** `.accessibilityIdentifier` on the screen root made all ten child elements report `newSession.root`. After removing it, the composer card's identifier did the same thing one level down — every child then reported `newSession.composer`. Two rounds to find it because I fixed the outer one and assumed that was the whole bug.
**Why this matters:** The ids are the automation contract; the whole surface was unqueryable while looking superficially fine. Container ids also silently defeat any future UI test.
**What better looks like:** Never put `.accessibilityIdentifier` on a SwiftUI container — only on leaf elements. When a propagation bug is found at one level, check EVERY container in the subtree in the same pass rather than fixing the outermost and re-running.

### 2026-08-01 — Guessed glyph point sizes instead of deriving them, then overcorrected

**What happened:** Fixing "SF Symbols 20-40% oversized", I scaled the point sizes by the ratio of measured-app-ink to measured-design-ink — arithmetic on someone else's numbers. Round 2 measured the chip chevrons 18% UNDERsized and the plus 12% undersized: I had overshot in the other direction. Two round trips of a ~20-minute verification each.
**Why this was wrong:** SF Symbol ink-per-point is not linear across sizes and weights, and pass 1's design measurements were coarser than pass 2's (which supersampled the SVG at 16x before downsampling). I treated an estimate as a target.
**What better looks like:** For glyph sizing, derive the ink-per-point ratio empirically at the actual weight (render two sizes, measure both, interpolate) rather than assuming the ratio from a single sample. Better still: when a verifier can measure, ask it for the ink-per-point ratio at the current size so the next value is computed, not guessed.

### 2026-08-01 — A 68pt text block whose tap target was 21pt

**What happened:** The composer's `TextField` sat inside `.frame(minHeight: 68)`, but the field itself only draws ~21pt, so taps in the lower two-thirds of the design's text block hit the card and were discarded. The verifier caught it by probing (tap at y=748 → character discarded; y=720 → typed). Purely visual comparison would never have found it — the screenshots are identical.
**Why this matters:** It is a real usability bug and it is under the 44pt HIG minimum touch target. Fixed with `.contentShape(Rectangle())` + `.onTapGesture { focused = true }`.
**What better looks like:** Whenever a control is placed inside a frame larger than its intrinsic size, verify the HIT area, not just the drawn pixels. Ask design verification to probe interaction targets, not only measure geometry — a11y frames report the element, not the hittable region.

### 2026-08-01 — Verifier's tap-probe overturned what the accessibility tree said

**What happened:** After fixing the composer's tap target, the a11y tree still reported `newSession.input` as 21pt tall — I nearly treated that as the fix failing. The verifier drove real taps and bisected the boundaries (focus at y=699, miss at 698; focus at y=789, miss at 790) to measure an effective target of **91pt**, 2.07x the 44pt HIG minimum. It wrote: "Judging this from the accessibility tree alone would have produced a false FAIL."
**Why this matters:** The a11y frame is the VoiceOver element rect, NOT the hittable region. `.contentShape` changes hit testing without changing the reported frame. Two different questions with two different instruments.
**What better looks like:** To verify a touch target, drive taps and bisect the boundary. Never read hit area off the accessibility tree. Conversely, to verify VoiceOver reachability, read the tree — taps won't tell you.

### 2026-08-01 — Design SVG ink must account for STROKE, not just path bbox

**What happened:** Sized the send arrow from the design's SVG path bbox (8.5x9.2) — but that path is *stroked at 2.2*, so its drawn ink is 10.0x10.7. The glyph came out 19.5% narrow. The `plus` on the same row had been sized from measured drawn ink and matched within 3%, so the file was internally inconsistent about its own method.
**Why this was wrong:** I read "drawn path" as "path bbox". For a stroked SVG the ink extends half the stroke width beyond the path on every side.
**What better looks like:** For any stroked SVG, drawn ink = path bbox + stroke-width (half on each side), scaled by the viewBox transform. Better: rasterise the SVG and measure the ink, which is what the verifier does — ask it for the target ink dimension rather than deriving from the source path.

### 2026-08-01 — ForEach identity collision silently blanked two whole sections

**What happened:** The model picker groups models by runtime and used `ForEach(models, id: \.self)`. `claude-opus-5` exists under BOTH `aisdk` and `claude`, so two groups shared row identities — SwiftUI kept their layout space but drew nothing and exposed no accessibility elements. Two entire sections were blank, and because the selected model lived in one of them, the panel showed no selection state at all. It compiled, ran, and looked like a rendering glitch.
**Why this was wrong:** I introduced the collision myself, by deciding to show all five runtime groups instead of the design's three. I reasoned about the UX of that choice (duplicate names look odd) and flagged it — but never considered that duplicate *identities* would break SwiftUI. My first fix attempt was also wrong: I added `.id()` INSIDE the ForEach body, which does not change how ForEach resolves identity from its data.
**What better looks like:** `id: \.self` on a String/value collection is only safe when values are unique across the ENTIRE ForEach. When flattening or grouping data, key on a composite (parent + child) via an `Identifiable` wrapper. And when a section renders blank while occupying space, suspect identity collision before layout.

### 2026-08-01 — Substituted a native material for the design's literal fill

**What happened:** The design's panel fill is `linear-gradient(180deg, rgba(0,0,0,0.4), rgb(18,18,18))` — its translucency IS the 0.4 alpha. I layered `.glassEffect`/`.ultraThinMaterial` behind that gradient, reasoning "this is the native way to do glass". Result: 3% light transmission against the design's 56% — the panel was effectively opaque and the whole intended effect was lost.
**Why this was wrong:** The spec named a concrete fill. "Use the platform-native API" applies to *controls* being themed, not to a literal gradient the design specifies. Adding a material behind a translucent fill composites toward opaque.
**What better looks like:** When the design gives a literal fill value, implement that value. Reserve native-material substitution for cases where the design is describing a system material, and verify transmission (is background content visible?) rather than assuming the material looks right.

### 2026-08-01 — Chose a custom overlay over native sheets without checking with Eugene

**What happened:** The design draws the picker panel inset 6pt from the sides AND bottom, which a system `.sheet` cannot do. I treated that as decisive, built a custom `ZStack` overlay with a hand-rolled gradient, grabber, and drag-dismiss — and then spent two rounds debugging its opacity (a native material layered behind the gradient made it opaque). Eugene's instruction: "The sheet should not be opaque just follow Apple's native sheets."
**Why this was wrong:** I let one geometric detail of the mock override the platform default, and never surfaced the tradeoff as a decision. The custom panel meant reimplementing translucency, the grabber, corner treatment, drag-to-dismiss and height behaviour — every one of which the system provides correctly, and one of which I then got wrong. The `implement-claude-design` skill's own guidance is to prefer a system control to theme over a re-creation.
**What better looks like:** When a design detail can only be honoured by abandoning a system control, that is a decision to raise — "the design insets the sheet 6pt on three sides, which `.sheet` can't do; custom overlay or native sheet?" — not one to settle silently in favour of pixel fidelity. Default to the native control and treat the mock's deviation as a question.
