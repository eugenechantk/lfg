### 2026-09-17 — Fourth recurrence of the composer-border parser class

**What happened:** Sends to cy-134704-39300 failed with "never left the input box". The top border was a numbered-branch label wrapped across two lines; the parser missed it and a dead Codex `›` fallback returned a transcript line as the composer, so sendq wiped its own draft three times. Fixed in `src/tmux.ts` (`ruleAt`, fallback removed), regression fixture from the live capture, deployed by port restart, verified by re-sending the exact message (delivered in <1s).
**Why this was wrong:** Each previous fix (wrapped bottom border, `(Branch) ──`, `(Branch 3) ─`) matched one more literal shape; none addressed the underlying failure mode, which is that an unrecognised border produced a *wrong non-null* region instead of `null`. `insertionOutcome` already degrades gracefully on `null`; the fallback bypassed that safety net.
**What better looks like:** When a heuristic parser feeds a retry loop, audit its failure mode first: it must return "unknown", never a plausible wrong answer. Also, the one-step diagnostic (run `inputBoxFromPane` over a capture) was faster than reading sendq.ts — now recorded in the project CLAUDE.md so it's the first move next time.

### 2026-09-17 — Restart drops the failed queue rows

**What happened:** After the deploy restart, `GET /queue` was empty, so the user's failed message could not be retried by id; I re-sent the exact text via `/send` instead.
**Why this matters:** The user's client still shows the failed rows locally; tapping retry there 404s. Verification had to substitute a fresh enqueue for the real retry path, and a duplicate would have been possible if the user retried at the same moment.
**What better looks like:** Consider persisting failed rows across restarts (they're already traced in sendq.log), or at least treat "restart then re-send the exact text" as the documented recipe and say so in the report.

### 2026-09-17 — Fixed the parser a fourth time instead of questioning the gate

**What happened:** I diagnosed and fixed the wrapped `(Branch 2) ─` case, deployed, and reported. Eugene asked "why not just always press enter anyways and verify in the transcript?" One log query answered it: 1,202 first-attempt successes, 1 retry rescue, 54 failures all caused by the check. I then removed the gate (`submitOutcome`, `.claude/feature/send-submit-transcript-authority.md`), deployed, and verified live.
**Why this was wrong:** A check that has needed four fixes is itself the suspect. I treated the fourth failure as another shape to teach the parser, not as evidence the parser should not be load-bearing. The data to decide that was already on disk in `sendq.log` and took one command.
**What better looks like:** When a guard fails repeatedly, before patching it again: count from the logs how often the guard has *saved* an operation versus *killed* one. If it has never earned its keep, demote it to advisory or delete it, and make the authoritative check the one closest to ground truth (here: the transcript).
