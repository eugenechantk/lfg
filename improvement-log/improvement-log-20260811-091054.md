### 2026-08-12 — A five-hour build break that no agent's build could see

**What happened:** Cutting a TestFlight build from a clean branch off `main`
failed on `store.navID`. `main` had not compiled since 19:10, when one session
committed `SessionListView` referencing a `SessionStore` member it left
uncommitted. Every agent in the repo was building green the whole time, because
each built the shared dirty tree — which still contained the missing half.
Repairing it exposed a second layer: the same `SessionStore` also needed
uncommitted `LFGStore.replaceSessions` and `MultiHost.unreachableLiveSessionIds`.

**Why it matters:** "it builds" is the check everyone runs, and in this repo it
is not evidence that HEAD builds. The failure is silent and it compounds — the
longer it sits, the more half-committed layers accumulate on top. It only
surfaced because a release build forced a clean checkout.

**What better looks like:** build from a clean worktree at HEAD before any
release, and treat a dirty-tree build as evidence about *your* tree only. Expect
the break to be more than one file deep and re-build after each repair rather
than trusting the first error to be the whole story. Captured as memory
`main-can-be-broken-while-every-build-is-green`.

**Adjacent, worth watching:** the FlowDeck sim guard forced per-session simulator
isolation automatically, which worked well and removed the contention hazard the
repo CLAUDE.md warns about — no coordination needed. That guard is doing its job;
the gap is that nothing plays the equivalent role for the shared git checkout.

### 2026-08-11 — Named a root cause without running the disconfirming test

**What happened:** I diagnosed the cellular connection problem as Surfshark
breaking Tailscale's hole punching, from a mismatch between `netcheck`'s
STUN-discovered address (`45.144.227.29`, the VPN) and Tailscale's advertised
endpoints (`203.145.95.116`, the real ISP). I wrote it into a diagnosis doc,
recommended two config changes off it, and told Eugene it superseded an existing
memory that had retracted exactly this theory. Two commands later — `tailscale
status` showing the Air **direct** on the LAN, and `tailscale ping` from the
Hostinger VPS reaching the Pro **direct on the real ISP address over the public
internet** — the theory was dead. Both tests were available the whole time, both
are non-destructive, and both took seconds.

**Why this was wrong:** memory `disconfirm-before-declaring-root-cause` says to
name the check that would prove the theory innocent and run it *before* writing
any diagnosis. I had that memory in context and skipped it. The address mismatch
was suggestive, not probative, and I promoted it to root cause because it
explained the symptom neatly. Worse, I used it to overturn a prior retraction —
so a correct memory nearly got replaced by a wrong one, and Eugene was one step
from configuring a router and a VPN to fix a blocker that didn't exist.

**What actually shook it loose:** Eugene refusing the test I proposed (quitting
Surfshark) because it risked wedging a machine he drives remotely. Being forced
to find a non-destructive test is what produced the decisive one. The
constraint improved the diagnosis — the destructive test would have answered
less, since it changes two things at once.

**What better looks like:** before writing a root cause into a doc, list the
observations it predicts that a *rival* theory does not, and go get one. Here the
rival was "the Mac punches fine, the phone's carrier is the blocker", and it
predicts a third party on the public internet reaching the Mac directly — one
`ssh hostinger 'tailscale ping'` away. Prefer the test that discriminates between
theories over the test that confirms the favoured one. And when reaching for a
destructive test, ask what non-destructive test answers the same question first —
that is nearly always available for a network path question, because peers
already on the tailnet are free probes.

### 2026-08-11 — A "ruled out" memory nearly suppressed a contradicting re-measurement

**What happened:** Memory `lfg-pro-host-sleep-disconnects` carries an explicit
"Ruled OUT with fresh evidence (don't re-chase): Surfshark — WRONG, retracted",
justified by Tailscale's STUN-discovered endpoint being the real ISP IP. Measuring
today, `tailscale netcheck` reports the Mac's public address as `45.144.227.29`
(Surfshark) while Tailscale still advertises `203.145.95.116` (real ISP) to peers —
the exact asymmetry that kills hole punching. The retraction was correct on
2026-08-04 and wrong on 2026-08-11.

**Why this matters:** A negative finding written as a standing prohibition
("don't re-chase") outlives the measurement that justified it. Positive findings
get re-verified naturally because something depends on them; negative ones just
sit there closing off a branch.

**What better looks like:** Negative findings in memory should carry the *check
that produced them*, not just the verdict — "Surfshark ruled out; the check was
`tailscale status --json .Self.Addrs` showing the real ISP IP" — so re-running it
costs one command. Treat a "don't re-chase" item as "re-run the named check first,
then don't re-chase" whenever the symptom recurs. Memory is a point-in-time
observation, and environment-level facts (VPN behavior, routing) decay fastest.

### 2026-08-11 — FlowDeck guard vs. the plist-seeding recipe: a documented dead end

**What happened:** To verify RTT-adaptive timeouts live I needed the sim app
pointed at a latency proxy. The project CLAUDE.md recipe for seeding sim app state
ends "launch with simctl — NOT `flowdeck run`, which reinstalls and wipes the
prefs." But the FlowDeck guard hook **blocks that simctl subcommand** and redirects
to `flowdeck run` — the exact command the recipe forbids. I confirmed empirically
that `flowdeck run` does wipe it: the data container UUID changed between runs.
`flowdeck ui simulator` has no launch subcommand either. ~6 tool calls burned.

**The way through:** the app registers a `lfg://` URL scheme, so
`flowdeck ui simulator open-url "lfg://" --simulator <UDID>` starts it without
reinstalling. Second and later opens raise a modal *"Open in lfg?"* that silently
swallows the launch — clear it with `flowdeck ui simulator tap "Open"` (positional
label; `--text` is not a flag and fails with a bare usage dump rather than an
error, which reads like the tap succeeded).

**Why it matters:** the recipe named a command the environment forbids, so it read
as a dead end rather than a detour. A blocked path with no stated alternative costs
more than no documentation, because it looks authoritative.

**What better looks like:** the seeding recipe in `.claude/CLAUDE.md` should name
the URL-scheme launch as the FlowDeck-compatible step, including the confirmation
dialog and the positional-label tap syntax. Worth adding once the concurrent edits
to that file settle.

### 2026-08-11 — The FlowDeck guard matches raw command text, not intent

**What happened:** Appending the entry above to this log via a bash heredoc was
**blocked** by the FlowDeck guard, because the prose inside the heredoc contained
the name of a blocked simctl subcommand. Nothing was being executed — it was a
string literal in a document about the block itself.

**Why it matters:** a text-matching guard on `Bash` makes writing *about* forbidden
commands impossible through that tool, which is exactly what an improvement log
needs to do. The failure is silent about its real cause — it reports the command as
blocked, not "your heredoc content tripped a pattern."

**What better looks like:** use the `Write`/`Edit` tools for any file content that
quotes shell commands, rather than heredocs — they bypass command-text scanning
entirely and are the right tool for writing files anyway. Reach for a heredoc only
when the content is generated by the shell.
