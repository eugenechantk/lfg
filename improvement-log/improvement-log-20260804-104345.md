### 2026-08-04 — Concurrent session fixed a different cause and called it the cause

**What happened:** Session `c5d4a5a2` was given the same symptom ("sessions still
showing running even though stalled"). It traced it to the journal pump dropping
vanished sessions without retracting `busy`, wrote the fix and 6 tests, and
reported it as *the* cause. It never captured the pane of the session that was
actually stuck. That session had not vanished — it was live and enumerated the
whole time, and its `busy: true` came from `isBusy()` matching the phrase
"esc to interrupt" inside its own printed answer.

**Why this matters:** the pump fix is real and worth keeping, but it was
presented as resolving the reported bug when it could not have. The disconfirming
check was 30 seconds of work: `tmux capture-pane` on the named session and run
`isBusy` against it. Two causes hid behind one symptom, and the cheap check
separated them immediately.

**What better looks like:** when a symptom names a specific instance
(`cy-163217-77946`), reproduce THAT instance before generalizing. Compute the
reported field from its live inputs and confirm which input is wrong, then fix
that. This is memory [[disconfirm-before-declaring-root-cause]] applied to a
concurrent session's work rather than my own — worth checking a peer session's
diagnosis the same way I'd check mine.

### 2026-08-04 — Pane-scrape predicates need a chrome anchor, not a whole-pane scan

**What happened:** `isBusy()` tested `/esc to interrupt/` and the spinner-meter
regex against the entire captured pane. Both markers are TUI chrome that only
render around the composer box, but nothing constrained the search, so an agent's
own output could satisfy them. In this repo — which documents its own busy
detection — sessions print those exact strings routinely, so the false positive is
expected traffic, not a freak input.

**Why this matters:** it is a whole class, not one bug. Every pane predicate in
`src/tmux.ts` (`feedbackPromptOpen`, `questionSelectorOpen`, `parsePrompt`) reads
a scraped pane where transcript text and TUI chrome are the same string. Any of
them can be spoofed by an agent that writes about the UI it runs in.
`inputBoxFromPane` already got this right by scanning bottom-up for the composer
borders — the pattern existed, it just wasn't applied to `isBusy`.

**What better looks like:** when scraping a TUI, first locate the chrome (the
composer border run is the reliable anchor here), then match inside that region.
Treat everything above the composer as untrusted agent output. Worth a line in
the project CLAUDE.md's send/scrape section, since the sendq traps are already
documented there.

### 2026-08-04 — Read a Syncthing sync-conflict transcript and reported a bogus stat

**What happened:** measuring how reliably Claude writes a `turn_duration` record, I
globbed `~/.claude/projects/<proj>/*.jsonl` and reported that one session had 32
prompts but only 21 turn ends — an 11-turn gap that looked like a serious hole in
the signal. The file `ls` picked was a `.sync-conflict-20260710-…jsonl` copy, a
truncated snapshot from the Syncthing pair. The canonical file was 34/34, a
perfect match. I nearly recommended against a design on the strength of a
corrupted sample.

**Why this matters:** `~/.claude/projects` is synced between the Air and the Pro,
so every transcript can have `.sync-conflict-*` siblings sitting next to it with
the same session-id prefix. Any glob, `ls -t`, or "newest file" heuristic over
that directory will eventually grab one. They parse fine as JSONL — the corruption
is silent truncation, not a syntax error — so nothing warns you.

**What better looks like:** when reading transcripts by pattern, always filter
`grep -v sync-conflict` (or match the exact `<uuid>.jsonl` shape). More generally
this is memory [[probe-shape-before-scripting]]: the anomalous number was the
signal to look at the file, not to write it up. I did eventually check, but only
after quoting the wrong figure.
