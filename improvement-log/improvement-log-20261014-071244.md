## Log

### 2026-10-14 — Navigating to a session by scrolling instead of the deep link

**What happened:** To photograph the session view with a long transcript, I tried `scroll --until` + `tap`, slow drags, status-bar taps, and a sim-navigate run. Several taps silently missed (nav-bar buttons need raw touch, list taps raced the scroll), and fast swipes over-scrolled into paginated closed sessions.
**Why this was wrong:** The app already has `lfg://session/<id>` (`DeepLink.swift`). `flowdeck ui simulator open-url` + tap "Open" lands on any session in one step.
**What better looks like:** For lfg sim verification, open sessions with `open-url lfg://session/<id>` first. Worth a line in `ios/CLAUDE.md` under verification.

### 2026-10-14 — GeometryReader that ignores the safe area reports zero insets

**What happened:** I wrapped the list's edge-fade overlay in `GeometryReader { … }.ignoresSafeArea()` expecting `proxy.safeAreaInsets` to report the bars. A debug print showed `top=0.0 bottom=0.0`; nothing drew. Keeping the safe area gave `top=116 bottom=86`.
**Why this was wrong:** I relied on remembered SwiftUI behaviour instead of measuring once before building on it.
**What better looks like:** Measure the inset with one print before writing layout on top of it. The working recipe is now in `Theme.swift` (`ListChromeFades`).

### 2026-10-14 — Inherited uncommitted change broke the + button; my self-check didn't tap it

**What happened:** The Oct 10 work moved the list dock into the list's `safeAreaBar`. Inside that bar, interactive glass on the + button's label swallowed the touch, so New session / New task never opened. The earlier agent's audit tested tabs and search, not +. My self-verification also skipped it. The independent auditor caught it (7/7 failures; HEAD worked).
**Why this was wrong:** When building on inherited, unverified work, its regressions become mine. A control that moved containers needs every element tapped once.
**What better looks like:** For any change that moves controls into a new container (bar, overlay, safe-area inset), tap each control and check its action fires before calling self-verification done. Keep the independent audit — it earned its cost here.

### 2026-10-14 — Bottom fade sized from a derived height instead of the real edge

**What happened:** The session view's bottom fade used `bottomChromeHeight` (140), but the composer's top sat 156pt above the screen bottom. The ramp ended 16pt short; the auditor measured text ~50% visible at the composer edge.
**Why this was wrong:** A visual edge should be anchored to the view whose edge it is, not computed from a separately measured number.
**What better looks like:** Attach the effect to the edge-owning view (background pinned to its top, offset by the tail). Derived heights drift.

### 2026-10-14 — Software keyboard disappeared after FlowDeck typing

**What happened:** The iPhone software keyboard showed early in the session, then only the AutoFill bar appeared on focus. The auditor (iPhone and iPad) and I tried raw touches, tap-by-id, cmd-K via System Events, and an `lfg-unlock` round trip. `ConnectHardwareKeyboard` was already 0. A `flowdeck simulator shutdown <udid>` + `flowdeck run` brought it back at once.
**Why this was wrong:** HID key events from FlowDeck `type` make iOS treat a hardware keyboard as attached until reboot; the existing memory (`sim-keyboard-needs-simulator-app`) only covers Simulator.app being closed.
**What better looks like:** If focus shows only the AutoFill bar and Simulator.app is running, shut down and relaunch the session sim before anything else. Add this to the `sim-keyboard-needs-simulator-app` memory.

### 2026-10-15 — Misread "border" in the edge-transition spec; shipped the wrong ramp

**What happened:** Eugene asked for bars that are "transparent with a transition at the end at the border". I read "border" as the bar's inner edge, held full glass across the whole bar, and faded just past it. Rows became unreadable behind the title, host line, dock and composer. After TestFlight 202610141854 he corrected: content should flow visibly behind the bars and transition only at the edge of the screen.
**Why this was wrong:** "Transparent" already said content stays visible behind the bars. I resolved the ambiguity toward my own legibility concern (rows colliding with "3 hosts online") instead of the literal word, and didn't show him a frame before shipping. A 2-image before/after in chat would have caught it before the build.
**What better looks like:** When a visual spec has an ambiguous word ("border", "edge", "end"), send one screenshot of the interpretation before building out and shipping. Prefer the reading that matches the other words in the sentence ("transparent").

### 2026-10-15 — Should have checked Apple's default scroll edge effect first

**What happened:** Three iterations (v2 heavy glass slab, v3 status-bar-only fade) of a custom `ChromeFade` on the lists, two of them shipped to TestFlight, before Eugene asked me to check Apple's defaults. The HIG (Scroll views, updated 2026-06-08) says: prefer the automatic scroll edge effect; use `safeAreaBar` for custom bars so the effect extends under them. The lists only needed the custom fade REMOVED. The automatic effect gave exactly the look he wanted.
**Why this was wrong:** The liquid-glass skill's first rule is "prefer system components"; I inherited a custom fade from the session view (which needs one because its transcript is flipped) and generalised it instead of asking whether the lists needed it at all.
**What better looks like:** For any glass or edge treatment, first render the system default and look at it, then customise only where the default provably fails (the flipped transcript). When a custom stand-in is needed, measure the system effect (fade-profile script) and copy its curve.
