## Log

### 2026-08-06 — Theorised about APNs delivery before measuring the two busy signals

**What happened:** Spent several rounds building hypotheses about token rotation,
push-to-start background launches, and the iOS update budget before running the
one cheap comparison that actually located the bug: journal-derived busy (what
the app renders) vs the watcher's own busy (what the card renders), sampled every
5s. The drift showed up in the first 12 seconds of monitoring.

**Why this was wrong:** `.claude/CLAUDE.md` already documents "session state has
two owners" as a known hazard in this repo. The moment the symptom was "server
and app disagree about what's running", that note should have been the first
place I looked — not the fifth. Memory `ground-truth-before-hypothesizing` says
the same thing generically.

**What better looks like:** When a symptom is "two surfaces show different
state", the first action is to sample both surfaces simultaneously and diff them.
Build the comparison harness before building the theory.

### 2026-08-06 — Codex scratch server runs the real push watcher

**What happened:** Found `bun run src/cli.ts serve` (pid 73041) on port 8767,
spawned by a codex agent at 20:40, running its own push watcher against
`~/.lfg/live-activity-tokens.json` — i.e. sending real APNs Live Activity pushes
to Eugene's real device, with an in-memory `active.current` independent of the
primary server's.

**Why this matters:** Two watchers can disagree and fight over one card, and any
agent that starts a scratch server silently starts pushing to production devices.
This is a system gap, not a one-off.

**What better looks like:** The push watcher should be opt-in for non-primary
servers (gate on port or an explicit env flag), and `.claude/CLAUDE.md` should
say so under the concurrent-sessions hazards.

### 2026-08-06 — Probe compared incomparable busy values

**What happened:** `probe-observe.ts` compared a cold `listSessions()` `.busy`
against the watcher's derived busy and printed "DRIFT" for sessions where the
real disagreement wasn't. The running server's `/api/sessions` (journal-fed) is
the only meaningful comparand; a fresh process's `listSessions()` has no journal
state.

**Why this was wrong:** I picked the convenient in-process value rather than the
one that represents what the client actually sees, and briefly believed a false
signal. Memory `probe-shape-before-scripting` covers this.

**What better looks like:** Before flagging a diff, confirm both sides of the
comparison are produced the same way the production consumers produce them.

### 2026-08-07 — Concurrent agents blocked live deploy verification twice in one session

**What happened:** The fix needed a server restart to go live. Twice, restarting
would have destroyed another agent session's work in progress:
1. A 25-minute memory-measurement window (`ps -o rss=` polling the serve pid),
   started minutes before I was ready to deploy.
2. A leak investigation whose SUBJECT is the long-running serve process itself,
   now at 1.36 GB RSS — a restart resets it and it takes hours to regrow.

Both were discovered only by chance, from `ps -eo pid,ppid,command` output I ran
for an unrelated reason. Nothing announces "this process is under measurement".

**Why this matters:** `.claude/CLAUDE.md` already says to check for concurrent
agents before LIVE verification, and I did — but the check it implies
(`lfg-sessions` / `git status`) does not surface "another agent is measuring the
shared server process". A restart is cheap to do and expensive to undo for
someone else, and the collision is invisible until after the fact.

**What better looks like:** Treat "restart the shared serve process" as a
coordinated action, not a routine one. Before restarting: grep `ps` for probes
attached to the serve pid (`ps -o rss=`, `vmmap`, `lsof -p <pid>` loops) as well
as checking for other serve processes. Better still, a lightweight convention —
an advisory lock file such as `~/.lfg/serve-hold` with a reason and an expiry
that any agent instrumenting the process writes, and any agent about to restart
reads. Worth proposing during `/self-improve`.

### 2026-08-07 — A "clean" live probe proved nothing, and nearly got recorded as evidence

**What happened:** SC1's live check compared the new busy derivation against the
journal across live sessions and returned `checked=3 drift(old)=0 drift(NEW)=0`.
I was about to log that as the criterion's evidence. But zero drift under the OLD
code as well means the run simply caught a moment with no stalled session — it
demonstrated nothing about the fix. Replacing it with a scan over all 275 real
transcripts produced the actual proof: 47 read "running" while stale past
`STALL_MS`; old code counted all 47 busy, new code counts 0.

**Why this was wrong:** A passing check whose CONTROL also passes is not
evidence. I had the control right there in the same probe and initially read past
what it was telling me.

**What better looks like:** When a probe includes a before/after control, read
the control first. If the old code also passes, the probe did not exercise the
bug — go find data that does before recording anything.

### 2026-08-08 — Used a mutating endpoint as a liveness probe and destroyed the evidence

**What happened:** To check whether the restarted server was running new code I
called `POST /api/push/live-activity/ended` and looked for 200 instead of 404. It
worked — and it also cleared the fleet card state, which was the exact artifact I
was about to read to diagnose the recurrence.

**Why this was wrong:** I picked the probe for its diagnostic value to ME (a route
that only exists in the new build) and ignored that it is a command, not a query.
The state it destroyed was the only record of what the card looked like at the
moment of the report.

**What better looks like:** Liveness probes must be reads. To prove a deploy,
diff the process start time against the source mtime (already in
`.claude/CLAUDE.md`), or call a GET that changed. Never a POST that mutates the
thing under investigation.

### 2026-08-08 — Live Activity had no success-path logging, so three investigations re-derived the same thing by repro

**What happened:** The card going stale has now been investigated three times.
Each time the server-side evidence was: nothing. The watcher logged only APNs
failures, and this bug's signature is a **200** — so the logs were silent
precisely when something was wrong. `end` was worst: it unlinks the state file,
so the one durable artifact is destroyed at the moment of interest.

**Why this matters:** `sendq.log` exists for exactly this reason and
`.claude/CLAUDE.md` calls it out as the thing to read before re-deriving a
delivery report by live repro. The Live Activity path had no equivalent, and the
absence was invisible until the third repeat.

**What better looks like:** When a push/delivery path can fail *successfully*
(the transport says OK and the effect does not happen), log the success path too
— which token, what came back, over time. Added as `~/.lfg/liveactivity.log` in
`72e6995`. Generalise the rule: any code whose failure mode returns 200 needs a
trace of its 200s.
