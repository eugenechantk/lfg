### 2026-10-21 — flowdeck-guard blocks `open X.app` for the swiftc-built desktop app

**What happened:** To launch a scratch build of `desktop/build/lfg.app` I ran `open -n -g <path>.app`. The FlowDeck guard hook blocked it and told me to use `flowdeck run --simulator none`. The desktop app has no Xcode project (`desktop/build.sh` calls `swiftc`), so FlowDeck cannot run it.
**Why this was wrong:** The guard has no exemption for apps FlowDeck cannot build. The workaround (start `Contents/MacOS/lfg` with nohup) works, but the launched app then opened no window, so I had to open it by pressing Window ▸ lfg through AX.
**What better looks like:** Add an lfg-desktop note (desktop/README or the macos-test skill): launch scratch desktop builds with `nohup <app>/Contents/MacOS/lfg &`, then `axdriver press --role AXMenuItem --title lfg --index 1` to open the window, then activate it with JXA `NSRunningApplication.activateWithOptions`. Or teach the guard to allow `open` for bundles that have no Xcode project.

### 2026-10-21 — axdriver per-process typing does not reach SwiftUI text fields

**What happened:** `axdriver type --text` reported `typed:true`, but a focused SwiftUI `TextField` stayed empty. `axdriver type --key k --modifiers cmd` did fire the menu's ⌘K. Real System Events `keystroke` filled the field at once.
**Why this matters:** Without the cross-check, an empty field looks like a focus bug in the feature under test. I nearly treated it as one.
**What better looks like:** In macos-test's gotchas: per-process key events reach menu key equivalents but not the SwiftUI field editor. For text entry into a SwiftUI field, use `set-value` or System Events `keystroke` while the app is in front (only when the Mac is free, for example after lfg-unlock).

### 2026-10-21 — `.onExitCommand` on a field misses Escape after Return

**What happened:** For "Escape exits search" I first put `.onExitCommand` on the search TextField. A live test showed it worked while typing, but did nothing after Return, because the field's `onSubmit` drops focus.
**Why this matters:** A test that only tried Escape while typing would have passed, and the shipped feature would have missed the most natural moment (type, Return, look at results, Escape).
**What better looks like:** For an "Escape dismisses X" feature on macOS, use a hidden `.keyboardShortcut(.cancelAction)` button that exists only while X shows (`opacity(0)`, `allowsHitTesting(false)`, `accessibilityHidden`). Always test Escape with focus inside the field and with focus outside it.
