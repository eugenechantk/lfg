### 2026-09-19 — Hit the Swift 6 region-isolation error the neighbouring file already documents

**What happened:** First `flowdeck build` of the dedupe wiring failed: binding `Activity<...>` values in an array and awaiting `activity.end` on them inside a `@MainActor` method trips "sending 'activity' risks causing data races". `FleetActivityController.swift` has a paragraph explaining exactly this and the fix (look the activity up in its own static scope and consume it immediately).
**Why this was wrong:** I had read that comment earlier in the session and still wrote the naive loop. One extra build cycle (~1 min) and a rewrite.
**What better looks like:** For any ActivityKit code in this repo: never hold an `Activity` across an `await` in an actor-isolated method; write a `static func` that iterates `Activity.activities` and awaits inside the loop. Candidate for the ios/CLAUDE.md Traps list.

### 2026-09-19 — Shipped the server veto without the client end-debounce it depends on

**What happened:** The 09-18 diagnosis listed five fixes; Eugene picked 1 and 2 (client dedupe, server veto) and I shipped exactly those. Within an hour of the restart the log showed 32 `client-ended` and 266 `start-vetoed`: the app ends every push-started card ~2 s after arrival (background wake, empty store), and the veto now stops the server from re-starting it — so the phone has no card between app opens instead of five stale ones. Eugene reported it as "the widget doesn't update when backgrounded".
**Why this was wrong:** I ranked the fixes by symptom leverage, not by dependency. Fix 2 changes what an eager client end *costs* (no card vs an extra card), so it needed fix 4 (don't end on a count you can't vouch for) in the same release. I had the timing evidence to see this — every client-ended in the 09-18 log sat seconds after a start — and read it as "phone disagrees on count" without asking *why the disagreement is always at start time*.
**What better looks like:** When a fix removes a self-healing loop (however wasteful the loop), ask what the loop was compensating for and ship that guard in the same change. And when a repeated event is always N seconds after another event, the second is caused by the first — read the client's launch path before blaming its inputs.
