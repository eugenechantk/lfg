### 2026-08-11 — Designed against the visible population, not the motivating one

**What happened:** Eugene asked to hide "gbrain sessions". `/api/sessions` showed
two, both in `/Users/eugenechan/.gbrain`, so I designed and built literal-path
hiding, wrote 19 tests, and wired it through the app. Only when I ran the client
live did a third row appear: `$TMPDIR/gbrain-claude-cli-cwd-24267` — an autopilot
session in a per-run temp directory whose name carries a pid. That is the
population Eugene actually complained about ("too many when autopilot is running"),
and literal paths would have muted exactly one run of it.

**Why this was wrong:** I sampled the session list once, at rest, and treated it as
the population. The ask itself said *when autopilot is running* — a temporal
qualifier telling me the interesting population was not on screen at that moment.
The repo's own memory [[verify-against-real-session-population]] says exactly
this about pane fixes; the same trap applies to any filter, and I didn't
generalize it.

**What better looks like:** When a request names a population by a *condition*
("when X is running", "during Y"), enumerate the population under that condition
before designing — trigger it, or read the tool that produces it. Here, one look at
how gbrain autopilot spawns sessions (or one `ls $TMPDIR`) would have shown the
per-run directories in the first minute rather than after the feature was built.
The rework was cheap only because the primitive extended cleanly to patterns.

### 2026-08-11 — Disclosure at the bottom of a paginated list

**What happened:** I put the "N sessions hidden" disclosure in a footer after the
last section. The session list is long and the closed section paginates, so the
footer is several screens down — a disclosure that exists but is never seen.

**Why this was wrong:** I placed it where it was structurally easy (end of the
`ForEach`) rather than where it does its job. The whole justification for the
element was "a filter with no visible trace is a bug report waiting to happen" —
and I then made it invisible.

**What better looks like:** For any always-relevant status, place it in persistent
chrome (header/toolbar), not in list flow. Ask "is this on screen when the user
needs it?" before "where is it easy to put?". Moved to a header chip beside the
filter and gear buttons.

### 2026-08-11 — A count that changed as the user scrolled

**What happened:** The hidden-count read "63" against a handful of live agents,
because it counted every hidden session including paged-in closed ones — so it also
*grew every time the closed list paginated*.

**Why this was wrong:** I picked the arithmetically complete number instead of the
meaningful one. A number that changes when you scroll trains the user to ignore it.

**What better looks like:** A count shown next to another count must describe the
same population. This one sits beside "N running", so it counts live sessions. Caught
only because I read the accessibility tree after the screenshot looked odd — worth
doing routinely, since the tree carries values the JPEG doesn't.
