## Log

### 2026-08-11 — Designed against the visible population, not the motivating one

**What happened:** Eugene asked to hide "gbrain sessions". `/api/sessions` showed
two, both in `/Users/eugenechan/.gbrain`, so I designed and built literal-path
hiding, wrote 19 tests, and wired it through the app. Only when I ran the client
live did a third row appear: `$TMPDIR/gbrain-claude-cli-cwd-24267` — an autopilot
session in a per-run temp directory whose name carries a pid. That is the
population Eugene actually complained about ("too many when autopilot is running"),
and literal paths would have muted exactly one run of it.

**Why this was wrong:** I sampled the session list once, at rest, and treated it as
the population. The ask itself said *when autopilot is running* — a temporal
qualifier telling me the interesting population was not on screen at that moment.
The repo's own memory [[verify-against-real-session-population]] says exactly
this about pane fixes; the same trap applies to any filter, and I didn't
generalize it.

**What better looks like:** When a request names a population by a *condition*
("when X is running", "during Y"), enumerate the population under that condition
before designing — trigger it, or read the tool that produces it. Here, one look at
how gbrain autopilot spawns sessions (or one `ls $TMPDIR`) would have shown the
per-run directories in the first minute rather than after the feature was built.
The rework was cheap only because the primitive extended cleanly to patterns.

### 2026-08-11 — Disclosure at the bottom of a paginated list

**What happened:** I put the "N sessions hidden" disclosure in a footer after the
last section. The session list is long and the closed section paginates, so the
footer is several screens down — a disclosure that exists but is never seen.

**Why this was wrong:** I placed it where it was structurally easy (end of the
`ForEach`) rather than where it does its job. The whole justification for the
element was "a filter with no visible trace is a bug report waiting to happen" —
and I then made it invisible.

**What better looks like:** For any always-relevant status, place it in persistent
chrome (header/toolbar), not in list flow. Ask "is this on screen when the user
needs it?" before "where is it easy to put?". Moved to a header chip beside the
filter and gear buttons.

### 2026-08-11 — A count that changed as the user scrolled

**What happened:** The hidden-count read "63" against a handful of live agents,
because it counted every hidden session including paged-in closed ones — so it also
*grew every time the closed list paginated*.

**Why this was wrong:** I picked the arithmetically complete number instead of the
meaningful one. A number that changes when you scroll trains the user to ignore it.

**What better looks like:** A count shown next to another count must describe the
same population. This one sits beside "N running", so it counts live sessions. Caught
only because I read the accessibility tree after the screenshot looked odd — worth
doing routinely, since the tree carries values the JPEG doesn't.

### 2026-08-11 — Treated a fixture-driven screenshot as evidence about real data

**What happened:** To verify directory hiding in the desktop app I used
`lfg --window-shot`, which draws the window off-screen. The first shot happened to
race a live refresh and showed real sessions, so I assumed the harness rendered live
data. The second shot — the one meant to prove gbrain was hidden — showed four
*fixture* rows ("Choose the launch direction", "Polish onboarding copy") and
"Connecting…". I nearly read a plausible-looking picture as proof.

**Why this was wrong:** I inferred the harness's data source from one lucky run
instead of reading `makeWindow`, which seeds `store.hosts` with fixtures
unconditionally. A layout harness answers layout questions; I asked it a data
question and it answered confidently in the wrong currency. The tell was on screen —
"Connecting…" next to sessions — and I only caught it because the session titles
looked unfamiliar.

**What better looks like:** Before treating any harness output as evidence, read what
feeds it. If the answer is "fixtures", it can only evidence rendering. For claims
about real data, use (or add) a live probe: `lfg --hidden-dirs-probe` now refreshes
against the real hosts and reports per-entry hit counts, which is what actually
proved the feature. Related to the repo's `verify-real-seam-not-mocks` memory — a
fixture-backed screenshot is a mock with a camera.

### 2026-08-11 — Threw away a verification lane's output with `tail`

**What happened:** I ran `fastlane ios verify_testflight_build ... | tail -45` in the
background. It exited 0, and the captured output contained only fastlane's summary
table — which lists *actions*, and the DoD checks are plain Ruby, so nothing I could
read said whether the build was actually testable. I reported the pass, then had to
correct myself and re-run with the full log.

**Why this was wrong:** I truncated the output of the one command whose entire
purpose is to print findings, and then trusted its exit code — the exact
"green means verified" reflex this repo's notes warn about. `tail` is for skimming
noisy logs, not for capturing a verdict.

**What better looks like:** Redirect verification output to a file in full
(`> log 2>&1`) and grep it afterwards. Never pipe a command through `tail`/`head`
when its output IS the deliverable.

### 2026-08-12 — Put a display option in Settings instead of the view chrome

**What happened:** I built the directory filter as a Settings page (iOS: a
NavigationLink under a "Filtering" section; desktop: a second Settings tab), with a
small separate indicator in the header to disclose it. Eugene moved it: "I feel like
filtering is more of a display option than a client setting." He was right, and the
consequence was real — changing what you're looking at took a Settings trip every
time.

**Why this was wrong:** I sorted the feature by *what it stores* (a persisted
preference → Settings) rather than by *how often it changes and alongside what*. The
signal was already on screen: grouping and sorting sit in the header because they're
per-task view choices, and hiding directories is the same kind of choice. I even
built a header chip for disclosure — half the answer — without noticing that the
control itself belonged there, which would have collapsed two elements into one.

**What better looks like:** Ask "how often does this change, and what does the user
change it *with*?" Per-task, alongside other view controls → view chrome.
Set-once-and-forget (hosts, credentials, default owner) → Settings. Persistence is
not the test; a display option can persist. Where a related control already lives is
the strongest hint.

### 2026-08-12 — Inserted a property between `@ViewBuilder` and its view

**What happened:** Adding a computed property "just above `groupPicker`" put it
between the `@ViewBuilder` attribute and the `var` it decorated. `groupPicker` lost
its builder and failed with "opaque return type … no return statements", pointing at
a function I hadn't edited.

**Why this was wrong:** I anchored an insertion on `private var groupPicker:` without
reading the line above it. Attributes, `@MainActor`, doc comments and availability
guards all sit on preceding lines, so "just above the declaration" is not a safe
anchor.

**What better looks like:** When inserting before a declaration, anchor on the line
above the *whole* construct (blank line, or the end of the previous member), and read
enough context to see any attributes. The build error naming an unedited symbol was
the tell that the edit landed inside another declaration's header.
