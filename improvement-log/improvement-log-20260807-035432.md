### 2026-08-07 — Asked for the symptom before hypothesizing

**What happened:** "Creating a session with a manually added path always fails" had three plausible readings — the request being rejected, the add-by-path alert never presenting over the sheet, or the path being silently discarded by the sheet's revert path. Each implies a different fix. I probed the server first (manual absolute path → 200, so the server was innocent), then asked Eugene which symptom he saw, then reproduced that exact case in the simulator.
**Why this was right:** Memory `ground-truth-before-hypothesizing` exists because of sessions that picked a theory and iterated on it. One question cost ~30 seconds and eliminated two of three branches. The sim repro then produced the literal failing UI, which showed a second bug (no error text) I would not have looked for.
**What better looks like:** Keep doing this. The tell for "ask" vs "just build": the readings lead to *different files*, not just different wording.

### 2026-08-07 — `lastError` is set everywhere and displayed nowhere

**What happened:** `SessionStore.lastError` is assigned on ~15 distinct failure paths (create, send, stop, transfer, outbox, fork, resume). `grep` across every view file found zero readers. The rejected create surfaced to the user as a bare "Not sent" chip with a Retry button and no reason — the server's actual sentence ("directory not found") was thrown away.
**Why this matters:** This is the reason a one-character input problem read as "it always fails" rather than "I typo'd the path." A failure the user can't diagnose is indistinguishable from a broken feature, and it routes a 2-minute self-fix into a debugging session.
**What better looks like:** A store property named `lastError` with no reader is dead code that *looks* like error handling — it makes the codebase read as if failures are surfaced. Either wire it to a view or delete it. This session added `PendingSend.failureReason` (rendered under "Not sent") for the send/create paths, but the other ~13 `lastError` writes are still invisible. Worth a follow-up: one app-level error surface, or drop the property.

### 2026-08-07 — Path input used prose keyboard defaults

**What happened:** The "Add directory by path…" alert used a bare `TextField`, so it inherited sentence autocapitalization and autocorrection. The simulator screenshot showed a red spellcheck underline under "eugenechan" while typing a real path.
**Why this matters:** On the software keyboard this silently rewrites directory names, so the app sends a path the user never typed and the failure looks random rather than caused. It's the same class of bug as the `~` one — the field accepts human text and the pipeline assumes machine text.
**What better looks like:** Any field holding a path, URL, identifier, host, or token gets `.textInputAutocapitalization(.never)` + `.autocorrectionDisabled()` at minimum. Treat the prose defaults as opt-in, not the baseline.

### 2026-08-07 — Verified a server change without restarting the shared server

**What happened:** The fix was in the long-lived `lfg serve` process on :8766, which ~16 concurrent agent sessions depend on. Rather than restart it (the documented deploy path, but it drops in-memory session tracking for everyone), I started a second server on :8799 with `LFG_DATA` pointed at the scratchpad, probed the real endpoint, and killed it.
**Why this was right:** It exercised the real HTTP seam (memory `verify-real-seam-not-mocks`) — expanded cwd in the 200 response, expanded path in the 400 — with zero blast radius on other sessions.
**What better looks like:** Make this the default for verifying server changes in this repo. `LFG_PORT` + `LFG_DATA` is a one-line isolated instance; note it as the standard pre-restart verification step. Clean up spawned tmux panes afterward (this run created 7 test sessions and killed all 7).

### 2026-08-07 — The directory picker listed capabilities, not history

**What happened:** The new-session directory picker offered Root, Inbox, and `store.repos` — a one-level scan of the repos root for directories containing `.git`. Every other place work actually happens was unpickable: a session started from the CLI or a tmux pane on the host, a subdirectory of a repo, a scratch folder, or a path typed into "Add directory by path…". You could start a session in a directory once and then never select it again.
**Why this was wrong:** The list answered "what looks like a repo?" when the user's question is "where have I been working?" Those diverge immediately in practice — this session's own repro directory (`lfg/scripts`) had a live session in it and still wasn't offerable. It also made the add-by-path feature a dead end: the one path you had to hand-type was the one the picker would never remember.
**What better looks like:** Derive pickable options from observed state, not from a heuristic scan. `store.sessions` (live + optimistic + closed, already fanned out across hosts) carries a `cwd` per session and covers host-started sessions via their transcripts — so the fix was a computed property on the client, no server change and no restart. General rule: when a picker is backed by a scan, ask what the scan structurally cannot see, and whether the app already observes that thing elsewhere.
**Known limit worth revisiting:** closed sessions come from the first resumable page (~30/host) plus whatever "Load more" fetched, so very old directories won't appear until paged in. A server-side enumeration of transcript cwds would be exhaustive but slower and needs a restart — deferred deliberately.

### 2026-08-07 — Lost the build number by tailing instead of teeing the deploy

**What happened:** Ran `bundle exec fastlane ios deploy_testflight 2>&1 | tail -45` so the output wouldn't flood context. The upload succeeded, but the build number (the HK timestamp the lane injects via `xcargs`) was printed earlier in the run and scrolled past the tail window. The `verify_testflight_build` lane — the skill's whole definition-of-done — takes `build_number:` as a required argument, so I then hunted it across the stale `fastlane/deploy-*.log` (that file is written per-invocation by a wrapper, not by this lane), `fastlane/report.xml` (no version in it), and a nonexistent `fastlane/build/*.ipa`, before finding it in `~/Library/Logs/gym/LFG-LFG.log`.
**Why this was wasteful:** Four probes for a value the deploy had already printed. `tail -N` on a long command discards exactly the identifiers you need next; the fix is to keep the whole thing on disk and tail the *file*.
**What better looks like:** Always `… deploy_testflight 2>&1 | tee fastlane/deploy-$(date +%Y%m%d-%H%M%S).log | tail -40` — full output persisted, terminal still quiet. Then `grep -oE 'CURRENT_PROJECT_VERSION=[0-9]{12}' <that log>`. Generalize: when a command's output feeds a follow-up command, tee it; only tail what you're reading with your eyes. Fallback for a lost lfg build number is `~/Library/Logs/gym/<scheme>-<scheme>.log`.
