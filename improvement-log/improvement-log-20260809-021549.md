### 2026-08-09 — Zero-size pty made a working feature look broken

**What happened:** To check whether `mosh host -- <cmd>` runs the remote command, I wrapped mosh in
`script -q /dev/null`. mosh connected (alt-screen escapes appeared) then died with
`mosh did not shut down cleanly … Error: vector`, and the remote side-effect never happened. Across
four probes I was converging on "mosh 1.4.0's remote-command form doesn't work here" — which was
wrong. `script` on macOS hands the child a pty with no winsize, and mosh's terminal emulator can't
initialise at 0×0. Re-running the identical command inside a `tmux new-session -x 120 -y 40` pane
worked first try.

**Why this was wrong:** I treated my harness as neutral and the subject as suspect. The failure mode
(`Error: vector`) was an artifact of the measuring instrument, and it was pointing me toward a false
conclusion about the very thing I was about to build on.

**What better looks like:** When a terminal-attached program misbehaves under automation, verify the
harness before doubting the program — a pty needs an explicit size. `tmux new-session -d -x W -y H`
+ `capture-pane` is the reliable default for driving pty programs headlessly; `script -q /dev/null`
is not, because its winsize is unset. Corollary of [[probe-shape-before-scripting]]: the probe can be
broken in ways that look like a real negative result, not just like a sentinel.

### 2026-08-09 — The mosh aliases in ~/.zshrc never worked

**What happened:** While porting the desktop client to mosh I measured what `mosh host -- cmd`
actually gives the remote command: `PATH=/usr/bin:/bin:/usr/sbin:/sbin`, no Homebrew, and no shell
(mosh `execvp`s the argv directly). So `alias airt='mosh … -- tmux attach'` cannot find `tmux` and
the window dies instantly — confirmed by a dead pane, exit status 0.

**Why this matters:** The alias comment in `~/.zshrc` explains the `--server` flag with exactly this
PATH reasoning, so the cause was already understood for the *server* half and simply not carried over
to the *command* half. The bug survived because the failure is silent and instant — it looks like
"mosh quit" rather than "tmux not found".

**What better looks like:** Same fact, two consumers — when a hazard is written down for one half of
an invocation, check whether the other half has it too. Fix is `-- /bin/sh -c 'PATH=…: exec tmux
attach'`. Captured in `desktop/README.md` and memory [[mosh-remote-command-no-shell]].

### 2026-08-09 — Almost built the desktop app on the Air instead of shipping the Pro's signed one

**What happened:** Memory [[air-desktop-adhoc-signing]] said "the Air signs ad-hoc, expect a TCC
prompt after every deploy", so I rsynced a build tree to the Air and built there. The build was
ad-hoc as predicted — but then I checked the *already installed* app on the Air and it carried
TeamIdentifier 39GJBP8V5A, the Pro's Developer ID. The prior deploy had copied the Pro's signed
bundle, which is strictly better: one stable code identity, so the iTerm automation grant survives.
I discarded the Air build and shipped the Pro's.

**Why this was wrong:** I read the memory as a description of what to *do* when it was a description
of a *constraint*. It documented the failure mode of one approach without recording that a better
approach existed and was already in use — and the evidence was one `codesign -dv` away.

**What better looks like:** Before deploying to a second machine, inspect what's actually installed
there — signature, version, mtime — rather than reproducing the build from scratch. When a memory
describes a limitation, ask whether it's the limitation of the *machine* or of the *approach* I last
took. Memory rewritten to lead with "build on the Pro, `ditto` the bundle over".

### 2026-08-09 — A test tmux client shrank a live agent pane by one row

**What happened:** To test the fixed `airt` alias verbatim I sized my throwaway tmux client to
120x200 to match lfg's `PANE_COLS`x`PANE_ROWS` so nothing would be resized. It attached to a live
Claude session on the Air, which then read 120x**199** — the client's 200 rows are split into 199
window rows plus one status line. `ensurePaneRows` should have restored it, but 15s later it was
still 199; I resized it back manually.

**Why this matters:** The project CLAUDE.md warns that one wrong-sized attach silently breaks
question capture forever. I did the right thing (match the size) and still lost a row, because I
matched the *client* size to the *window* size — off by the status bar. That the pump didn't
self-heal is a second, separate thing worth understanding.

**What better looks like:** When attaching a client to a size-sensitive tmux session, size it to
`PANE_ROWS + 1` (status line) — or better, verify with
`tmux list-sessions -F '#{window_width}x#{window_height}'` before AND after, and restore on drift.
Open question to check later: why `ensurePaneRows` didn't restore this pane — if it only runs for
pump-tracked sessions, hand-started `cy-*` sessions are unprotected.
