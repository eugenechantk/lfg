## Log

### 2026-09-05 — `script -q` is not a valid pty for mosh in a tty-less session

**What happened:** Probing what SGR attributes survive mosh, I ran `mosh-client` under `script -q` twice (once via mosh-bridged, once loopback). Both died with `Error: vector` / "did not make a successful connection", which I first read as a bridge/UDP problem.
**Why this was wrong:** `script` inherits the invoking terminal's winsize; with no tty that's 0×0, and mosh aborts on the zero-size framebuffer before doing anything. The failure fingerprint looks like a network problem but is the harness.
**What better looks like:** For any curses/emulator probe from a non-tty session, go straight to a Python pty harness — `pty.openpty()` + `ioctl(TIOCSWINSZ, 24×80)` — rather than `script`. Recipe recorded in `.claude/diagnosis-codex-mosh-dim-20260905.md` and the [[mosh-color-depth-is-the-c-flag]] memory.

### 2026-09-05 — "Unfixable" verdict issued without reading the upstream source

**What happened:** The first diagnosis pass concluded the mosh dim drop was "unfixable from outside — faint support would have to land in mosh's emulator" and recommended living with it. When Eugene asked for a fix, ten minutes of reading mosh master showed the `faint` enum bit already existed and only needed ~10 lines to wire up (parse SGR 2, emit `;2`); a patched build deployed to both hosts the same day.
**Why this was wrong:** "Unfixable" was really "not fixable by configuration". For open-source tools we build and control on both ends, patching IS an available fix path, and its cost should be assessed (by reading the source) before writing the option off. The wrong verdict nearly ended the task at "live with it."
**What better looks like:** Before declaring a third-party limitation unfixable, check: (1) is it open source, (2) do we control every deployment point, (3) what would the patch actually touch? Only call it unfixable if one of those fails.

### 2026-09-05 — Fixed a real defect that wasn't the symptom the user meant

**What happened:** The opening report was "codex sessions over ssh have some color difference." I found a genuine defect (mosh drops SGR dim), fixed it, and declared the issue resolved. The user came back with a screenshot: the actual thing he saw was the composer's grey background missing — a completely separate mechanism (codex's OSC 10/11 startup probe going unanswered, latching a no-fill fallback per session).
**Why this was wrong:** With a vague symptom, I anchored on the first real defect I found and never confirmed it produced the difference *he* was seeing. The discriminating question — "what exactly looks different, on which screen element?" — or one screenshot request would have pointed at the composer immediately. [[verify-the-discriminating-case]] applies to symptom identification too, not just fixes.
**What better looks like:** For "X looks different/wrong" reports, pin down the observable (which element, which shade, compared to what) before or immediately after finding the first plausible cause. One found defect is not proof it's THE defect; check whether the old behavior would also explain the report.

### 2026-09-05 — Canonical-mode tty ate the probe replies; nearly debugged the wrong layer

**What happened:** Two loopback tests of the new OSC responder returned zero bytes. I instrumented the emulator (debug fopen logging, two rebuilds) before realising the responder had worked all along — the reply has no trailing newline, and the test child's tty was in canonical mode, so the line discipline held the bytes and `cat`/`dd` never saw them. `stty raw` made both replies appear instantly.
**Why this was wrong:** The failing component was the test harness, not the code under test. The instrumentation DID narrow it (branch fired, bytes queued), but a tty-discipline check should have come before rebuilding with debug code: real clients (codex) set raw mode, my probe didn't — a probe-vs-reality mismatch, the [[probe-shape-before-scripting]] failure mode.
**What better looks like:** When a byte-level probe over a tty reads nothing, check the line discipline first (canonical vs raw, echo) — it's a 5-second `stty raw` test before any rebuild-with-printf cycle.

### 2026-09-05 — Edited the live connect path in place; user hit the broken window

**What happened:** While adding the LAN fast path I edited `scripts/mosh-bridged` — the script behind Eugene's `pro`/`prot` aliases — in place, and a zsh quoting bug (`${(q)arr}` without `[@]` quotes the joined string, not each element) made the carrier exit 127. Eugene tried to open a session during that ~5-minute window and got "mosh: Nothing received from server on UDP port …".
**Why this was wrong:** This script is production infrastructure for a user actively connecting. The edit sat live and untested while I continued working; the very first execution was Eugene's real connection instead of my probe.
**What better looks like:** For scripts on a live path, verify with one probe run immediately after each edit — before moving to anything else — or stage the edit in a copy and swap it in after the probe passes. Also: zsh per-element quoting is `${(j: :)${(q)arr[@]}}`; the `[@]` is load-bearing.

### 2026-09-05 — `cat`-echo latency test measured mosh's prediction, not the network

**What happened:** The first LAN-vs-CF latency A/B used a remote `cat` and reported 0ms on both paths — mosh's predictive local echo answers an identity echo instantly. Switching the remote to `tr a-z A-Z` (a transform only the far side can produce) gave the real numbers (41ms vs 364ms).
**Why this was wrong:** The probe's output was indistinguishable from the thing being measured — the [[verify-the-discriminating-case]] failure: identical output under both hypotheses proves nothing.
**What better looks like:** Latency probes through any predictive/caching layer must demand a response the near side cannot fabricate. For terminals: echo through `tr`/`rev`, never `cat`.

### 2026-09-06 — GUI automation raced a user who wasn't at the keyboard

**What happened:** Automating Surfshark's Bypasser on the Air, the app window kept closing between steps and AX reads went intermittently blank. I retried four rounds (single-step, atomic script, reopen-with-guard) before a screenshot came back black — the display had slept, and the wake showed the lock screen. Eugene was messaging from his phone the whole time; nobody was at the Mac.
**Why this was wrong:** The very first anomaly (a self-closing window with no user click to explain it) was already evidence that the local session wasn't being used. The project CLAUDE.md even warns "the display is usually asleep" — I checked once at the start, then never re-checked as conditions changed.
**What better looks like:** Before and *during* GUI automation, verify someone is actually at the machine: `ioreg -c IOHIDSystem | awk '/HIDIdleTime/'` for input idle time, plus a screenshot on any unexplained UI state change. If idle time is minutes-long while the user is actively chatting, they're remote — park GUI work and ask for an unlocked window of time instead of retrying.
