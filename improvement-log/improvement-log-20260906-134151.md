### 2026-09-06 — Unquoted `--include=*.swift` glob under zsh

**What happened:** Two separate grep calls used `--include=*.swift` unquoted; zsh tried to expand the glob, found nothing, and aborted the whole command with `no matches found`. I re-ran the search without noticing the first time and lost a round-trip.
**Why this was wrong:** zsh (unlike bash) errors on an unmatched glob instead of passing it literally. The pattern is a known trap and the fix is trivial.
**What better looks like:** Quote it (`--include='*.swift'`) or just grep a directory and filter with `.swift` in the pattern. Read the tool result before re-issuing a command that looks like it worked.

### 2026-09-06 — Re-hit a documented FlowDeck guard trap

**What happened:** Put the simulator UDID in a shell variable (`S=…; flowdeck … -S $S`) to shorten a multi-command chain. The guard parses raw command text, saw `$S`, and blocked the call. The memory `flowdeck-sim-guard-cwd` lists exactly this ("use a literal UDID, never a shell variable") plus "one flowdeck command per Bash call".
**Why this was wrong:** The memory index line only says "don't cd between flowdeck commands; use the literal UDID the guard returns" — I read that as "don't retype it wrong", not "don't use a variable". I also chained several flowdeck calls per Bash call, which the memory says to avoid (they happened to work).
**What better looks like:** When a memory is recalled for the tool I'm about to drive, open the file before the first command, not after the first block. The index hook for that memory should name the variable trap explicitly.

### 2026-09-06 — pbxproj signing diff was deploy residue, not a teammate's edit

**What happened:** `git diff` showed `CODE_SIGN_STYLE = Manual` / `Apple Distribution` changes in `project.pbxproj`. I assumed another session had made them deliberately, decided `xcodegen generate` would clobber their work, and hand-inserted four pbxproj entries for my new file. The Fastfile's `deploy_testflight` runs `xcodegen generate` and `update_code_signing_settings` on every deploy; a deploy had run at 17:55 that day. The diff was its residue, and the deploy lane regenerated the project anyway.
**Why this was wrong:** I attributed a diff without checking who made it. `ls -t ios/fastlane/deploy-*.log` or `grep update_code_signing ios/fastlane/Fastfile` would have taken ten seconds. The hand patch cost more than that and was thrown away by the next regen.
**What better looks like:** For any unexplained diff in a generated file, look for the generator's own log first (fastlane, xcodegen, formatters) before assuming a human/agent edit. Saved as memory `lfg-pbxproj-signing-diff-is-deploy-residue`.

### 2026-09-06 — Wrong interpretation of "highlight text" (sheet vs in-place)

**What happened:** Eugene asked to "highlight text and show the highlight overlay to copy specific text in a response or in a table". I built a ChatGPT-style long-press → "Select Text" → sheet with a UITextView, verified it, and pushed it to TestFlight. He said: "You did it completely wrong. I need to be able to do the native thing and long press to get a cursor, and drag to highlight. Like how I can do that now in my input field."
**Why this was wrong:** The request described the native UIKit gesture on the content itself. I chose the sheet because it was the low-risk way to get UITextView behaviour without replacing MarkdownUI, and I logged that as a decision instead of recognising it as a fork that changes the whole UX. "What the OLD build would render" was never the question; "does this match the gesture he named" was. Then I deployed without him seeing it once — a deploy is outward-facing and the feature was untested by the person who asked for it.
**What better looks like:** When a request names a concrete native interaction ("long press to get a cursor, drag to highlight", "like my input field"), the deliverable is that interaction on that surface; an indirection (sheet, menu, mode) is a different feature and needs a one-line check before building. Before pushing a build of a new UX, show a screenshot/recording and let him react; ship on the next message, not the same one.

### 2026-09-06 — Replaced the renderer when only the selection layer was asked for

**What happened:** To get cross-block selection I rendered the whole message in one UITextView with my own table grid (tab stops + hand-drawn lines). Eugene, after seeing the TestFlight build: "The table rendering is all messed up. Revert back to the original rendering, but let me long press and highlight text, but limited to the content of that cell. We don't need cross cell copying."
**Why this was wrong:** I optimised for a capability he never asked for (drag across cells) at the cost of the rendering he already liked and another session had just polished (`BoundedTableCellLayout`). The cheaper design — MarkdownUI layout, native text view per paragraph/cell via the theme's `configuration.content` — was available from the start; I dismissed it because "selection would be per block", without checking whether per-block was acceptable. It was.
**What better looks like:** When a request is about an interaction layer, keep the rendering layer untouched unless the interaction is impossible without changing it — and if it seems impossible, ask which constraint he'd rather drop before rebuilding the renderer. Also: a screenshot of a table was in front of me and looked "fine enough"; compare against the previous rendering side by side before shipping a visual change to something he uses daily.
