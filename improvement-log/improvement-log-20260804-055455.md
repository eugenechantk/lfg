### 2026-08-04 — Stale memory: "fix is uncommitted" was wrong

**What happened:** `lfg-pro-host-sleep-disconnects.md` asserted the instant-reconnect
fix was uncommitted in the working tree. It had since been committed (`7a5b2ea`) —
but *after* the `41ac525 ios: 1.2.0` version bump, with `MARKETING_VERSION` never
re-bumped. So the true state was "committed, never shipped", which points at a
completely different action (cut a build) than what the memory implied (land the code).
**Why this matters:** a memory that names a *transient* state (uncommitted, in-tree,
pending) goes stale silently and sends the next session down the wrong path.
**What better looks like:** when writing a memory about work-in-progress, record the
*durable* fact (which commit, which released version) rather than the working-tree
state, or explicitly date-stamp the volatile claim. Corrected in place.

### 2026-08-04 — TestFlight deploy blocked by an unsigned Apple agreement

**What happened:** `deploy_testflight` failed instantly at the first App Store Connect
call with "A required agreement is missing or has expired." Nothing built, nothing
uploaded. This is a legal agreement only the Account Holder can sign in the ASC web UI.
**Why it cost time:** worktree creation, env copying, and `bundle install` all ran
before hitting a blocker that a single API call could have detected up front.
**What better looks like:** the testflight-deploy skill should preflight ASC
reachability (a cheap `Spaceship::ConnectAPI::App.find`) *before* the worktree/bundle
setup, so an agreement or auth blocker surfaces in seconds rather than after setup.
Worth proposing as a skill change during the next `/self-improve`.

### 2026-08-04 — A stale pid made a server restart silently not happen

**What happened:** Restarting the Air's server, `lsof -ti :8766 | head -1` returned
34613. Killed it; `ps` still showed the Jul-31 server (34701) running. The real port
owner was 34701 — a child of `serve-forever` — and 34613 was stale. Had I trusted the
kill, I'd have reported the Air as updated while it ran 4-day-old code.
**Why this matters:** project CLAUDE.md already says "kill by PORT, not by pkill
pattern (stale processes silently keep the port), and verify the NEW code answers
before declaring the deploy done." I followed the first half and nearly skipped the
second. The verification is the part that caught it.
**What better looks like:** after any restart, assert the *new* pid's start time is
later than the changed file's mtime. Never infer a restart from the kill succeeding.
`lsof -ti` can return more than one pid — resolve each through `ps` before killing.
