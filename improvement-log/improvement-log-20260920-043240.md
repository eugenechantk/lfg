### 2026-09-20 — Bundled-hosts feature existed but the shipped build lacked the payload

**What happened:** Eugene asked to bundle Pro/Air tunnel URLs and tokens into the app. The feature was fully implemented on Aug 20–21 (LFGCore parser, launch seeding, generator, gitignored payload), but build 202609192001 was archived from a clean worktree with no payload, so the phone showed the setup form again.
**Why this was wrong:** A gitignored build input with no lane check is a silent failure: the archive succeeds, the DoD lane passes, the user experiences a regression. The worktree-deploy memory listed `.env` files but not the payload, so the deploying session had no cue.
**What better looks like:** Every gitignored build input needs (1) a generate-or-fail gate in the lane and (2) an IPA ground-truth check in the DoD lane. Done for this payload; the same pattern applies to any future private resource. Also: when asked for a feature, grep for it first — this one took one grep to find.

### 2026-09-20 — TestFlight upload thrashed through a VPN tunnel

**What happened:** altool uploaded for 13 minutes, sending >260 MB for an 8 MB IPA. Its error output showed "WILL RETRY PART 1. Checksums do not match" on every attempt, then crashed. The route to Apple's upload host was via utun4 (a VPN, 26.26.26.1) while the default route was the en0 hotspot.
**Why this was slow:** I only noticed after Eugene asked; the deploy lane prints nothing during upload, and I had no pre-flight route check. Memory already documents the same VPN-corruption pattern for cloudflared (edge-bind) but not for altool.
**What better looks like:** Before any TestFlight upload, run `route -n get 17.156.106.13` (or the resolved contentdelivery host) and refuse or warn when the interface is a utun. Consider a Fastfile pre-upload check that prints the route and interface. When the upload runs >3 min, sample `nettop -p <altool pid>`: bytes_out ≫ IPA size with tiny bytes_in means retries, kill it.

**What better looks like:** Any codesign on the Air runs inside its GUI tmux server: `/opt/homebrew/bin/tmux new-session -d -s <name> -c <dir> "<cmd> > log 2>&1"`. Added to the secondary-host TestFlight memory so both entry points say it.

### 2026-09-20 — git on the Air's synced repo rewound the Pro's main

**What happened:** I ran `git fetch` + `git worktree add` in `~/dev/personal/lfg` on the Air (whose `.git` is Syncthing-shared with the Pro). Minutes later the Pro's `refs/heads/main` was back at 08de5d5 (the Air's stale value) although fb23f0d had been committed and pushed from the Pro. My docs commit 419f22c was therefore created on 08de5d5, and `git push` was rejected as non-fast-forward. Recovery: replay the docs commit onto origin/main in a scratch worktree, push, `git update-ref` local main, reset the index for the three affected paths.
**Why this was wrong:** Memory `air-xcode-license-bypass` already warns that `.git` syncs and that agents committing on both machines risks ref conflicts. I treated fetch/worktree as harmless; any write under `.git` on either machine can win the sync.
**What better looks like:** Never run git write operations (fetch, worktree, checkout, commit) in the Air's synced checkout. For Air builds, use a separate clone outside the synced folder (`git clone https://github.com/eugenechantk/lfg.git ~/build/lfg-testflight`) and copy the gitignored env files into it. After any git activity on the peer, `git log -1` on the Pro before committing.
