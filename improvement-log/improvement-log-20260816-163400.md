## Log

### 2026-08-16 — Two rounds of root-cause work, zero rounds on the escape hatch

**What happened:** Rounds 1 and 2 of the "stuck pending rows" investigation shipped two builds of
reconciliation fixes (timestamp-aware matching, history-fetch retry) and the bubbles were still
there. Nobody checked what happens when the user taps the row and picks **Remove** — which turned
out to be a guaranteed 409 for exactly the rows that get stuck, because `removeMessage` treated a
`delivered` receipt as un-retractable work.

**Why this was wrong:** The bug report literally said "a queued message I cannot delete". That
sentence names a broken affordance, not a reconciliation edge case. Reading it as "reconciliation
is still wrong" skipped the cheapest, most direct check: exercise the control the user says is
failing. Two builds and a day of work went into the harder theory first.

**What better looks like:** When a report names a specific control that doesn't work ("I can't
delete it", "the button does nothing"), trace THAT control end-to-end before theorising about the
state machine behind it. Recovery paths deserve the same verification as happy paths — an escape
hatch that fails only in the situation it exists for is worse than none.

### 2026-08-16 — FlowDeck sim guard rejects shell variables

**What happened:** Wrote `S=<udid>; flowdeck ui simulator tap ... -S $S` to avoid repeating the
UDID. The guard hook blocked it with "this command targets '$S'" — it matches the raw command text
before the shell expands anything.

**Why this matters:** Cost a round-trip and looked like the UDID was wrong. Related to memory
`flowdeck-sim-guard-cwd`, which already says the guard is text/cwd sensitive.

**What better looks like:** Always paste the literal UDID the guard hands back into every
`flowdeck run/test/ui` call. Never parameterise it with a shell variable.
