### 2026-08-07 — Six tool calls of AX automation against an asleep display

**What happened:** To verify the narrow window I launched the app, then tried System Events to resize
and screenshot it. `count of windows` returned 0. I retried with a second instance, an app relaunch,
the Window menu, and the menu-bar status item before taking a full-screen `screencapture` — which came
back solid black. The login session was locked/display asleep the whole time (Eugene drives these
sessions remotely from the iOS client, so this is the *normal* state, not the exception).
**Why this was wrong:** The AX symptom (0 windows) is indistinguishable from a dozen other causes; the
one-call check that disambiguates all of them (`screencapture` → is it black?) came last instead of first.
**What better looks like:** In this repo, assume the screen is asleep. Before any GUI automation, take a
throwaway `screencapture -x` and look at it. If it's black, skip straight to a headless harness.

### 2026-08-07 — Hardcoded test count in `--desktop-feature-test`

**What happened:** `DesktopFeatureTestCLI` prints `{"ok":true,"tests":37}` as a string literal. I added two
assertions and the output still said 37 — it only got noticed because I grepped `try expect(` out of
curiosity. Fixed to 39, but the next person hits the same trap.
**Why this matters:** A count that doesn't come from the run is decoration, not a signal. A dropped or
skipped assertion would never show up.
**What better looks like:** Count assertions at runtime (increment in `expect`) instead of maintaining the
literal by hand. **Done** later in the session — `expect` now increments `assertionCount` and the CLI prints it.

### 2026-08-07 — Hid host labels by breakpoint when I could measure the real fit

**What happened:** For the compact toolbar I made "narrow" mean "no host labels" — a single boolean applied
to every item at once. Eugene immediately pointed out there was obvious empty space next to the dots at 490pt.
Measuring showed his actual labels ("Pro", "Air") cost 67pt and fit comfortably from ~470pt up; only long
display names ("Creative Studio") needed dropping.
**Why this was wrong:** I already had `--window-fit` giving exact numbers, and still made the degradation
decision from a hand-picked threshold rather than from the measurement. A tier-based "compact mode" bundles
unrelated decisions (picker style, search style, label visibility) behind one switch, so the cheapest item
gets punished for the most expensive one.
**What better looks like:** Degrade per element against a measured budget, not per breakpoint. The fixed
version measures the labelled cluster off-screen (cached per name set) and keeps the labels while they fit —
`ContentView.hostLabelsFit(clusterWidth:windowWidth:)`, unit-tested. Same idea applies to any responsive
layout: measure the element, spend the budget, don't guess a tier.

### 2026-08-07 — Built a headless window/toolbar harness (done)

**What happened:** The existing headless hooks render *views* through `ImageRenderer`, which can't see
toolbars — toolbars are window chrome, and the whole bug was "the toolbar won't fit". Added
`--window-fit` (real off-screen `NSWindow`, reports items vs `visibleItems` per width, exits 1 on
overflow) and `--window-shot` (draws the window incl. titlebar via `cacheDisplay`, so it needs no Screen
Recording grant and no awake display).
**Why it mattered:** It immediately falsified my first two attempts (compact labels, then moving the
centered item) by showing items still dropping into », and gave the exact 440pt floor. Guessing from
item widths would have shipped a broken minimum — AppKit charges ~300pt of chrome before any item gets a point.
**What better looks like:** Reach for a measurement harness the moment a layout question has a number in
it. Both hooks are documented in `desktop/README.md`.
