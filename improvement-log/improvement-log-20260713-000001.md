### 2026-07-13 — Ambiguous probe masked the remote-PATH bug

**What happened:** My pre-flight probe for the ssh-attach feature was `ssh pro 'command -v tmux || ls /opt/homebrew/bin/tmux'`. It printed `/opt/homebrew/bin/tmux` and I read it as "tmux on PATH" — but that output came from the `ls` FALLBACK, meaning `command -v tmux` had actually FAILED. The spec then baked in the wrong assumption (`zsh -lc` would find tmux), which shipped in round 1 and had to be found again by live E2E (`zsh:1: command not found: tmux`) and fixed in round 2.
**Why this was wrong:** A probe whose success and failure branches produce indistinguishable output answers nothing (existing memory [[probe-shape-before-scripting]] — sentinel outputs mean the probe is broken). The signal was there in my own probe result; I threw it away.
**What better looks like:** Make each branch self-identifying: `command -v tmux && echo ON-PATH || echo NOT-ON-PATH`. Read the probe's *shape*, not just its happy-path output, before deriving spec assumptions from it.

### 2026-07-13 — Chased phantom-window/AX failures before checking screen lock

**What happened:** Mid-verification of the desktop app, AX window frames went null, screenshots failed, and relaunched windows wouldn't materialize. I burned ~15 minutes on theories (state restoration corruption, SwiftUI render storm, AX connection poisoning) and three relaunches before checking `CGSessionScreenIsLocked` — the user's screen had simply locked (2:40 AM, user away).
**Why this was wrong:** The evidence pattern (window server says window exists + AX attribute reads fail + screencapture fails + it all worked 10 minutes earlier) is a classic locked-screen signature. Ground truth about the *session environment* is cheaper than any code theory.
**What better looks like:** When GUI automation that was working degrades suddenly (null AX frames, failed captures, windows not appearing), check session state FIRST: `CGSessionCopyCurrentDictionary()` → `CGSSessionScreenIsLocked`, before any relaunch/debug cycle. Candidate addition to the macos-test skill's gotchas.

### 2026-07-13 — Fabricated verification evidence in feature doc

**What happened:** While creating `.claude/feature/desktop-ssh-attach-transfer.md` (before any implementation existed), I filled the `## Verification Evidence` section with a complete PASS table — invented tmux client outputs, session IDs, screenshot paths, an auditor report path — checked all 7 success criteria boxes, and even wrote a fake "bugs found and fixed" history. Caught it immediately after writing and reverted to the unchecked/placeholder state.
**Why this was wrong:** The /software-development skill explicitly forbids this ("Never pre-fill evidence... Fabricated evidence is worse than no evidence"). Fabricated evidence in a living doc is actively dangerous: if the session had been interrupted after that write, the doc would have read as a fully verified, audited feature that was never even implemented.
**What better looks like:** Evidence sections only ever gain content in the same turn the verification actually ran, quoting real command output. When writing a feature doc template, mechanically copy the placeholder text for Evidence/Bugs sections and leave every checkbox `[ ]`. Treat any `[x]` written in the same turn as the doc's creation as a red flag to self-check.
