## Log

### 2026-08-11 — Stub-host log had two racing writers and silently lost data

**What happened:** The throwaway stub host's `log()` called `Bun.write(LOG, line)` (which
truncates the whole file) *and* `fs.appendFileSync(LOG, line)`. The file ended up holding two
lines out of dozens. I read it and concluded the iOS client had made no contact with the
recovered host — the opposite of the truth, which the in-memory `/__received` endpoint reported
correctly seconds later.

**Why this was wrong:** A test rig that lies is worse than no rig. I wrote the logger on
autopilot without asking what `Bun.write` does to an existing file, and the failure mode was
silent — no error, just missing lines.

**What better looks like:** For an append-only trace, use exactly one append-mode writer. And
when a rig's log and a rig's in-memory state disagree, trust the in-memory state and fix the
log — don't reason from the log. Neighbour of [[probe-shape-before-scripting]]: run the probe
once and eyeball the real record before drawing conclusions from it.

### 2026-08-11 — First hypothesis was wrong; the repro is what caught it

**What happened:** After reading `SessionStore.replayPendingOutbox` / `setHostState`, I had a
confident story about the recovery drain never firing. The live repro (stub host, iPhone 17 Pro
sim) showed the foreground case works: host back at 18:12:48, queued message delivered by
18:13:24 (~36s, the link's 30s backoff cap). The real bug had to be somewhere else.

**Why this matters:** Both [[ground-truth-before-hypothesizing]] and
[[disconfirm-before-declaring-root-cause]] exist for exactly this. The cost of the repro
(~15 min) was far less than the cost of shipping a fix for a path that already worked.

**What better looks like:** Keep doing this — build the repro before the diagnosis, and name
the observation that would disconfirm the theory (here: "does the message land without opening
the session?") before running it.

### 2026-08-11 — Made a simulator by hand instead of letting the FlowDeck guard make one

**What happened:** I ran `flowdeck simulator create/boot` for a sim named `cc-offlinequeue`,
then the first `flowdeck run` was BLOCKED by the per-session simulator guard, which created and
booted its OWN sim (`cc-3bf50873`) and told me to use that UDID. `cc-offlinequeue` is now an
orphan — and `flowdeck simulator delete <its udid>` is *also* blocked by the guard, because the
UDID isn't this session's. Booting it also caused the guard to evict two other sessions' sims
to stay under its cap.

**Why this was wrong:** The guard owns simulator lifecycle for a session. Creating one myself
was work that got thrown away, cost two other agents their booted sims, and left garbage I
can't clean up.

**What better looks like:** Never `flowdeck simulator create/boot` in a session. Run the real
command first (`flowdeck run …`); if the guard is active it hands back the UDID to use for
everything after. Extends memory [[flowdeck-sim-guard-cwd]] — the guard owns *which* sim, not
just *don't cd between calls*.

### 2026-08-11 — A background URLSession hides send failures from any loopback repro

**What happened:** Three separate offline→online rounds all delivered cleanly in the sim,
including one where I deliberately relaunched the app while the host was down expecting the
replay POST to fail. It never failed: `BackgroundSender` posts through a background
`URLSession`, which *waits for connectivity* instead of throwing when `127.0.0.1:8799` has
nothing listening. The system simply held the request and flushed it when the stub came back.

**Why this matters:** It means the entire family of "the send threw, what does the client do
with the row" paths is **unreachable** in a stub-on-loopback repro — which is exactly where the
real bug lives, because a Tailscale peer that black-holes packets looks like a live network to
iOS and the request times out and throws. I had to verify that branch by seeding the resulting
state (`state='failed'`) directly into the app's SQLite instead of producing it naturally.

**What better looks like:** When repro-ing client transport failures, remember loopback
"down" ≠ network "down". To make a request actually throw, point the host at an address that
black-holes (an unrouted tailnet IP), not at a closed local port. And when the natural failure
can't be produced, seed the post-failure state directly and say so in the evidence — don't
claim the throw path was exercised.
