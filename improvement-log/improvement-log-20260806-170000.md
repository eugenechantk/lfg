### 2026-08-06 — Tests polluted the real trace log

**What happened:** Added lifecycle tracing to `sendq.ts`; the first `bun test` run appended
~360 synthetic lines to `~/.lfg/sendq.log`, the exact file someone reads to explain a lost
message.

**Why this was wrong:** The unit tests drive real `enqueueMessage` calls, and the trace writes
to `PATHS.data`, which the tests don't override. Caught immediately by inspecting the file
after the run (rather than trusting the green suite).

**What better looks like:** Any new side effect on a shared host path needs a test guard in the
same change — here `if (process.env.NODE_ENV === "test") return`. Verified by re-running the
suite and confirming zero new lines. Log lines were cleaned out.

### 2026-08-06 — Reverted the "every send is a bubble" UX

**What happened:** Commit `40c1e8f` (a previous session) replaced the one-line pending bar above
the composer with an immediate blue bubble + "Queued" caption for messages waiting behind a
running turn. Eugene asked for the old behaviour back: bar while waiting, blue bubble only once
the backend has it.

**Why the original change was wrong:** It made "queued behind a running turn" and "the agent has
your message" render identically — same accent bubble, in the same place in the conversation,
differing only by a small grey caption. The commit's own rationale (a follow-up "never appeared
until the agent got around to it") is a *feedback* problem, and the bar already solved it; the
fix traded a real distinction for immediacy the bar already provided.

**What better looks like:** When a state is "not yet real", don't render it in the same visual
language as "real". Reverting restored: bar for queued/offline/failed-before-ack, bubble only
for sends the host has accepted. Also now filtered against the transcript so the bar clears in
the same render pass the real turn appears.

### 2026-08-06 — Rebasing left the Syncthing peer with a broken git HEAD

**What happened:** After committing and rebasing onto origin, the Air reported
`fatal: bad object HEAD` for every git command. Its **source files were already correct**
(all three fixes present, verified by grep) and `git rev-parse HEAD` resolved to the right
sha — but `git log` failed, because Syncthing had delivered `.git/refs` and the working tree
without yet delivering the matching `.git/objects`. A rebase rewrites objects wholesale, so
the window is much wider than for an ordinary commit.

**Why this matters:** It looks like repo corruption on the peer, and the instinctive fix —
`git reset --hard origin/main` — would have discarded whatever uncommitted work other agents
had in flight on that host (there were 10 dirty paths).

**What better looks like:** `git fetch origin` on the peer. It pulls the missing objects from
GitHub, heals HEAD, and touches no files. Confirmed: the Air went from `bad object HEAD` to a
correct 3-commit log with its 10 dirty paths untouched. General rule — on a Syncthing-shared
repo, treat a peer's git-metadata error as a *sync race*, not damage, and prefer the
additive repair (`fetch`) over any resetting one.
