### 2026-09-22 — Reached for host-routing hypotheses before testing the parse

**What happened:** On "404s on image/video files", my first three candidate causes were all
infrastructure: `/api/file` root containment, `routeHost` pinning reads to a down host, and
Syncthing lag on `~/.claude/projects`. Two memories ([[offline-host-read-routing]],
[[claude-projects-sync-lags-minutes]]) point that way, so it was an easy groove to fall into.
The actual cause was one regex in the iOS client: the session cwd was
`/Users/eugenechan/dev/inbox/AI girl game` and the markdown destination pattern `([^)\s]+)`
stops at a space.

**Why this was inefficient:** The cheapest discriminating fact was free — list the paths the
sessions actually handed over and ask whether they *exist* and whether the server *serves*
them. Both were yes within two commands (`os.path.exists` over the transcript's SendUserFile
inputs; one `curl` to `/api/file` with the percent-encoded path returning 200 + correct byte
count). That eliminated the entire server/routing family before a single hypothesis was
written down.

**What better looks like:** For any "the client can't load X" report, establish the three
links of the chain in order and stop at the first break: (1) does the file exist on disk,
(2) does the server return it when asked *correctly*, (3) does the client ask correctly.
Step 3 — what literal string does the client send — is where a 404 with a healthy file and a
healthy server has to live, and it is testable offline in seconds (a 10-line `swift`
scratch file running the real regex against the real transcript line printed the answer).

### 2026-09-22 — FlowDeck flag placement cost four failed invocations

**What happened:** Four commands failed in a row on flag shape: `flowdeck ui simulator -S <udid>
screenshot` (no such subcommand), `flowdeck ui simulator screen -S <udid> --screenshot <path>`
(unknown option), `flowdeck ui simulator --help` (blocked by the session guard for targeting
the shared simulator), `flowdeck ui simulator tap --label <x>` (no such option).

**Why this was inefficient:** Each round trip is a full tool call. The rules are simple and
uniform once seen: the subcommand comes first and `-S` belongs to the subcommand; `screen`
writes with `-o`; `tap` takes a bare positional target or `-p x,y`; and even `--help` must
carry `-S` because the guard inspects every invocation.

**What better looks like:** When first using a FlowDeck subcommand in a session, run
`flowdeck ui simulator <sub> -S "<udid>" --help` once and read the options — one call instead
of three or four guesses. Carry `-S "<udid>"` on *every* flowdeck command including help.

### 2026-09-23 — Documented a latent bug instead of fixing it, and it came back the same day

**What happened:** While fixing the spaced-path 404 I noticed and wrote in the diagnosis:
"`URLComponents` leaves `+` unescaped in a query value, and Bun's `URLSearchParams.get`
decodes `+` as a space — so a path containing a literal `+` would still 404. No such path
exists in these sessions." Hours later Eugene reported exactly that bug in a different
session, where three of nine images had `+` in the filename.

**Why this was wrong:** I scoped "does this matter" to the three transcripts I happened to
be looking at, and concluded from that sample that the case was hypothetical. It was a
two-second check to find out otherwise — `+` is routine in FlowDeck/auditor screenshot names
(`…-t+3.5s.jpg` is a timestamp convention), and a single `find ~ -name '*+*'` or a grep
across recent transcripts would have shown it live. The fix was ~10 lines in the file I
already had open, in the exact function I was already changing.

**What better looks like:** When a fix uncovers a sibling defect in the same code path, the
default is to fix it in the same change, not to write it down. If it genuinely should be
deferred, the deferral has to be justified by evidence that it is not live — and the
evidence has to come from the whole corpus, not from the handful of files in front of me.
"No such path exists in these sessions" was not that evidence.

### 2026-09-23 — `git stash` on a tree shared with concurrent agents

**What happened:** To check whether two failing tests pre-dated my change, I ran
`git stash --include-untracked`, ran the tests, and popped. Between my session start and
that moment another agent had begun editing `SessionStore.swift`, `SessionDetailView.swift`,
`ChildAgentSessions.swift` and `src/sessions.ts`. My stash swept up all of their in-flight
work and held it for the duration of the test run; the pop restored it, but a conflict, a
crash, or a second stash from another session would have stranded it.

**Why this was wrong:** The repo CLAUDE.md is explicit that the dirty tree IS other sessions'
work. `git stash` is a whole-tree operation — it does not care whose changes it takes — so
it is exactly as destructive as `git checkout --` on a path someone else is editing, just
with a longer fuse.

**What better looks like:** To test HEAD without my changes, never move the shared tree.
Use `git worktree add` on a temp dir at HEAD (or `git stash push -- <only my paths>` when a
worktree is overkill) and run there. Related consequence I did get right afterwards: because
the tree was mixed, `src/commands/serve.ts` contained both my hunks and theirs, so staging
had to be hunk-level (`git diff` → filter by hunk header → `git apply --cached --recount`)
rather than `git add <file>`. Check `git status` for newcomers before any whole-tree git
operation, not just before editing a shared file.
