## Log

### 2026-08-06 — Declared a root cause without running the disconfirming check

**What happened:** Diagnosing why `cy-001114-96215` showed "running" while wedged, I saw a
frozen `✻ Crunched for 2m 4s` in the pane capture, confirmed it matches `BUSY_METER` in
`isBusy`, and wrote that into `.claude/diagnosis-stop-close-noop-20260806.md` as the cause.
Eugene then asked "if the session is wedged, why is it stated as running?" — and the real
answer was elsewhere: `journal-pump.ts:209` is
`verdict != null ? verdict.state === "running" : paneBusy`, so the transcript verdict wins and
`paneBusy` is **never consulted**. The actual cause is a user turn (row 317) written into a
403-blocked session 33 hours later, which both (a) displaced the 403 assistant row that
`computeStatus` gates on and (b) became a `transcriptTurnState` "running" verdict that can
never be closed out.

**Why this was wrong:** I had a plausible mechanism and stopped. The disconfirming check was
one grep — "what actually assigns `busy`?" — and it would have shown the pane is a fallback,
not the source. Memory [[disconfirm-before-declaring-root-cause]] says to name the check that
would prove the theory innocent and run it *before* writing any diagnosis. I wrote the
diagnosis first. The wrong cause also implied a wrong fix ("un-latch busy on a frozen pane"),
which would have shipped and changed nothing.

**What better looks like:** For any "the UI shows state X" bug, trace the field back to its
assignment before theorizing about the *content* of a signal. The question is never "what
could produce X?" but "which line writes X, and what does it read?" One grep for the field
name beats a plausible story every time. Concretely: `grep -n "busy:" src/` before reading a
single pane capture.

### 2026-08-06 — Guessed a timing constant instead of measuring it

**What happened:** Writing the close-and-verify path, I picked `REAP_GRACE_MS = 700` as the
window a SIGHUP'd agent gets before escalating to SIGKILL. Pure intuition. The first LIVE close
came back `escalated: true` on a perfectly healthy session — so I measured, and a clean `claude`
actually takes ~1157 ms to exit after `tmux kill-pane`. 700ms would have hard-killed essentially
every close, costing each agent the `SessionEnd` hook that writes `state: "ended"` into the lease
and feeds the `closed` derivation.

**Why this was wrong:** All 13 unit tests passed with the bad constant, because they inject a
fake `alive()` — the fakes encoded my assumption instead of testing it. A timing constant is a
claim about the real world; a mocked suite structurally cannot check it. This is
[[verify-real-seam-not-mocks]] in a form I hadn't recognised: not "did the wire work" but "is my
number right".

**What better looks like:** When a constant encodes an assumption about how long something in
the real world takes, measure it before writing it down — the measurement here was one loop and
~30 seconds (`kill-pane`, then poll `ps` until the pid vanishes). Then bake the measured value
and the date into the comment so the next person knows it was observed, not invented. Rule of
thumb: any `*_MS` / `*_TIMEOUT` / retry-count constant governing an external process needs either
a measurement or an explicit "generous by design" note — never a bare round number.
