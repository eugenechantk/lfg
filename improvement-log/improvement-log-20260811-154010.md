## Log

### 2026-08-11 — Fixed-size tail window missed the data entirely

**What happened:** `recentUserTurns` read a fixed 192 KB tail of a transcript to
collect the last few human turns. On the real corpus that returned 0–1 turns for
every busy session, so the first live dry-run reported "all candidates too thin
to judge" and did nothing. The cause: in an agentic session the tail is almost
entirely assistant output and tool results — a 2.4 MB transcript had zero human
turns in its last 192 KB.

**Why this was wrong:** I picked the window size by feel and reasoned that "a
short window simply yields fewer turns, and fewer is a fine answer" — which is
only true if human turns are evenly distributed. They aren't, and the sessions
where they're sparsest are exactly the long, drifted ones the feature exists to
fix. Worse, the failure was *silent*: the task reported success with 0 changes,
which is indistinguishable from "nothing had drifted". Had I only run the unit
tests, this ships broken and looks fine.

**What better looks like:** When a heuristic depends on how data is distributed
in a real corpus, measure the distribution before choosing the constant — one
`bun -e` probe over five real transcripts would have shown it immediately (memory
[[probe-shape-before-scripting]] says this and I still didn't). And when a task
can legitimately return "nothing to do", make its log distinguish "found nothing"
from "couldn't look" — I only caught this because the note said *all* candidates
were too thin, which was too uniform to be real.

### 2026-08-11 — A format change is a deploy problem, not just a code problem

**What happened:** I changed `~/.lfg/session-titles.json` from `Record<id,string>`
to a record shape. The `lfg serve` process running on this box had been up since
14:45 and still had the old reader, which would have handed the client objects
where titles belonged. I caught it just before the first live write.

**Why this was wrong:** Not a code bug — the new reader is backward compatible in
the direction I was thinking about (old file → new code). I hadn't thought about
the other direction (new file → old code), which is the one that actually bites,
because this repo's CLAUDE.md explicitly warns that Bun has no hot-reload and the
running server routinely lags source.

**What better looks like:** For any change to an on-disk format shared with a
long-lived process, ask both directions of compatibility and order the deploy
accordingly — restart the reader *before* the first write of the new format, not
after. Checking `ps -eo pid,lstart` against the file mtime is already the
documented habit here; apply it when *writing* a format, not just when debugging
a stale one.

### 2026-08-11 — Bookkeeping fields on a record that gets dropped without a title

**What happened:** I first stored "autopilot last examined this session at N
bytes" as extra fields on the title-override record. But `parseTitleRecord` drops
any row without a title — and the sessions that most need a checkpoint are
exactly those with *no* override yet (they're wearing the drift-prone
first-prompt title). The checkpoint would have been silently discarded, so those
sessions would be re-examined on every single run forever.

**Why this was wrong:** I attached state to a record whose validity rule I had
just written myself, without re-reading that rule against the new use. The two
pieces of state have different lifetimes and different owners; colocating them
was convenience, not design.

**What better looks like:** Before adding a field to an existing record, re-read
that record's parser and ask what makes a row get dropped — then check whether
the new field's important cases survive it. When the answer is no, the field
belongs in its own store (which is where it ended up: `autopilot-retitle.json`).

### 2026-08-11 — `bun test` silently deleted the user's real session titles

**What happened:** After a full-suite run, `~/.lfg/session-titles.json` lost every
override. It looked like my new write path was clobbering the file, so I spent a
cycle hardening `updateTitleRecord`. The actual cause: `PATHS.data` falls back to
`~/.lfg` when `LFG_DATA` is unset, `PATHS` is resolved on the FIRST import of
`config.ts`, and only one test file wins that race. Under the full suite the
fallback stayed pointed at the real `~/.lfg`, and `session-search.test.ts`'s
`beforeEach` → `rmSync(sessionTitlesPath)` deleted live user data. It was
disguised: on the next `lfg serve` boot, `config.ts`'s legacy-data migration
re-copied the stale two-entry `<repo>/data/session-titles.json`, so the file came
back looking plausible instead of obviously missing.

**Why this was wrong:** Two failures. (1) I read that exact hazard — the comment
in `session-search.test.ts` spells out "another test file's `LFG_DATA` may already
have won" — and treated it as a correctness note about which temp dir wins, not as
"this can point at the user's real data". (2) I then wrote a fourth test file with
the same `rmSync(PATHS.…)` shape, and only got lucky that I ran it in isolation
first. A test suite that destroys real state is a much bigger bug than the feature
I was building.

**What better looks like:** When a test derives a path from production config,
the question is not "which temp dir wins" but "what happens if NO test file wins".
Isolation must be enforced where it can't be raced — a preload that sets the env
before any test file loads (`bunfig.toml` → `src/test-preload.ts`), not per-file
discipline. And verify it the only way that counts: md5 the real file, run the
full suite, compare. Which is what finally proved both the bug and the fix.

### 2026-08-11 — Hardened against a root cause I had not disconfirmed

**What happened:** When titles vanished the first time, I could not reproduce it,
so I reasoned from mechanism: truncating write + a reader that degrades a parse
error to `{}` = silent total loss. Plausible, real, and I implemented atomic
rename + abort-on-unreadable to close it. It was not the cause. The cause was the
test suite deleting the file, which I only found when the loss recurred at a
moment that had nothing to do with writing.

**Why this was wrong:** Memory [[disconfirm-before-declaring-root-cause]] says to
name the check that would prove the theory innocent and run it. The check here was
trivial and I skipped it: `md5` the file, run the suite, compare — 30 seconds,
and it would have pointed straight at the real culprit. Instead I let "I found a
mechanism that produces this exact symptom" stand in for "I found the mechanism
that produced it". The hardening is worth keeping on its own merits, but it was
shipped as a fix for something it didn't fix.

**What better looks like:** Before writing defensive code for an unreproduced
failure, spend one cheap experiment trying to reproduce it directly. "I can't
reproduce it" is a reason to keep looking for a *cheaper observation*, not a
licence to fix the most plausible candidate. And when a fix is speculative, say so
in the commit and the doc rather than letting it read as the diagnosis.

### 2026-08-11 — Took the default LLM backend without checking auth or contamination

**What happened:** For the retitle task's model call I reached for
`pipeToClaudeAiSdk` because it is the repo's default backend. Eugene had to tell
me the call should run on the `.claude` subscription and to look at how gbrain
invokes Claude. gbrain's `claude-cli` provider spawns `claude --print` directly,
scrubs `ANTHROPIC_API_KEY`/`AUTH_TOKEN`/`BASE_URL` from the child env, and
isolates the run (`--tools ""`, `--strict-mcp-config`, `--disable-slash-commands`,
a clean tmpdir cwd).

**Why this was wrong:** Two blind spots. (1) Auth: I never asked what the backend
authenticates with. It happened to be fine — it drives the same binary and there
is no API key on this box — but "happened to be fine" is not the same as knowing,
and a future `ANTHROPIC_API_KEY` in `.env` would have silently flipped a recurring
background job to per-token billing with nothing in the output saying so. (2)
Contamination: I saw `[WARN] MCP servers not connected` in my own first run and
read past it. That warning was the backend booting the user's MCP servers and
loading project settings for a call that summarises four lines of text — 25-56s
per batch versus ~6-8s once isolated. The evidence was on screen and I didn't
follow it.

**What better looks like:** For any recurring/background LLM call, decide the auth
path deliberately and make it unconditional in code (scrub the env rather than
trusting it), and check what the harness loads before each call — a background job
should look like a raw model call, not a full agent boot. Warnings in my own tool
output are evidence about my design, not noise to scroll past. When a sibling
system on the same box already solved this (gbrain), read its provider first
instead of defaulting to whatever the local repo happens to import.
