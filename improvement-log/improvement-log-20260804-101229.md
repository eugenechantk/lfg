## Log

### 2026-08-04 — Guessed FlowDeck tap flags

**What happened:** Needed a coordinate tap and wrote `flowdeck ui simulator tap --x 201 --y 305`. It failed silently-ish (printed the usage hint), and I chained a `type` after it, so the typed text went nowhere. Correct syntax is `-p 201,305`.
**Why this was wrong:** The flowdeck skill's rule 7 says explicitly: don't invent syntax, run `--help`/`--examples`. I skipped it for a "simple" flag.
**What better looks like:** Any flag I haven't used this session → `flowdeck <cmd> --examples` first. And never chain an action after a command whose success I haven't confirmed.

### 2026-08-04 — Per-session simulator wipes lfg app state

**What happened:** The isolation hook created a brand-new simulator, so the app booted into `ConnectView` and I had to drive onboarding (tap field → type URL → Save & continue) before I could see the screen under test. Finding the URL meant reading `.env` for `LFG_PORT`.
**Why this matters:** Every iOS session in this repo pays this tax. The recipe is stable: `http://localhost:8766` in the onboarding field, then "Allow" the notification prompt.
**What better looks like:** A memory (or a line in `ios/CLAUDE.md`) recording the onboarding seed recipe so it isn't rediscovered. Driving the real onboarding UI is right per the CLAUDE.md plist trap — only the URL lookup is waste.

### 2026-08-04 — Apple docs stub; SDK interface was faster

**What happened:** WebFetch on `developer.apple.com/documentation/swiftui/defaulttoolbaritem` returned a title-only stub (JS-rendered), as the global CLAUDE.md warns. Instead of escalating to a browser tool, I grepped the iPhoneOS SDK's `SwiftUI.swiftinterface` and got exact signatures + `@available` annotations in one call.
**Why this is worth keeping:** For *API shape and availability* (not HIG prose), the local `.swiftinterface` beats both WebFetch and a browser — it is the shipping SDK, versioned to the installed Xcode.
**What better looks like:** Add "grep the SDK swiftinterface" as the first step for Apple API-availability questions, ahead of the WebFetch → browser escalation which is for HIG/prose.

### 2026-08-04 — "The automation can't tap it" was the bug, not an automation artifact

**What happened:** The New Session send button ignored `tap --by-id`, a coordinate tap, and a raw HID touch down/up, while the model chip 200pt away at the same y responded first try. My working assumption was a FlowDeck/glass-effect artifact (the CLAUDE.md trap list even primes for that: "nav-bar toolbar buttons don't respond to synthetic taps"). Adding `.contentShape(Circle())` made it fire immediately — the Button's label had no hit shape covering its 32pt frame, only the ~10x11pt arrow glyph ink. That dead zone IS the user's "I press send and it doesn't respond".
**Why this matters:** A known-trap list can misfire as a diagnosis. The distinguishing evidence was already in hand: a *sibling* control in the same view, same y band, responded — so the input path was fine and the control was the outlier. I nearly logged it as environment noise and moved on to the navigation timing bug alone, which would have shipped half a fix.
**What better looks like:** When automation can't hit one control but hits its neighbours, treat "the control has no hit area" as the leading hypothesis, not the fallback. The a11y frame is the tell — a button reporting a glyph-sized frame (10x11 for a 32pt control) means SwiftUI never got a content shape.

### 2026-08-04 — Chained UI steps without verifying state; a whole timing run measured nothing

**What happened:** After a send landed on the session detail, I ran the next measurement pass starting with "tap the + at (350,822)" — but I was on the detail screen, not the list. The plus tap hit nothing, the id lookups failed, the typing went nowhere, and I captured 8 timed frames of the *previous* session before noticing.

**What better looks like:** Any multi-step UI sequence starts by asserting the entry state (read the tree or grep for one expected id), and `grep -c success` on each step's JSON rather than piping to /dev/null.

### 2026-08-04 — Bottom-toolbar accessibility ids are unreliable on iOS 26

**What happened:** `tap --by-id newSessionBar` worked, then intermittently returned "Element not found", with the tree showing a single opaque `Group 'Toolbar'` instead of the button. Point taps at the same location always worked.
**Why this matters:** The bottom bar is a system-hosted toolbar (separate from the app's view tree), so the in-process accessibility query sometimes only sees the container. Any automation contract that depends on `newSessionBar` will be flaky.
**What better looks like:** For system bar items (bottom toolbar, nav bar), drive by point from the last known frame and keep the id only as a locator, not a tap target — same family as the existing "nav-bar toolbar buttons aren't in the tree" trap in `ios/CLAUDE.md`.

### 2026-08-05 — Saw a 99% CPU spin and could not attribute it

**What happened:** While verifying the optimistic follow-up bubbles, the app froze — UI unresponsive to taps and swipes while the simulator clock kept ticking — and `ps` showed the process pegged at ~99% CPU for most of its 4-minute life. A fresh launch on the same build, opening the same session, sat at 2–9%. I could not reproduce it.
**What I did:** Rather than claim a fix or ignore it, I looked for what my change made more expensive and found a real one: `containsMatchingUserTurn` scanned the ENTIRE transcript (two intermediate arrays, every user turn lowercased/re-joined) on every render per pending message. Before, that ran only for short-lived idle sends; my change makes a queued message sit unmatched for the whole running turn, i.e. exactly while the transcript is streaming re-renders. Bounded it to the last 30 user turns, lazily, with a test.
**Why this matters:** The honest state is "mitigated a plausible amplifier, root cause unconfirmed" — not "fixed". Writing it down means the next session that sees a spin here starts from this note instead of from zero.
**What better looks like:** For an unreproducible perf event, capture *while it is happening* — the `ios_performance_verifier` agent exists precisely for this (headless Instruments trace: hangs + time profiler). I had a live 99% process in front of me and killed it by relaunching instead of sampling it first. `sample <pid>` takes 10 seconds and would have named the spinning stack.
