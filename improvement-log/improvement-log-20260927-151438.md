### 2026-09-27 — Nearly shipped a fix that would have forked a live session

**What happened:** The error showed a missing `/opt/homebrew/bin/codex`; I fixed the path resolution and was about to install. Only while confirming codex could resume the rollout did I see a fresh `.lease.json` and a `.sync-conflict` copy, and find the session was LIVE on the Air. The "closed" row was a phantom (Syncthing-lagged lease + Air dropped from the refresh by a 4s timeout). With only the path fix, the click would have started a second codex on a live thread.
**Why this matters:** The literal error pointed at the proximate cause, not the real one. "Why is this row resumable at all?" was the question that mattered, and the project CLAUDE.md already warns that `closed` only means "closed on this host".
**What better looks like:** For any "can't open/resume session X" report, first ask every host whether X is live (`/api/sessions` on each, plus the lease file beside the transcript) before fixing the resume command. Consider adding the desktop's open-time guard to the CLAUDE.md "closed" hazard bullet.

### 2026-09-27 — Desktop tool resolution blind in Finder launches

**What happened:** `Opener.resolve` used `zsh -lc 'command -v X'`; in the app's real env (`ps eww <pid>` → PATH=/usr/bin:/bin:/usr/sbin:/sbin:/usr/local/bin) it found none of tmux/claude/codex/mosh. Everything had silently been running on hardcoded fallbacks.
**Why this matters:** Same class as the "service restarted over ssh loses brew PATH" hazard, on the client side. Simulating with `env -i … zsh -lc` reproduced it in one command.
**What better looks like:** When a GUI app shells out, verify with the process's actual env (`ps eww`), not your terminal. Fixed with known-dir fallbacks + `--resume-check` probe.

### 2026-09-27 — `-e PATH` looked like a fix and wasn't

### 2026-09-28 — "Live" is not "running" to the user

**What happened:** My live-elsewhere guard refused "Resume locally" for any session with a process on another host. Eugene's Sidewalk session was codex parked idle at an empty prompt for 9 hours — "not running, it's just a tmux". The guard protected against two writers but blocked the one thing the menu item is for.
**Why this was wrong:** I designed the safety rule from the system's state model (process exists) instead of the user's (is it doing work?). The existing Move flow already had the right shape: stop there, then resume here.
**What better looks like:** When adding a refusal, ask what the user is trying to do in that state and whether the system can do it safely instead of refusing. Here: idle → take over (close + sync wait + resume), busy → refuse. Refusals should be for states where no safe action exists.
