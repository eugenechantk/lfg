### 2026-08-04 — Checked for concurrent work after investigating, not before

**What happened:** Spent the first several tool calls reading `FleetActivitySnapshot.swift`, `watcher.ts`, and `tmux.ts` before running `lfg-sessions`. When I did check, sessions `c7d0c9e8` and `c5d4a5a2` were both already mid-fix on the exact two root causes (sticky `isBusy`, and making `blocked`/`closed` server-computed) — `src/tmux.ts` had been edited 40 seconds before I read it.

**Why this was wrong:** The project CLAUDE.md explicitly flags concurrent-session collision as a top hazard for this repo, and says to check `lfg-sessions` / `git status` before editing shared files. I did read `git status` (it showed the in-flight diffs), but I read it as "prior work" rather than "another agent is typing in this file right now." A file modified in the last few minutes means a live agent owns it — go read what that session is doing before forming a plan, not after. The cheap version: run `lfg-sessions` list as step one of any lfg bug report, since the fleet list also *is* the bug's ground truth here.

### 2026-08-04 — Pane-scraping was never re-examined against what Claude Code actually exposes

**What happened:** lfg has detected "is this agent busy" by regexing the tmux pane since the beginning, and the whole fleet-counter bug chain (phantom busy → ratcheting Live Activity counter) descends from it. Eugene pushed back — "there must be a better way" — and 20 minutes of investigation turned up two authoritative signals that were always there: Claude Code's hook system (`UserPromptSubmit`/`Stop`/`SessionEnd`, verified firing with `session_id` in 2.1.220) and the `system`/`turn_duration` record the TUI writes into its own transcript (13/14 agreement with the fixed pane scrape across the live fleet).

**Why this was wrong:** The fix I validated earlier was a better regex — it made the scrape correct *today* against Claude Code 2.1.220's exact chrome layout. It is still coupled to spinner words, footer text, and border drawing, all of which are cosmetic and change without notice. Nobody had asked "does the thing we're scraping publish this state directly?" The answer was yes, twice over, and one of them (hooks) is documented, versioned, and push-based.

**What better looks like:** When a detector works by pattern-matching another program's *output*, treat that as a smell and spend one round asking what that program exports deliberately — hooks, structured logs, state files, an API. Scraping is the fallback, not the default. Concretely for this repo: the busy/prompt signal should come from hooks with the transcript's turn markers as the durable reconciler, and pane scraping should survive only for agents that expose neither (codex).

### 2026-08-04 — codex and Claude Code share a hook contract; lfg was scraping both

**What happened:** Followed the Claude Code finding by checking whether codex exposes equivalents. It does, and more: codex 0.145.0's native binary carries the same hook event names (`UserPromptSubmit`, `Stop`, `SessionStart`, `SessionEnd`, `PreToolUse`, `PostToolUse`, `PermissionRequest`, `SubagentStart`/`Stop`, `Pre`/`PostCompact`) with the same payload field names (`session_id`, `transcript_path`, `hook_event_name`, `permission_mode`), plus `turn_id`. Verified firing order end-to-end. Its rollout JSONL also carries explicit `task_started`/`task_complete`/**`turn_aborted`** events — an abort marker Claude Code's transcript lacks entirely.

**Why this matters:** lfg currently runs two independent pane scrapers reasoning about two TUIs' cosmetics, when both agents publish the same structured state under the same field names. The `turn_aborted` discovery is the sharper point: the single failure mode I identified in the Claude transcript approach (a terminal interrupt strands a turn "open" forever — one live session had been stuck 25 days) simply does not exist on the codex side, because codex records the abort.

**What better looks like:** One hook script, one state directory, both agents — the payloads are field-compatible. Per-agent logic shrinks to the reconciler: `system/turn_duration` + a staleness bound for Claude, `task_started`/`task_complete`/`turn_aborted` for codex. Two operational gotchas to carry: codex pins a `trusted_hash` per hook entry in `config.toml` so hook files cannot be dropped in silently, and codex's `notify` slot is already claimed on this machine by the Computer Use app — use hooks (a list) rather than notify (single-valued).

### 2026-08-04 — Steered messages don't fire UserPromptSubmit, and that's the right semantics

**What happened:** Measured hook emission points directly instead of trusting the docs' one-line summaries. Ran a tool-loop turn (`Stop` fires once, after the whole loop — not per assistant message) and then an interactive tmux session where a second message was sent while the first turn was verifiably busy. The queued message produced `queue-operation enqueue` → `remove` → a `user` record injected **into the running turn**, and exactly one `Stop` at the end. No second `UserPromptSubmit`.

**Why this matters:** lfg's entire send path is queued, so my first instinct was that this is a hole — hooks would miss turn starts for the primary code path. It's the opposite: the busy window is exactly `[UserPromptSubmit, Stop]`, steers extend the turn without toggling state, and the pairing stays 1:1. Sending to an idle session opens a new turn (hook fires); sending to a busy one steers (no hook, but the session is already marked busy). Both cases land on correct state with no counting logic.

**What better looks like:** Two lessons. First, "when exactly does this fire" is measurable in about five minutes and the answer changed my design conclusion — measure emission points before building on an event. Second, the first attempt at this test silently failed (the opening message was swallowed because Claude was still starting up — the exact trap the repo CLAUDE.md documents for `sendq`), and I only caught it because the hook log showed one submit instead of two. Assert the precondition (`grep -c 'esc to interrupt'`) before the step that depends on it, rather than inferring failure from the results afterward.
