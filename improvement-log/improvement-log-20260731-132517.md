## Log

### 2026-07-31 — Stale model name in the codex-delegate skill example killed the first delegation

**What happened:** I launched the implementation delegation with
`--model gpt-5.5 --effort high`, copied from the `codex-delegate` skill's Step 2 example
line ("Model/effort: `--model gpt-5.5 --effort high`"). The background job failed after
2 seconds with `no rollout found for thread id …`. `~/.codex/config.toml` shows the
account's actual default is `gpt-5.6-sol` with an `http_headers` version pin of
`0.146.0` (codex-cli 0.145.0 installed). Relaunching with no `--model` flag was the fix.

**Why this was wrong:** The same skill says two paragraphs later, in the operating rules,
"Leave the model unset unless the user explicitly asks for one." I followed the example
snippet over the rule. Cost ~1 minute plus a wasted job, but the failure mode is nasty —
a 2-second "failed" with an opaque `no rollout found` message gives no hint that the
model name is the problem.

**What better looks like:** (1) Never pass `--model` to `/codex:rescue` unless Eugene
names one — the config default is already the right model and it moves faster than any
skill doc. (2) The `codex-delegate` skill's example line should drop the hardcoded
`gpt-5.5` (it pins a model name in a doc that can't track the CLI), and its "Operational
gotchas" should list `no rollout found for thread id` as the signature of an
unavailable/invalid model — sitting next to the existing `codex-shim-shadows-global` and
`codex-version-header-pin` memories. Worth fixing during the next `/self-improve`.

### 2026-07-31 — codex-plugin-cc background jobs fail instantly on this host

**What happened:** Two `/codex:rescue --background` launches both failed after exactly 2
seconds with `no rollout found for thread id <uuid>` and an otherwise empty job log. A
direct control probe (`codex exec --skip-git-repo-check "reply with exactly: OK"`)
succeeded in the same repo with the same account, model (`gpt-5.6-sol`), and sandbox —
so the CLI, auth, and model access are all healthy. The break is in the plugin's
app-server/daemon path, which creates a thread and then can't find its rollout file.
Installed: codex-cli 0.145.0, plugin `openai-codex/codex` 1.0.6, config
`http_headers = { version = "0.146.0" }`.

**Why this matters:** `codex-delegate` routes ALL substantial implementation through
`/codex:rescue` and explicitly forbids hand-rolling `codex exec`. With the plugin down,
that policy has no working mechanism — every delegation this session would have silently
failed in 2s. The failure is also easy to misread as "Codex refused the task" because
`/codex:status` just says `failed` with a 2s duration.

**What better looks like:** (1) Treat a sub-5-second `failed` job with `no rollout found`
as a plugin/daemon fault, not a task fault — probe `codex exec` once to isolate CLI vs
plugin before re-briefing. (2) `codex-delegate` should name `codex exec --skip-git-repo-check
… </dev/null` (backgrounded through the Bash tool, output tee'd to a log) as the sanctioned
fallback when the plugin is down, so the brain/hands split survives a broken plugin instead
of collapsing back to Claude implementing inline. (3) Worth a memory entry alongside
[[codex-shim-shadows-global]] and [[codex-version-header-pin]] — this is the third distinct
way Codex delegation breaks on this machine.


### 2026-07-31 — I over-packed the Dynamic Island's expanded leading region in the spec

**What happened:** My feature doc specced the expanded island's leading region as
"state-A label + title, one line, `.minimumScaleFactor(0.6)`". Codex implemented exactly
that. On screen it rendered as `_ need you  redesign…` — both strings scaled to 60% and
clipped on both sides, unreadable. I had to cut it back to the summary label alone. The
same pass also found the expanded rows clipping against the island's rounded corners,
which no amount of code review would have caught.

**Why this was wrong:** I wrote the spec for that region by analogy to the lock-screen
card, which has ~4x the width. `minimumScaleFactor` was doing the work of admitting I'd
asked for too much — a scale factor in a spec is a smell that the content doesn't fit.
The titles were already in the rows directly below, so the leading region was carrying
duplicate information at an illegible size.

**What better looks like:** For constrained render regions (Dynamic Island leading /
trailing, watch complications, widget accessory families), spec the **minimum** legible
content — one short string — and add only if the live capture shows room. Treat a
`minimumScaleFactor` below ~0.8 in a spec as a design error to resolve before
delegating, not a runtime fallback. Also: always budget for edge padding in
edge-to-edge system containers; the island clips its corners over content.
