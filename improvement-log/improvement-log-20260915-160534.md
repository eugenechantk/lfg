### 2026-09-16 — AX drilling instead of the existing CLI probe

**What happened:** Tried three System Events scripts to enumerate SwiftUI row buttons (unnamed, `.plain` style); the last one ran past 90s in the background before I gave up.
**Why this was wrong:** The project already ships `--attach-command` to print the exact command a row hands iTerm, precisely so the transport can be exercised "without driving the GUI". I should have extended that probe first (which is what worked: a `held` flag) and used AX only if the click itself was in doubt.
**What better looks like:** Before driving a GUI, grep the source for existing headless probes (`--*-probe`, `--*-test`, `--attach-command`) and prefer extending one.

### 2026-09-16 — flowdeck guard blocks `open <app>.app`

**What happened:** The relaunch step of a compound command was blocked by `flowdeck-guard.sh` (`open <app>.app` → "use flowdeck run"), even though this is a swiftc-built app with no Xcode project, so `flowdeck run` doesn't apply.
**What better looks like:** For `desktop/lfg.app`, launch with `(nohup /Applications/lfg.app/Contents/MacOS/lfg >/dev/null 2>&1 &)`. Worth a guard exemption for this path.

### 2026-09-16 — Late to the decisive bypass test

**What happened:** After the Air's restart proved the Surfshark bypass works there, I spent ~40 min on the Pro trying resolver flags, edge-IP pins, a cgo resolver, a binary swap, and a DoH proxy before copying `dig` into the bundle — which showed in one command that the bypassed path carries no packets at all.
**Why this was wrong:** Every cloudflared-side knob assumed the app had a working network path. The first question for "bypass is on but the app can't resolve" is whether *anything* run from that bundle path has connectivity; that isolates VPN-side from app-side in seconds.
**What better looks like:** When a per-app VPN rule is involved, test the rule itself first (a copied `dig`/`curl` inside the bundle vs the system one), then touch the app's flags.
