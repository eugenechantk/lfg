### 2026-08-06 — `sqlite3` probe created a phantom empty DB

**What happened:** Ran `sqlite3 data/journal.db ".tables"` to inspect the journal. sqlite3
*creates* the file if missing, so a 0-byte `data/journal.db` appeared in the repo with a
fresh mtime. I then read that mtime as evidence ("the server restarted at 14:07") and built
a hypothesis on it. The real DB was `~/.lfg/journal.db` all along, as `src/journal.ts`'s
header comment says.
**Why this was wrong:** A read-only probe silently mutated the tree, and the artefact it
created then fed a false inference. Memory `probe-shape-before-scripting` covers the
adjacent lesson; this is the write-side version of it.
**What better looks like:** Before pointing a tool at a path, confirm the path from source
(`PATHS.data`), and prefer probes that cannot create (`ls`, `file`, `sqlite3 -readonly`).
If a probe does create something, delete it immediately and do not reason from it. (Removed.)

### 2026-08-06 — Theorised about the cause before checking the pump was alive

**What happened:** Worked through several increasingly elaborate explanations for a stuck
`busy: true` — turn-state cache latching, hook-state cache latching, `delegated`,
SQLite writer contention between two `serve` processes — before running the one check that
settled it: does the pump emit *anything* right now? (It doesn't; my own actively-writing
session has zero journal events, and the main thread is parked in `kevent64`.)
**Why this was wrong:** For a change-only event stream, "is the emitter alive" is the first
question, not the fifth. Each discarded theory cost a read-and-reason cycle. Memory
`disconfirm-before-declaring-root-cause` says to name the check that proves a theory
innocent — the cheap global check ("is anything being emitted?") disconfirms four theories
at once and should have come first.
**What better looks like:** When a latched/stale value is the symptom, check liveness of the
producer before investigating the value's computation. Concretely: find a session that
*must* be producing events right now and confirm it appears in the stream.

### 2026-08-06 — Nearly read a post-fix value as "still broken" when it was newly correct

**What happened:** After restarting the server, one of the two stuck codex sessions
re-stated as `busy: true` again. My first reading was "the fix didn't take". It had: the
session's long-stuck `/review` send landed during the restart window and codex was
genuinely working (`Working (1m 50s • esc to interrupt)` in the pane). The other session
re-stated correctly as `busy: false`.
**Why this matters:** I was comparing the post-fix state against my *expected* value
(`false`, the value that had been wrong) instead of against ground truth (what the agent is
actually doing right now). In a system whose whole bug class is "stale value looks like a
live one", that's precisely the mistake that produces a false "still broken" — or worse, a
false "fixed".
**What better looks like:** After a state fix, re-derive ground truth *at that moment* and
compare to that, never to the value you predicted before the change. Concretely here: read
the pane before judging the flag. Related to memory `verify-real-seam-not-mocks` — the
same principle applied to a post-fix reading rather than a test suite.
