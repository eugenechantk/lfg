### 2026-08-08 — First tiebreak for the sessionId collision was wrong for forks

**What happened:** Fixed duplicate-sessionId rows by keeping "the newest claimant". Tests against the reelly case (two processes, both with pidfiles) passed. Then the *existing* `sessions-resumable.test.ts` — which calls the real `listSessions` against the live host — printed a second collision I had not designed for: `claude --resume X --fork-session` forks whose pidfiles aren't readable yet all fall back to the identical `--resume` arg, so every fork momentarily looks like its parent. Newest-wins handed the parent's session to a fork. Had to redo the comparator to take the *claim* (authoritative vs guessed), with opposite orderings per shape.

**Why this was wrong:** I designed the tiebreak from one observed instance and wrote fixtures that encoded only that instance. The second shape was discoverable up front — `sessions.ts` has an explicit `--resume` fallback branch right next to the pidfile read, and `[[fork-transcript-materialization]]` in memory already says forks defer materialization. I read past both.

**What better looks like:** When adding a rule that arbitrates between rows, enumerate every code path that can *produce* the field being arbitrated (here: pidfile, `--resume` regex, newest-unclaimed-in-cwd) and write a fixture per path before picking the ordering. Also: a pure function that will run against live host data should be exercised against live host data early — the warning that exposed this cost nothing and appeared the first time the real `listSessions` ran.

### 2026-08-08 — Disconfirmation `perl` hit the wrong guard

**What happened:** To prove the new tests weren't passing vacuously, I neutralised both dedupe guards with two `perl -0pi` substitutions and re-ran. Result: 5 fail / 45 pass — but the two *push-storm* tests were in the passing set. The first `perl` (no `/g`) had matched the earliest occurrence in the file, which was the Live Activity reducer's guard, not `runPushTick`'s; the second pattern then found nothing. I nearly read "5 tests fail" as "the disconfirmation succeeded".

**Why this was wrong:** I checked the test *outcome* without checking that the mutation I intended had actually been applied. A disconfirmation that silently no-ops is worse than none — it manufactures confidence. This is [[disconfirm-before-declaring-root-cause]] applied one level down: the check that would prove my *check* innocent (grep the file for the guard) was one command away.

**What better looks like:** After any scripted source mutation, assert the mutation landed (`grep -c` for the removed token) before running the thing that depends on it. Prefer `git stash`/explicit edit over regex surgery when the pattern appears more than once, and always pass `/g` or anchor the match.

### 2026-08-08 — Re-hit the FlowDeck sim guard despite having a memory for it

**What happened:** Wrote the UI-automation commands with a shell variable for the UDID (`S=...; flowdeck ui ... -S $S`). The guard does literal string matching on the command text and blocked it, reporting that the command targeted `'$S'`. Lost two round-trips before switching to the literal UDID — which is exactly what memory [[flowdeck-sim-guard-cwd]] already says ("use the literal UDID the guard returns"). Also burned two more round-trips on flag placement (`-S` must follow the full subcommand path, and `screen`/`tap` use `--point x,y`, not `--x/--y`).

**Why this was wrong:** The memory is already exactly precise — line 17 reads "Use a literal UDID, never a shell variable like `-S \"$UDID\"` — the guard parses the raw command text and sees `$UDID` unexpanded, then blocks", and line 22 already covers `type` taking its text positionally. It was recalled into context at session start and I wrote the variable form anyway. So there is nothing to sharpen in the memory; the failure was purely non-application. A memory that gets recalled and then not applied is worth as much as no memory.

**What better looks like:** Treat the guard's returned command as a template to copy verbatim, variables never substituted — when a guard pattern-matches command text, the first invocation should be a literal copy-paste of what it printed. Before the first call into a guarded tool, re-read the recalled memory for that tool as a checklist rather than as background. The only genuinely NEW detail (now added to the memory) is flag placement: `-S` goes after the full subcommand path, and coordinates are `--point x,y`, not `--x/--y`.
