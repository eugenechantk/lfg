### 2026-07-31 — Routed "ask claude design to recreate them" to Codex instead of Claude Design

**What happened:** Eugene asked me to screenshot the iOS client states "and then ask claude design to recreate them as a baseline." I captured the screenshots correctly, then wrote a spec + delegation brief and launched a background Codex run to hand-write 29 HTML replica files. Eugene interrupted: "wait you can just work on my chrome and use claude design on my chrome" and "instruct claude design with the screenshots you captured." I cancelled the Codex job and redid it through claude.ai/design in Chrome.

**Why this was wrong:** "Claude Design" is a specific product (claude.ai/design) that Eugene named explicitly and uses regularly — it was in the browser, logged in, with three existing projects. I pattern-matched the phrase onto tooling I already had loaded (the `DesignSync` MCP tool for design-system projects, plus the `codex-delegate` routing policy that says "all substantial coding goes to Codex") and reconstructed the task as "produce HTML that could be pushed to a design system." That reinterpreted the request rather than executing it. The routing policy is about *who writes code Claude would otherwise write* — it does not apply when the user has named a product that does the work itself. Cost: one wasted spec, one wasted brief, one cancelled high-effort Codex run.

**What better looks like:** When the user names a product or surface by name ("claude design", "figma", "linear"), treat that as the literal execution target and check whether it's directly drivable (browser tab, MCP tool, CLI) BEFORE reaching for a general-purpose substitute. Delegation policies answer "who implements" — they never override "what the user asked me to use." A one-line check ("is claude.ai/design open/available?") would have caught this before any spec was written.

### 2026-07-31 — `flowdeck ui simulator scroll` silently no-ops

**What happened:** Spent ~5 round-trips trying to scroll the session list. `flowdeck ui simulator scroll -d DOWN` worked once, but `-d UP` never moved the view — repeated calls returned `success: true` while `latest.jpg` stayed identical. Switched to `swipe --from x,y --to x,y --duration 0.15` and it worked immediately and predictably in both directions.

**Why this was inefficient:** I trusted `success: true` as evidence the gesture landed, and re-issued the same failing command with different `--distance` values instead of switching primitives after the second identical screenshot. An earlier failed `swipe --start/--end` (wrong flag names — it's `--from`/`--to`) also returned success-shaped output, which pushed me toward `scroll` in the first place.

**What better looks like:** For FlowDeck UI automation, `success: true` means "the command was accepted," not "the UI changed." Verify by screenshot diff after the first attempt; if two identical screenshots follow the same command, switch primitive rather than tune parameters. Also: run `--help` for the gesture flags before the first call, not after the first failure. Related known trap already in project CLAUDE.md: nav-bar toolbar buttons and segmented-control segments don't respond to `tap "<label>"` — coordinate taps (`tap --point x,y`) work.

### 2026-07-31 — Claude Design caps attachments at 10 per message

**What happened:** Uploaded 10 screenshots, then a second batch of 9 to the same file input. A toast said "Keeping the first 10 files." It was not clear from the UI which 10 survived, so I reloaded the page and re-uploaded a single deliberate batch of 10.

**Why this matters:** Silent truncation on a bulk upload is exactly the failure mode that produces a confidently-wrong result — the model would have recreated whichever 10 happened to survive, and I'd have reported "all 19 states sent."

**What better looks like:** When a surface has an unknown attachment limit, upload one batch, read the confirmation, and only then decide how to split. On truncation, reset to a known state (reload) rather than trying to reverse-engineer what survived. For Claude Design specifically: 10 attachments per message — plan multi-batch handoffs as an explicit first message + follow-up, and tell the model in message 1 that more are coming.
