## Log

### 2026-09-20 — Bare `flowdeck build` failed on the Air: synced config names a Pro-only simulator

**What happened:** `flowdeck config get` returned a valid-looking config (sim `ios-fde82f4d`, 11845F95-…), so I ran a bare `flowdeck build`. It failed with "Unable to find a device matching the provided destination" — that UDID exists only on the Pro; `ios/.flowdeck` config syncs between hosts but simulators do not. FlowDeck's hint ("arm64 simulator architecture issue") pointed the wrong way.
**Why this was wrong:** The flowdeck skill says "config exists → bare commands". That rule assumes the config was written on this machine. Cost one ~full build cycle.
**What better looks like:** On the Air, check `hostname` and pass `-S "iPhone 17 Pro"` explicitly (flag override, config untouched). Worth a memory/CLAUDE.md line: FlowDeck config is host-specific but synced.

### 2026-09-20 — Evidence harness keyed ForEach on a non-unique value

**What happened:** The ImageRenderer sheet for the minimal island view used `id: \.1.description` over cases containing the count 3 twice, so SwiftUI reused the first (green) view for the needs-input case. The first PNG showed a green dot where amber was expected.
**Why this was wrong:** A harness bug that mimics the exact failure under test (wrong state colour). Caught only because I compared the image against the inputs.
**What better looks like:** Index-keyed ForEach in throwaway render sheets; always check each rendered case against its input before reading the image as evidence.

### 2026-09-21 — Keyboard-sensitive repro attempted on a host that cannot show a keyboard

**What happened:** For "composer not cleared after a queued send" I built a queued-send fixture and drove it on the Air. It did not reproduce — and only afterwards did I find the Air has no Simulator.app (`flowdeck simulator open` fails), so the software keyboard, the main suspect, was never in play. The Pro was offline.
**Why this was wrong:** Memory `sim-keyboard-needs-simulator-app` already says text-input bugs reproduce 0% headless. I should have checked `flowdeck simulator open` before investing in the harness, and known up front what the run could and could not prove.
**What better looks like:** For any text-input bug, first confirm the host can show the software keyboard. On the Air it cannot until Xcode's first-launch components are installed (`sudo xcodebuild -runFirstLaunch`); worth adding to the Air memory.
