## Log

### 2026-10-28 — iphone-control's WDA run holds the build-guard lock forever

**What happened:** My `flowdeck run` sat on "Build guard: waiting for the active build/test job." `build_guard.py status` showed the holder: a `flowdeck test --skip-build` of WebDriverAgent started 2h35m earlier from `~/dev/inbox` by a Codex thread. The iphone-control skill says to leave Appium/WDA alive and never kill the WDA xcodebuild, so the lock is effectively permanent.
**Why this was wrong:** The guard serializes builds for memory safety, but a long-lived WDA server is not a build. Routing it through the `flowdeck` shim makes it block every other build on the machine indefinitely, with no message saying who holds the lock.
**What better looks like:** The iphone-control skill should start WDA through the vendor binary (`~/.local/share/flowdeck/flowdeck`) or the guard should exempt `test --skip-build` WDA runs. The guard's "waiting" message should also name the holder (pid, cwd, age). I bypassed the guard for this session's builds only, with the holder idle at 120 MB.

### 2026-10-28 — `_printChanges` found in one run what sampling took several rounds to circle

**What happened:** After the first two fixes, the list body still re-ran per event. I read store code for every per-event write and ran stack-chain scripts over `sample` output, all inconclusive. A temporary `let _ = Self._printChanges()` in `SessionListView.body` and `RootView.body`, plus `flowdeck logs <shortId>`, printed `_collapsedStatusStored changed` 619 times in 25 s on the first run.
**Why this was wrong:** Stack samples show *where* time goes, not *what invalidated* a view. The SwiftUI instrument (which shows causes) is unsupported on the simulator, so `_printChanges` is the cause tool there.
**What better looks like:** For "view re-renders too often", go to `_printChanges` right after the first sample shows repeated body evaluation. Saved as memory `observable-subscript-and-appstorage-fanout`.

### 2026-10-28 — `cd` inside Bash calls moved the sim-guard cwd

**What happened:** Twice I ran `cd <subdir> && ...` (the fixture dir, `ios/LFGCore` for `swift test`), which moved the persistent shell cwd. The FlowDeck guard derives the session simulator from the cwd basename.
**Why this was wrong:** A later flowdeck call from the wrong cwd would provision a second simulator. I caught it from the cwd-change notice each time.
**What better looks like:** Use subshells `( cd x && ... )` or absolute paths for anything outside the repo root.

### 2026-10-28 — `flowdeck test` on the audit simulator replaced the running app

**What happened:** I ran the LFGTests suite on the session simulator just before spawning the visual auditor. The test run installs and launches its own host app, so the fixture-mode app I had launched was gone. The auditor found it not running and had to work out that it had not crashed.
**Why this was wrong:** It cost the auditor time and left an unexplained "app not running" note in the evidence.
**What better looks like:** Run app-target tests before the final launch, or relaunch the app after tests and before handing the simulator to an auditor.
