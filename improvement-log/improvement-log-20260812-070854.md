### 2026-08-12 — Asked for the concrete symptom before investigating

**What happened:** "Can't open closed sessions" had at least four distinct failure modes
(not in list / tap does nothing / opens empty / can't resume). I probed the server first
to rule it out, then asked Eugene with the four modes as options. He answered "shows
opening sessions indefinitely", which pointed straight at `DetailLoading` and made the
root cause a 10-minute read instead of a broad hunt.

**Why this was right:** memory `ground-truth-before-hypothesizing`. The four modes lived
in completely different layers (server paging, List selection, read routing, send
routing). Guessing would have had a 75% chance of investigating the wrong layer.

**What better looks like:** keep doing this — but pair it with cheap parallel evidence
first (I had already proven the server innocent before asking), so the question is
narrow and the user's one word is maximally informative.

### 2026-08-12 — Search shipped a tappable row the state layer couldn't resolve

**What happened:** `SessionListView.matchingSessions` renders a UNION of
`store.filteredSessions` and `store.searchResults`, but `SessionStore.session(_:)` — the
resolver `RootView` binds the detail column through — only knew about `sessions`,
`remappedIds`, `focusedSnapshot`, and `deepLinkSession`. Every search-only row was
tappable and unopenable, landing on an untimed "Opening session…" spinner. The
notification path had hit the identical problem earlier and been given a bespoke
escape hatch (`deepLinkSession`) rather than a general one.

**Why this was wrong:** the invariant "anything the list makes tappable must be
resolvable by `session(_:)`" is never asserted anywhere. `DetailLoading` is a *fallback*
for an unresolvable id, but it renders as a *load state* — so the failure is
indistinguishable from slowness and silently waits forever. A second source of rows was
added without extending the resolver, and nothing caught it.

**What better looks like:** (1) when a view renders a union of two collections as
selectable rows, the resolver must cover the same union — treat that as a checklist item
when adding any new row source; (2) `DetailLoading` should not be able to spin forever —
after a few seconds with an unresolvable id it should say so, which would have turned
this into a self-reporting bug rather than one Eugene had to notice and file; (3) the
second bespoke escape hatch (`deepLinkSession`) was the signal that the general fix was
overdue — a pattern appearing twice is the trigger to generalize.

### 2026-08-12 — flowdeck guard does literal string matching on `-S`

**What happened:** wrote `SIM="4CDA…"; flowdeck ui simulator tap -S "$SIM"` and the
guard blocked it with `targets '$SIM', '$SIM'` — it inspects the raw command text
before shell expansion, so a variable never matches the allowed UDID.

**Why it cost time:** three blocked calls before the pattern was obvious. Memory
`flowdeck-sim-guard-cwd` says "use the literal UDID the guard returns" but is about
cwd; it does not mention that shell variables also defeat it.

**What better looks like:** always paste the literal UDID into every flowdeck command,
never a variable, never a heredoc. Worth folding into the existing
`flowdeck-sim-guard-cwd` memory.

### 2026-08-12 — Called a dirty tree "in-flight work" without checking if anyone was working

**What happened:** I saw 5 modified iOS files, invoked the repo's "never archive a tree
another agent is mid-refactor in" rule, and recommended isolating my fix in a clean
worktree at HEAD. Eugene pushed back — "I feel like we don't have any session that is
running LFG right now, so they should be completed already." He was right: all 8 other
lfg sessions were `busy=False`, and every diff was finished, documented work. Worse, my
recommendation was actively the *riskier* one: `HEAD` is mid-way through a
half-committed change (`427e2b0` = "land the SessionStore half of the directory-filter
change"), so building at HEAD is the `main-can-be-broken-while-every-build-is-green`
trap, while the dirty tree is the coherent state — and I had already built and driven it
successfully.

**Why this was wrong:** "dirty" and "in-flight" are different facts and I conflated
them. The check that distinguishes them is one API call (`busy` per session) plus
reading the diffs — both cheap, both things I had the tools for, neither of which I did
before making a recommendation that would have cost an unnecessary worktree + build
cycle.

**What better looks like:** before invoking the concurrent-agent hazard, establish
(a) are those sessions actually busy right now, and (b) do the diffs read as complete?
Only then decide. And when the working tree is ahead of a knowingly half-committed HEAD,
the tree is the safer build source, not the more dangerous one — the repo rule is about
*mid-edit* trees, not merely uncommitted ones.

### 2026-08-12 — Nearly filed a false bug from a11y-tree evidence

**What happened:** After typing a pattern into the directory-filter field, the a11y tree
showed `TextField | '' | ''` and the Hidden list said "Nothing hidden". I started
writing this up as a defect in another session's feature. A screenshot showed the text
was plainly in the field — the a11y tree just doesn't expose SwiftUI TextField values.
The real cause was my first label-based `tap "Hide"` missing; a coordinate tap worked
and the pattern saved correctly.

**Why this was wrong:** I treated one tool's silence as positive evidence of absence,
against a feature another session had presumably verified. Filing that would have sent
someone chasing a bug that didn't exist. Memory `ground-truth-before-hypothesizing`
covers this and I applied it to the original bug but not to this incidental observation.

**What better looks like:** the a11y tree proves *structure*, the screenshot proves
*content* — for "did my input land", always look at the pixels. And before reporting a
defect in another session's work, reproduce it twice by different means.
