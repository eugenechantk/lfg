## Log

### 2026-08-06 — TTL stamped at scan start, not completion

**What happened:** The 5–10s answer latency traced to `listSessions`' cache stamping `at` when the
scan *started*. With a 600ms TTL and a 3.7s scan, the cache never once served a completed result —
a fresh overlapping scan launched every 600ms forever. I found this only on a second read, after
already writing a diagnosis that recommended "raise the TTL" (which alone would not have fixed it).

**Why this matters:** It inverts the fix. Raising a start-stamped TTL just moves the overlap
threshold; the actual repair is to stamp on settle and share the in-flight promise unconditionally.
I nearly shipped a recommendation that treated the symptom.

**What better looks like:** For any cache-with-TTL, ask two questions before recommending a change:
(1) is the timestamp taken at start or completion? (2) is the TTL larger than the operation it
guards? If start-stamped AND TTL < operation duration, the cache is guaranteed to be useless and
guaranteed to cause unbounded overlap. Check this by reflex, before proposing tuning.

### 2026-08-06 — Nearly validated the fix against a warm cache

**What happened:** First post-fix measurement fired 10 `curl`s back to back and got 1ms each. That
looked like a 3000x win but was meaningless — all 10 landed inside one 1.5s TTL window, so nine of
them measured nothing but a resolved promise. I caught it, then re-measured 30 samples 1s apart to
cross many cache windows (p50 2ms, p90 0.49s, max 0.53s).

**Why this was nearly wrong:** The thing I changed was the caching. Measuring it with a probe that
sits entirely inside one cache window tests the happy path only and hides the cold-scan cost, which
is the number the user actually feels.

**What better looks like:** When the change under test is a cache, the probe must deliberately
straddle cache boundaries — space samples wider than the TTL, and report a distribution
(min/p50/p90/max), never a single number or a tight burst.

### 2026-08-06 — Rogue duplicate `serve` unnoticed for 6.5 hours

**What happened:** Found a second `bun run src/cli.ts serve` (pid 66597) started 12:53 by a
`codex --yolo` process, still alive at ~13% CPU. It never held the port — pid 31132 did — so it was
pure waste, invisible because the app worked.

**Why this matters:** The project CLAUDE.md already warns "restart by PORT, not pkill pattern,
because stale processes silently keep the port". This is the mirror case: a stale process that
*doesn't* hold the port and therefore produces no symptom at all, just burns a core.

**What better looks like:** `serve` should detect it couldn't bind and exit rather than lingering.
Until then, when investigating any lfg performance issue, run `ps -eo pid,lstart,command | grep
'[c]li.ts serve'` early — more than one line is a finding regardless of the reported symptom.
