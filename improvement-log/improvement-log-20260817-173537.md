### 2026-08-18 — Root cause: Syncthing corrupts codex's SQLite DBs

**What happened:** Eugene couldn't start a codex session from his phone ("codex started but did not assign a session id" = server's 504 `Codex started but did not produce a session ID`). Reproducing the exact spawn argv showed `codex` exiting instantly: *"Codex couldn't start because its local database appears to be damaged"* — `logs_2.sqlite` disk I/O error (code 522) on the Pro, `Failed to read ptrmap` on the Air.
`~/.codex` is a Syncthing `sendreceive` folder (`mgwa7-zewio`) with **no `.stignore`**, so Syncthing was replicating the live `*.sqlite` / `-wal` / `-shm` files between the Pro and Air — 22 sync-conflict files in 24h. No codex rollout had been written on either host since Aug 16.
**Why this matters:** This is a recurring class ("again"), not a one-off, and it is invisible from lfg: the pane is killed on failure, the error is generic, and the host stays green. Every codex session on every host was dead.
**Fix applied:** moved `logs_2.sqlite{,-wal,-shm}` into `~/.codex/db-backups/broken-20260818/` on both hosts (codex rebuilt it), and wrote `~/.codex/.stignore` excluding `*.sqlite`, `*.sqlite-wal`, `*.sqlite-shm`, `*.sync-conflict-*`, `db-backups`. Verified Syncthing loaded the patterns live on both hosts via `/rest/db/ignores`, and that `POST /api/sessions/new {agent:"codex"}` now returns a real sessionId on both.
**What better looks like:** never sync a live SQLite database. Saved as memory `codex-sqlite-syncthing-corruption`.

### 2026-08-18 — The failing create leaves no server-side trace

**What happened:** `grep` over `/tmp/lfg-serve.log` for the 504 / codex spawn produced nothing — the only way to learn why the spawn failed was to hand-reconstruct `managedCodexSessionArgv` and run it in a throwaway tmux pane.
**Why this was inefficient:** serve kills the pane (`tmuxKillSession`) before returning 504, destroying the one artifact that explains the failure — codex's startup error was on that pane.
**What better looks like:** before `tmuxKillSession` in the codex create-failure branch, `capture-pane -p` the dying pane and log it (server log + the error body's detail). One line of code turns a 20-minute reconstruction into a `grep`.

### 2026-08-18 — Promptless codex create always 504s

**What happened:** My first end-to-end check after the DB fix posted `/api/sessions/new` with `agent:"codex"` and **no prompt**, got the same 504, and briefly read as "the fix didn't work".
**Why:** codex only writes its rollout `.jsonl` at the first turn (verified: pane idle at composer for 2 min → no rollout; sent one keystroke → rollout appeared, named with the *start* timestamp). No rollout → no id → the create path's 28 polls expire.
**What better looks like:** when verifying a create path, mirror what the client actually sends — iOS `createOptimistic` always carries the typed prompt. Also worth deciding whether a promptless codex create should be rejected up front with a clear message instead of a 14s poll then 504.

### 2026-08-18 — Air create returned the Pro's synced rollout id

**What happened:** The verification create on the Air returned `01a010d1-2337-7030-bb99-5f38c686c6dd` — byte-identical to the id the Pro's create had returned two minutes earlier. The Air did spawn its own codex (its own fresh rollouts exist), but `~/.codex/sessions` syncs, so the Pro's rollout was on the Air's disk inside the bind window.
**Why this matters:** `pickSingleCodexCreateFallbackCandidate` matches on cwd + spawn time against *all* local rollout candidates, and with Syncthing those include other hosts' rollouts. Two hosts can hand the client the same sessionId — exactly the duplicate-id hazard the project CLAUDE.md warns about downstream (leases, sendq, unread all key on sessionId).
**Not yet verified as a defect** — the timestamps are ambiguous enough that this needs its own repro before writing a fix.
