## Log

### 2026-08-06 — Theorized before instrumenting

**What happened:** For the create-session double-push bug I wrote out three candidate mechanisms
(List clearing its selection, `requestSelection(realId)` re-pushing, the modal pop racing the push)
and started designing fixes for all three before adding a single log line. A one-line
`NSLog` on `selection` changes settled it immediately: `selection` went `local-X → nil` **175ms**
after being set and **before** the remap, which pointed straight at the create screen's pop being
read as "the stack returned to root" — none of my first two theories.

**Why this was wrong:** Memory `ground-truth-before-hypothesizing` and
`disconfirm-before-declaring-root-cause` both say to get the literal signal first. SwiftUI
navigation races are exactly the case where reasoning from source is unreliable — the ordering that
matters is UIKit's, not the code's.

**What better looks like:** For any SwiftUI navigation/state race: add a trace on the state variable
in question as step ONE, before reading more source or writing any fix. The trace is ~2 minutes
including the rebuild; theorizing cost far more.

### 2026-08-06 — Verification loop spawned real (billable) agent sessions

**What happened:** Each repro of "submit a message in create session" starts a real Claude Code
session on the host. I ran eight (NAVTEST, NAVTEST2, NAVA–NAVF) before the fix was confirmed, then
had to close them all via `POST /api/sessions/:id/close`.

**Why this matters:** The repro is inherently side-effecting — it costs host credits and leaves
panes running. That is acceptable for a product-tier fix, but the count should be deliberate, not
incidental.

**What better looks like:** When a verification step has real cost, decide up front how many runs
the evidence needs (here: 1 to reproduce, 1 per fix iteration, 2 to confirm stability), say so, and
clean up in the same session rather than at the end. Closing them is a single scripted loop —
write it before starting, not after.
