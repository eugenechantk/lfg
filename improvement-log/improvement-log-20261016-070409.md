## Log

### 2026-10-16 — An old-build comparison nearly blamed S2 for a server bug

**What happened:** In the S2 build, a live reply never drew in the open session. I built the pre-S2 release on the same simulator and its reply drew in about 1 s, which read as an S2 regression. Instrumenting the S2 build then showed it working too. The real cause was server-side: the first S2 run launched with no saved cursor (fresh install), got a `resync`, and the server never subscribed that stream. Every later run started from a valid saved cursor.
**Why this was wrong:** The A/B changed two things at once: the build and the client's persisted state (the event cursor in UserDefaults). The "discriminating case" was not controlled.
**What better looks like:** When comparing builds for a live-data bug, reset the client to the same state for both runs (uninstall, or note the cursor), and read the connection log's launch lines (`RESYNC`, `catchingUp -> live`) before attributing anything to the build. This is the existing [[verify-the-discriminating-case]] lesson applied to client state, not just inputs.

### 2026-10-16 — The /api/events resync branch had been deaf since 649f3c7

**What happened:** After a `resync` frame the server sent only heartbeats on that connection. The client treats heartbeats as "live", so it never reconnected; busy, prompt and message events were lost until the connection dropped for another reason. Unit tests covered the replay path only.
**Why this matters:** It hit every fresh install and every phone idle for more than the 14-day retention, and it looked like a client rendering bug.
**What better looks like:** Fixed in `8aaffc7` with tests for the resync path. A stream contract test should cover each branch (replay, resync, live) end to end with a real journal. A probe for "stream connected but deaf" is cheap: open `/api/events?since=<stale>` and check that `id:` rows follow while the heartbeat head moves.

### 2026-10-16 — Shipped TestFlight before running the end-to-end check

**What happened:** Phase 5 ran the TestFlight upload first and the SC14 end-to-end send + answer afterwards. The check then found a bug (server-side, so the uploaded build did not need replacing).
**Why this was wrong:** Had the bug been in the app, the uploaded build would have shipped it to the phone.
**What better looks like:** In a ship phase, run the live end-to-end check on the exact commit before the upload. The upload can run in the background, but hold the "done" until the check passes.

### 2026-10-16 — Perf task: three lessons

**A regex rewrite of a test file mangled nested parens twice.** I used `re.sub` to turn `#expect(p.mutating(...))` into `let r = …; #expect(r)` and broke every line with nested calls, then fixed it with a second regex that missed one more. Writing the test file correctly the first time (bind the mutating call to a local; Swift Testing's `#expect` cannot take a mutating call) would have been faster than two blind rewrites. For small files, rewrite with Write, not regex.
**`$UDID` in a FlowDeck command is rejected by the guard** (memory [[flowdeck-sim-guard-cwd]] already says so); I hit it again when I shortened a long command with a variable. Keep the literal.
**Server-Timing beat a profiling build.** In-process timings said the closed list was 1.3 s; the live server said 1.9–3.5 s and the header showed the lease loop at 1.2–3.6 s for 0.2 s of work: the single event loop makes serial awaits expensive. Put step timings in a response header for any slow route before profiling in-process.
