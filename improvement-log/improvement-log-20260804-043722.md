### 2026-08-04 — Mis-read a reconnect count across server runs

**What happened:** Ran `grep -c '\[events\] connect'` over the whole 13MB
`/private/tmp/lfg-serve.log`, got 47, and divided it by the *current process's* 48-minute
uptime to announce "one reconnect per minute — the smoking gun". The log is append-only
across `serve-forever` respawns and spanned **17 hours**, not 48 minutes. Correctly scoped
per run it was 36 connects over 16.3h (~2/hr) — completely normal, and the opposite of a
smoking gun. I built a probe harness on the back of the wrong number before catching it.

**Why this was wrong:** I paired a count from one time window with a duration from a
different one without checking that the log started when the process did. The file's own
`[serve-forever] starting lfg serve` markers were right there and would have caught it.

**What better looks like:** For any rate derived from a log, first establish the log's time
span — `head -1`, the first restart marker, or `stat`. Never divide a whole-file count by a
process uptime. When a number looks dramatic (1/min), that is the cue to re-derive it, not
to act on it.

### 2026-08-04 — Anchored on a stale memory before measuring

**What happened:** The `lfg-pro-host-sleep-disconnects` memory named Surfshark owning the
Pro's default route as the top cause. I opened by confirming Surfshark was still on the
default route and treated that as corroboration. It is not: Tailscale's STUN-discovered
endpoints are the real ISP address (203.145.95.116), not the Surfshark exit
(45.144.227.62) — Tailscale already bypasses the VPN. The memory's headline fix was moot.

**Why this was wrong:** The memory even carried a "don't anchor — I over-anchored on sleep
first" warning, and I repeated the pattern one theory later. Checking "is the suspected
cause still present?" is not a test; the test is "does the suspected cause actually affect
the path?" — one `curl ifconfig.me` vs `tailscale status --json` would have answered it.

**What better looks like:** Treat a memory's named cause as a hypothesis with a stated
disconfirming check (per [[disconfirm-before-declaring-root-cause]]). Run the disconfirming
check first, before the confirming one. Memories are point-in-time; a 3-week-old network
diagnosis deserves re-measurement, not re-assertion.

### 2026-08-04 — A finished fix sat uncommitted while the bug kept biting

**What happened:** The entire root cause of the user's complaint was already diagnosed and
fixed on Aug 1 in `.claude/feature/instant-reconnect.md` (C1–C5), with 165 Swift + 150 bun
tests passing. It was never committed or shipped because live timing verification was
impossible that day (load 748, 23 booted sims, 99% disk). Three days later the user is

**Why this matters:** "Blocked on verification" silently became "abandoned". There was no
marker anywhere that work was complete-but-unlanded — it was only discoverable by reading

**What better looks like:** When work is finished but blocked on an environmental
precondition, say so explicitly at the end of the session and record the unblock condition
("re-verify SC2/SC4/SC5 when load < 20 and sims are free"). A dirty working tree is not a
handoff mechanism.

### 2026-08-04 — Server log has no timestamps

**What happened:** `/private/tmp/lfg-serve.log` carries no per-line timestamps, so
correlating `[events] connect` lines with wall-clock events was impossible directly. I had
to build a `tail -0f` wrapper that stamped lines as they arrived, and could only recover
historical timing from the `[serve-forever] starting` markers.

**Why this was inefficient:** The single most useful question in a connectivity
investigation — "what else was happening when the client dropped at 14:32?" — was
unanswerable from 13MB of history. It also enabled the mis-count above.

**What better looks like:** Prefix serve log lines with an ISO timestamp (and rotate the
file — it is 13MB, dominated by one repeated `[sessions] no confident session for cwd
.../reelly` line). Cheap change, large payoff for every future connectivity session.
