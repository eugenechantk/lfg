### 2026-09-21 — Stale worktrees accumulate with uncommitted work in them

**What happened:** A worktree audit found 11 extra worktrees; 4 were "merged to main" by branch yet held 6–76 files of work that was never committed anywhere (session-list from 08-01, browser-preview-history 08-06, offline-host-swipe-continue 09-04, agent-portal-login 09-06). "Merged" described the branch tip, not the tree. Asked to remove merged worktrees, I snapshotted each to a `wip:` commit on its branch (a new `wip/session-list-20260801` for the detached one) before `git worktree remove --force`.
**Why this matters:** `git worktree remove --force` on these would have been unrecoverable, and "is the branch merged" is the wrong question for whether a worktree is safe to delete. Also, 7 worktrees showed the same 29 phantom ` D .codex/evidence/*` entries — a sync artefact that makes every worktree look dirty and hides real dirt.
**What better looks like:** Sessions that finish work in a worktree commit (or explicitly discard) before ending. A periodic sweep (`scripts/worktree-audit`: per worktree — merged?, non-artefact dirty count, last-touched, live cwd) would surface these weekly instead of after two months. Find out why `.codex/evidence` is missing from worktree checkouts (likely `.stignore`) so status is trustworthy.

### 2026-09-21 — Stale gem path in the secondary-host deploy recipe

**What happened:** The memory's tmux deploy recipe hardcodes `/opt/homebrew/lib/ruby/gems/3.4.0/bin`. The Air's Homebrew Ruby is 4.0.5, so that dir does not exist; only `gems/4.0.0/bin` does. It did not break anything (`/opt/homebrew/opt/ruby/bin/bundle` also exists and comes first), but a recipe with a dead path is one Homebrew upgrade from failing.
**Why this matters:** Recipes copied verbatim from memory are trusted; a versioned path rots silently.
**What better looks like:** Recipes should derive the path (`$(ls -d /opt/homebrew/lib/ruby/gems/*/bin | tail -1)`) or omit it when `opt/ruby/bin` already covers `bundle`. Memory note updated.

### 2026-09-21 — Hunk-level staging without `git add -p`

**What happened:** `ios/LFG/SessionStore.swift` held my two hunks plus another session's fixture hunk, and the brief wanted my change committed on its own. Interactive `git add -p` is unavailable, so I dumped `git diff` to the scratchpad, kept the header + first two hunks with `head`, and `git apply --cached` it, then checked the staged diff did not contain the other hunk's marker string.
**Why this matters:** This comes up in nearly every commit-grouping task in this repo (the dirty tree is other sessions' work). Doing it by line-count is fragile.
**What better looks like:** A tiny script (`scripts/stage-hunks <file> <hunk-indexes>`) or a `session-cleanup` skill step that splits a diff by `@@` and stages the chosen hunks, with the same "grep the staged diff for a marker" assertion.
