### 2026-10-20 — Shipped a preview without multi-width checks

**What happened:** Delivered `preview/index.html` after eyeballing it at one desktop width. Independent QA then found four defects in a row: an inline two-column grid that never stacked (480px scrollWidth at a 390px viewport), a bare `section` selector whose padding leaked into `<section class="sheet">` inside the mocks, an iPad mock that clipped its second card, and a `.cols.mac` class that collided with the `.mac` mock-window class so the grid container inherited the window styling.
**Why this was wrong:** The brief explicitly asked for "narrow phone review". I had the browser open and checked only the width it happened to be. Three of the four were findable in about 60 seconds by resizing and by grepping my own class names for collisions.
**What better looks like:** Before calling any responsive page done: (1) measure `documentElement.scrollWidth` vs `innerWidth` at 1440 / 768 / 390 / 375; (2) grep every new layout class name against classes already in the file; (3) scope broad element selectors (`section`, `header`, `nav`) to the page shell when the page embeds mock markup that reuses those tags.

### 2026-10-21 — `{{token}}` cannot inject HTML in a canvas board

**What happened:** Wrote three boards that built HTML strings in `renderVals()` (a spinner glyph, a status line, a row dot) and interpolated them with `{{markHtml}}`. The runtime escapes to text, so the boards would have shown raw markup. Caught by a structural validator before publishing, but it cost a rewrite of three boards.
**Why this was wrong:** The format reference says `{{hole}}` is "a dotted lookup into renderVals()" — a value, not markup. I pattern-matched from templating engines that do have a raw-HTML hole.
**What better looks like:** In a `.dc.html` board, variable *markup* is `sc-if` branches; variable *values* are tokens inside real markup (`background: {{dotColor}}`). Never build an HTML string in the script block. Validate generated boards for `{{` appearing in rendered `innerText` before publishing.

### 2026-10-21 — Buttons without an inline background render white

**What happened:** The Fit and Keyboard buttons in the manual-control chrome showed as white circles on a dark glass pill. The helmet CSS reset `font` and `color` for buttons but not `background`, so the UA's default ButtonFace applied.
**Why this was wrong:** Only visible by rendering. The structural validator passed it.
**What better looks like:** Put `button{background:transparent;border:0}` in the helmet of every board set, and always render a contact sheet of the new boards before publishing — the two bugs this caught were both invisible to source inspection.
