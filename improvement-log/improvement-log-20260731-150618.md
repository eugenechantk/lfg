## Log

### 2026-07-31 — `/design-sync` invoked for a design→code implementation task

**What happened:** Eugene asked to "use /design-sync to implement the new live activity widgets from this claude design file." No `design-sync` skill exists locally (checked `~/.claude/skills`, plugins, project `.claude/skills`). The `DesignSync` *tool* does exist, but it syncs a **local component library up to** a claude.ai/design project — the opposite of implementing a design into native code.

**Why this matters:** The two names are easy to confuse. Blindly running DesignSync would have pushed files to the remote design project instead of writing Swift.

**What better looks like:** For "implement X from a claude.ai/design link" → `implement-claude-design` (pull + build + verify). For "push my local component library into a design system project" → the `DesignSync` tool. Note the direction before picking.

### 2026-07-31 — `implement-claude-design` Step 1 is slower than the available API

**What happened:** The skill's Step 1 prescribes opening the project in Claude-in-Chrome, opening the Design Files tab, and right-clicking each folder/file → Download, then reassembling with `collect_assets.py`. It notes a Connect-RPC alternative but says "prefer the UI procedure until the API path is validated." I skipped all of it: `DesignSync{method:"list_files"}` + `get_file` returned the full file list and contents directly, no browser, no downloads directory, no zip reassembly. Total time ~30s vs. an estimated several minutes of clicking.

**Why this matters:** The skill's #1 documented trap (downloads landing in a non-obvious browser directory) simply doesn't exist on the DesignSync path. The browser is still needed for *rendering* ground truth (Step 2), but not for acquisition.

**What better looks like:** Update `implement-claude-design` Step 1 to try `DesignSync.list_files` / `get_file` FIRST, and fall back to the browser-download procedure only when the project isn't reachable that way (e.g. not owned by the user). Keep the browser for Step 2 rendering.

### 2026-07-31 — `DesignSync.get_file` truncates silently at 256 KiB

**What happened:** `get_file` on `LFG iOS Baseline.dc.html` returned content that wrote to disk as exactly 262144 bytes. The tool description does say "Capped at 256 KiB," but the response's `truncated` field wasn't visible in the persisted output, and nothing in the content itself signals the cut — the file just ends mid-`<script>`. I only noticed because the byte count was suspiciously round. The rendered page then showed a JS syntax error banner, which would have been baffling without knowing why.

**Why this matters:** For this task it was harmless (artboard 4a was complete; only 5a's tail was lost). But if the target artboard had been near the end of the file, I'd have implemented against a half-read design and not known it.

### 2026-07-31 — Offered a design fork without checking the platform guidance first

**What happened:** Artboard 4a showed two Live Activity architectures — 27 (one aggregate card) and 28 (one widget per session). I framed them as a product fork, recommended 28, and Eugene picked it. I only checked Apple's Live Activities HIG *after* implementation, during verification. The HIG says the opposite: "Instead of creating separate Live Activities people need to jump between to track different events, prefer a single Live Activity that uses a dynamic layout and rotates through events." Empirically, iOS renders only one Live Activity per app on the Lock Screen, so screen 28's three-stacked-cards mockup isn't reproducible.

**Why this was wrong:** I had `apple-hig` available and the skill's own Step 3 says to open the HIG reference *before* implementing native behavior. I treated "which variant" as purely Eugene's taste when it had a hard platform constraint attached. The recommendation I attached ("Matches your 'widgets' plural") was reasoning from the user's phrasing instead of from the platform. A fork where one branch is platform-discouraged isn't a preference question — that fact belongs *in* the question.

**What better looks like:** Before presenting any design fork with an `AskUserQuestion`, check the platform guidance for each branch and put the constraint in the option's description. If one branch conflicts with the HIG, say so in the option text rather than discovering it at verification time. Cost here: a full high-effort Codex implementation of an architecture that may need to be reversed.

### 2026-07-31 — Spec's SwiftUI mapping column introduced a 1 pt fidelity bug

**What happened:** In `component-breakdown.md` I wrote a type-ramp table with the design's measured sizes (14 pt) in one column and a "Nearest SwiftUI" suggestion (`.subheadline`) in another. `.subheadline` is 15 pt. Codex followed the suggestion column for the directory tag, footer, pill and elapsed text, but used explicit 14 pt for the status label — so 14 pt and 15 pt text ended up side by side in the same header row.

**Why this was wrong:** I put two sources of truth in one table and the less accurate one was the actionable-looking one. "Nearest" is an invitation to approximate, in a document whose entire premise is exact measured values.

**What better looks like:** In a design spec, give exactly one authoritative value per property. Use explicit `.system(size:)` for pixel-specified designs and only name a semantic style when it *exactly* matches (`.footnote` = 13 pt did). If a semantic style is close-but-not-equal, don't mention it. The spec table now carries a warning note to this effect.

**What better looks like:** After any `get_file`, check whether the byte count is exactly 262144 — if so, treat it as truncated and pull the remainder another way (the `MintPreviewToken` origin serves the current files at clean static paths, or extract the section via the browser DOM). Verify the target artboard's closing tag exists before reading it as complete.
