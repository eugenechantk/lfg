## Log

### 2026-08-13 — Burned ~6 flowdeck calls rediscovering CLI arg order

**What happened:** Six failed invocations before landing the right FlowDeck syntax:
`flowdeck run -p LFG.xcodeproj` (rejected — must pass the `.xcodeproj` to `-w`),
`ui simulator screenshot` (the subcommand is `screen`), `--output` / `-S` placed
before the subcommand (silently prints usage), `tap --x 201 --y 306` (it's
`-p 201,306`). And `--help` is itself blocked by the sim guard unless `-S` is
passed, so the fast way to recover was also blocked.

**Why this was wrong:** All of it is discoverable in one `flowdeck help ui simulator -S <udid>`
call, which I only ran after four failures. The guard's error message even hands
back the UDID to use — I should have appended `-S` to every flowdeck command in
the session from the first one.

**What better looks like:** On the first FlowDeck UI command of a session, run
`flowdeck help ui simulator -S <udid>` once and keep the subcommand list. Always
append `-S <udid>` to *every* flowdeck call including `--help`. Project args:
`-w <path-to-.xcodeproj-or-.xcworkspace> -s <scheme>`.

### 2026-08-13 — Blind-scrolled a long transcript looking for one message

**What happened:** To verify the image branch I opened a session and swiped up
~15 times, overshooting past the target message twice, then had to search by
name and start over.

**Why this was wrong:** The server has a messages API. One `curl
/api/sessions/<id>/messages` per candidate session told me exactly which session
had the message I needed *near its tail* — I used that trick only after wasting
the scrolling. Verification targets should be chosen so the thing under test is
on the first screen.

**What better looks like:** Before driving the UI, query the API to pick the
session/screen where the case under test is closest to the default scroll
position. Drive the UI to confirm rendering, not to search for content.

### 2026-08-13 — Piped a long deploy through `tail`, lost the outcome, re-ran it

**What happened:** Ran `fastlane ios deploy_testflight 2>&1 | tail -45`. Fastlane
prints its "update available" changelog banner at the very END of every run,
success or failure — so all 45 lines were changelog and the actual result
(archive path, build number, upload confirmation) was cut off above it. I
concluded it had failed, re-ran the whole 5-minute lane, and only afterwards
found the first run's archive at 19.04.20 with build 202608131903. Two builds
uploaded where one was intended.

**Why this was wrong:** `tail -N` on a command whose interesting output is in
the middle is a coin flip, and this tool in particular pads its ending with
dozens of irrelevant lines. The fix is not a bigger N.

**What better looks like:** Redirect long-running builds/deploys to a file
(`> deploy.log 2>&1`), then grep the file for the outcome — which is what I did
on the second run, and it answered immediately. Applies to any command over ~30s
with verbose output: fastlane, xcodebuild, bundle install.

### 2026-08-13 — Repeated the blind-scroll mistake, in a live transcript

**What happened:** Having just logged "don't scroll-hunt, use the API to pick
the screen," I did it again while verifying the card change — ~10 more swipes,
overshooting three times. Worse: the session was *live and appending*, so the
scroll position shifted under me between captures and the same swipe sequence
that worked ten minutes earlier no longer landed.

**Why this was wrong:** Writing the lesson down is not the same as applying it.
And the accessibility tree from `flowdeck ui simulator screen --json` already
answered the question outright — it listed the two `.mp4` elements at 40pt tall
(cards) instead of 200pt (players). I had the evidence and kept swiping for a
screenshot anyway.

**What better looks like:** (1) Verify against a session that is NOT live, or
one where the target is within one screen of the bottom — check with the
messages API first. (2) Read the a11y tree for the *assertion* (element size,
type, count) and use the screenshot only as the human-readable artifact. Element
geometry is the real evidence; the picture is the illustration.

### 2026-08-13 — SendUserFile was invisible in the iOS client

**What happened:** Eugene's global CLAUDE.md now tells every agent to hand files
over with `SendUserFile` rather than pasting paths — but lfg's server mapped the
tool call to a generic `tool_use` line, so the client rendered a collapsed blob
of JSON and the deliverable was the one thing you couldn't open. The paths were
right there in the payload, unparsed.

**Why this mattered:** The instruction and the client had drifted apart, and
nothing failed loudly — the files just quietly never appeared. Sessions had been
sending files this way for days.

**What better looks like:** When a global instruction tells agents to use a
specific tool for a user-facing outcome, check that the surface the user
actually reads knows about that tool. Fixed server-side (`sendUserFileText` in
`src/sessions.ts`) so it works on installed clients with no app release.
