### 2026-07-31 — `/design-sync` invoked when `implement-claude-design` was meant

**What happened:** Eugene ran `/design-sync` asking to "implement the new session list from this
claude design file". `design-sync` is the *opposite* direction — it pushes a local component
library UP to claude.ai/design. The correct skill was `implement-claude-design`.
**Why this matters:** The two skills bracket the same product surface (claude.ai/design) but move
data in opposite directions. Loading the wrong one wastes a full skill-load and, worse, could have
started a multi-hour design-system import into a project that is a screen mockup, not a DS.
**What better looks like:** Recognize the direction from the request verb, not the skill name —
"implement X *from* a design link" is always `implement-claude-design`; "sync my components *to*
Claude Design" is `design-sync`. Say the correction in one line and switch, which is what happened
here. Worth a memory so the routing is instant next time.

### 2026-07-31 — `DesignSync(get_file)` silently truncated at the 256KiB cap

**What happened:** Fetched `LFG iOS Baseline.dc.html` (266.4KB) via `DesignSync(get_file)`. The tool
capped it at exactly 262144 bytes and returned it without an obvious truncation flag in the part I
read. I wrote it to disk and started reading. The cut landed mid-`renderVals()`, removing the
`dirGroups`/`hostGroups`/`collapsedGroups` mock data and the closing tags — so the file could not
render. I noticed only because the byte count was suspiciously exactly 256KiB.
**Why this was costly:** I then burned ~4 tool calls trying to recover the tail via the GetProject
API (JSON-escaped blob, no `</html>` match) and the preview origin (CORS, then 404 without the
token) before stopping and reconstructing the missing mock data by hand.
**What better looks like:** After any `get_file`, check `len(content)` against 262144 and check the
`truncated` field explicitly — the tool description states the 256KiB cap up front. When a fetched
design file *is* over the cap, skip the recovery chase entirely: extract the one section needed and
assemble a focused render file with hand-written mock data. That is what finally worked and it took
two minutes. Cap the recovery attempts at two before switching strategy.

### 2026-07-31 — Full-width section header was only tappable on its leading text

**What happened:** The collapsible group header put `Spacer(minLength: 0)` *outside* the `Button`, so
the button's hit area covered only chevron+title+count while the row's accessibility frame spanned the
full width. `flowdeck ui simulator tap --by-id` reported `"success": true` and nothing happened —
the synthetic tap landed at the element's centre, which was dead space.
**Why this was nearly missed:** The tap tool returned success. Only re-reading the screenshot showed
the group had not collapsed. A real user tapping the right half of the header would also have gotten
nothing.
**What better looks like:** Two rules. (1) In SwiftUI, if a row is meant to be tappable end-to-end,
the `Spacer` belongs *inside* the button's label, with `.contentShape(Rectangle())` — never outside.
(2) `tap` returning success proves a hit-test target existed at those coordinates, NOT that the
intended action ran. Always confirm with the post-action screenshot. This is the same class of trap as
the repo's existing "nav-bar toolbar buttons don't respond to synthetic taps" note.

### 2026-07-31 — SF Symbol name shadows `.accessibilityIdentifier` on image-only buttons

**What happened:** `Button { } label: { Image(systemName: "mic") }` with
`.accessibilityIdentifier("sessionComposerMic")` on the Button was not findable by id — FlowDeck
suggested the auto-derived label "Microphone" instead. The tree showed ids like `arrow.up`,
`paperclip`, `sparkles` — SF Symbol names being published as element ids. Moving the identifier onto
the `Image` did not fix the FlowDeck query either.
**Why this matters:** A11y identifiers are the test contract. If image-only buttons silently publish
symbol names instead, every such control is unaddressable by id and the contract is fiction.
**What better looks like:** For icon-only buttons, don't rely on `--by-id`; give the button an explicit
`.accessibilityLabel("…")` and drive it by label, or wrap the image in a container that owns the
identifier. Verify each new identifier actually resolves (`tap --by-id`) rather than assuming it does
because the modifier is present — I only caught this because I tried to use it.

### 2026-07-31 — `Section("TITLE")` around an inline `Picker` drops the menu header

**What happened:** The group/sort menu was built as `Section("GROUP BY") { Picker(...).pickerStyle(.inline) }`.
The options and checkmarks rendered correctly but both section titles were missing. Moving the title
onto the `Picker`'s own label also produced no header. Only replacing the pickers with plain `Button`s
inside a titled `Section` rendered "GROUP BY" / "SORT BY".
**Why this cost time:** Three build-and-look cycles. The first two were plausible-looking guesses at
the same API.
**What better looks like:** In a SwiftUI `Menu`, section headers render only when the section's children
are menu elements the menu owns — an inline `Picker` is opaque to that. Reach for `Section` + `Button`
with an explicit checkmark when a menu needs visible group titles. And cap "try another spelling of the
same API" at two attempts before changing approach.

### 2026-07-31 — Gave the verifier the simulator I was still driving; it stalled

**What happened:** I spawned `claude-design-verifier` against UDID E0DC8228 — the very simulator I then
kept using: four `flowdeck run` rebuild-and-relaunch cycles, a `set-appearance dark`, and my own
`ui simulator session` capture. Twenty-four minutes later the agent's output was 146 bytes and had not
been written to since its second minute. Eugene noticed before I did and asked whether simulator
clashing was the cause.
**Why this was wrong — two distinct collisions:** (1) The app under it was being reinstalled and
relaunched underneath it, and its appearance flipped mid-run, so any crop it captured was of a moving
target. (2) `flowdeck ui simulator session start` explicitly "stops any active session" — so my capture
session and its capture session were evicting each other. A verifier cannot see the screen if its
capture keeps being torn down.
**What better looks like:** A verification agent gets a **dedicated simulator, created for it**, and the
spawning session stops touching that simulator entirely for the duration. Concretely: `flowdeck simulator
create` a fresh named sim, force the software keyboard, boot it, install + launch + seed app state
(drive the real onboarding — the connect flow needed a coordinate tap since the URL TextField publishes
no label or id), dismiss the notification prompt, `session stop` my own capture, and only then spawn the
agent with that UDID plus an explicit "do not rebuild, do not change appearance, this sim is yours."
**Correction to my own reasoning here:** I justified killing that agent by claiming it had "stalled"
because its task output file sat at 146 bytes for 24 minutes. That inference was wrong — 146 bytes is
just the task header, and a subagent's transcript is only flushed at completion, so file size carries
NO progress information. The kill notification returned its real last line ("Let me build the paired
component crops"), proving it was working the whole time. The simulator contention was genuine and the
dedicated-simulator fix stands, but I destroyed ~25 minutes of live work on a fabricated signal.
**Never use task-output file size or mtime as a liveness signal for a subagent.** There is no cheap
progress read; either wait for the completion notification or accept the cost of not knowing.

### 2026-08-01 — Registered the simulator guard mid-run and broke my own verifier

**What happened:** A design-verification agent started at 00:04. I registered the FlowDeck guard hook
at 00:09, while it was running. Every one of its `flowdeck ui simulator` calls after 00:09 was blocked
— the guard keyed on its session id, which is the PARENT's, and pointed it at a bare auto-created
simulator with no app installed. Three of seven components went unverified.
**Why this was avoidable:** I had explicitly noticed the risk ("enabling the hook right now could
break the in-flight verifier") and registered it anyway without checking whether anything was mid-run.
**What better looks like:** Enabling or changing a PreToolUse guard is a change to the *execution
environment of every running agent*, not a config edit. Before registering one: check for in-flight
background agents and either wait for them to finish or accept and state the cost. The safe window is
between tasks, never during one.

job id.

### 2026-08-01 — Turned a partial observation into a load-bearing code comment

**What happened:** Having found that `#000000`, `#1C1C1E`, `0.60` and `0.30` are exactly UIKit
semantic colors, I wrote into `SessionListView.swift` that "every value the design specifies for this
screen is exactly the DARK variant of a UIKit semantic color" and mapped the whole palette that way.
An independent verifier measured it: the design also uses `0.07` white, `0.50`, `0.40` and `0.45`,
none of which has a semantic equivalent, and `Color.purple` is `(219,52,242)` while the design's
`#BF5AF0` is `(191,90,240)` — SwiftUI's bare color names are not the UIKit *system* palette.
**Why this was wrong:** I verified four values and generalized to all of them, then wrote the
generalization down as justification, which makes a wrong claim durable and persuasive to the next
reader. The rounding silently shifted four inks.
**What better looks like:** State in a comment only what was actually measured, and say which values
were checked. When a mapping is convenient-but-unverified, either measure the rest or write the
exceptions down. Concretely for SwiftUI: `Color.purple` ≠ `Color(.systemPurple)`; for design fidelity
always go through `UIColor`'s system palette, and build an explicit adaptive color when the design's
alpha has no semantic twin.

### 2026-08-01 — Four attempts on an unfindable accessibility id; a working counter-example was on screen the whole time

**What happened:** `--by-id sessionComposerMic` returned not-found. I tried: (1) the id on the Button,
(2) moved onto the Image, (3) removed `.accessibilityElement(children: .contain)` from the parent,
(4) moved the id back onto the Button. All failed. The fifth attempt worked instantly: the parent
HStack carried `.accessibilityIdentifier("sessionComposerBar")`, and **an identifier on a container
shadows its children**. Moving the container id onto a zero-size sibling element — a pattern already
present three lines below in the same function for `newSessionBar` — fixed it.
**Why this dragged:** I twice concluded "SF Symbol names shadow identifiers on image-only buttons"
and wrote that into a code comment and the improvement log as fact. It was wrong. The disproof was
sitting right there: `sessionSearchToggle` and `sessionSortMenu` are *also* image-only buttons and
*do* resolve — their difference is that their parent HStack has no identifier. I had that evidence
before attempt two and did not use it.
**What better looks like:** When something fails and a near-identical thing succeeds, diff the two
before trying another variation of the failing one. That is faster than any amount of hypothesis
generation. Concretely for SwiftUI: never put `.accessibilityIdentifier` on a container that has
children you need to address — publish container ids as zero-size sibling elements instead.
**Correction to the earlier entry in this log:** the claim "SF Symbol name shadows
`.accessibilityIdentifier` on image-only buttons" is FALSE. The cause was the parent container's
identifier.
