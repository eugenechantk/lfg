### 2026-08-01 — `cd`'d into a FlowDeck session subdir mid-verification

**What happened:** While inspecting FlowDeck's tree dumps I ran `cd .../automation/sessions/50DE51D1/trees` inside a Bash call. The Bash tool keeps cwd between calls, so the next `flowdeck ui simulator session start` resolved its session directory relative to that subdir. For several minutes the accessibility tree returned stale data (a dismissed dialog) while the screenshot showed the home screen, and I chased that as a simulator bug.
**Why this was wrong:** Memory `flowdeck-sim-guard-cwd` and `ios/CLAUDE.md` both say explicitly: don't `cd` between FlowDeck commands. I had read that rule and still broke it.
**What better looks like:** Never `cd` in a Bash call during FlowDeck work — inspect via absolute paths (heredoc python, `Read`). If a `cd` is unavoidable, prefix the next flowdeck command with `cd <project-root> &&`.

### 2026-08-01 — Measured SSE latency with the wrong curl metric

**What happened:** To test "does an idle `/api/events` stream send anything on connect", I used `curl -w "%{time_starttransfer}"`. It reported 1.5ms and I almost concluded the stream was fine. `time_starttransfer` includes the response *header*, which SSE flushes immediately — the body was actually silent for 10s. Only switching to a `read(1)` on the body exposed the real 10.004s.
**Why this matters:** The 10s silence was the ROOT CAUSE of the user's bug. A one-line measurement mistake nearly buried it.
**What better looks like:** For streaming endpoints, measure the first **body** byte (`python urllib` + `read(1)`), never a curl timing metric. Related to memory `probe-shape-before-scripting`: eyeball the actual bytes before trusting a summary number.

### 2026-08-01 — Fought a saturated host for ~40 min before running `uptime`

**What happened:** iOS install hung for 7+ minutes, screenshots took 7s each, the simulator display went black, and a scratch `lfg serve` took 20s to answer `/api/sessions`. I treated each as its own puzzle. When I finally ran `uptime`: **load average 748**, with **23 booted simulators** (parallel agent sessions) and a **99%-full disk**.
**Why this was wrong:** Every one of those symptoms is a known consequence of host saturation, and `uptime` + `df` + booted-sim count is a 5-second check. Memory `ios-disk-and-runtime-ops` already says "opaque failure → check disk first"; the same reflex should cover load.
**What better looks like:** Before ANY iOS timing/verification work, run a 3-command host sanity check (`uptime`, `df -h /System/Volumes/Data`, count of booted sims). If load > ~50 or disk > 95%, say so and either clean up or declare timing unverifiable — don't collect numbers that can't mean anything. Worth promoting to `ios/CLAUDE.md`.

### 2026-08-01 — A tick-count back-off constant rotted when the poll interval changed

**What happened:** `HostProbePolicy.coldProbeEveryNTicks = 10` was documented as "3s poll cadence → cold hosts retried every ~30s". The poll loop had since become 60s, so cold hosts were actually re-probed every **10 minutes** — nobody noticed because the constant and the interval live in different files.
**What better looks like:** Policy constants expressed in ticks must either (a) be expressed in seconds and converted at the call site, or (b) carry an explicit "coupled to X" note AND a test that fails when the coupling breaks. I added the note and re-derived the value; the seconds-based version is the real fix if this bites again.
