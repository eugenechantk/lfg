### 2026-10-04 — "Stop doesn't work" was a label lag, not a failed stop

**What happened:** Eugene reported stopping `lfg-e4d53c` repeatedly with no effect. `data/ops.log` showed every interrupt (31 since August, both of today's) as `stopped: true` in ~0.26s. The pane showed Claude idle with the prompt rewound into the composer. The real bug: Stop before the first assistant row writes no `[Request interrupted` marker, so the transcript layer reads `running` until `STALL_MS` (15 min).
**Why it matters:** The fastest path was ops.log + pane + `sessionTurnState` on the real transcript — three probes, no hypotheses. Repeated interrupts of one session within minutes in ops.log (368c5822 ×6, cbc915c7 ×3) are the fingerprint of this lag.
**What better looks like:** For any "stop/interrupt didn't work" report: (1) `grep <sid> data/ops.log` for `op: interrupt` and `stopped`, (2) capture the pane, (3) run `sessionTurnState` on the transcript. Worth a line in the project CLAUDE.md beside the `sendq.log` guidance. Note `ops.log` is `data/ops.log` in the repo, NOT `~/.lfg/ops.log` (that one is stale since Aug 6).

### 2026-10-04 — Shared-cache race my sequential tests could not see

**What happened:** `interrupt-marks.ts` advanced `checkedSize += bytes` after an `await`. The pump, push watcher and REST list call `sessionTurnState` in the same tick, so two readers both added the same bytes. The auditor reproduced it 20/20 with `Promise.all`; my 9 tests all awaited one call at a time.
**Why it was wrong:** I knew three consumers share the module — I even wrote that in the doc — but did not test concurrent access to the mutable mark.
**What better looks like:** Any module-level mutable state read by several async callers gets one `Promise.all` test. Mutations after an `await` compute from a value captured before it.
