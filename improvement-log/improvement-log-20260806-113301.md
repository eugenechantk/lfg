### 2026-08-06 — The documented "restart by port" recipe doesn't work

**What happened:** Followed the project CLAUDE.md rule "kill by PORT (`lsof -ti :8766`), not by pkill
pattern". `lsof -ti :8766` returned **four** pids (the listener plus three established client
connections), so `kill $OLD` died with `illegal pid: 14940\n27943\n...` and nothing was restarted.
The correct form is `lsof -nP -iTCP:8766 -sTCP:LISTEN -t`.
**Why this matters:** The rule exists to prevent a stale process silently holding the port, and it's
followed precisely *because* it's written down. A recipe that fails on a busy server is worse than
no recipe — on a quiet server it works, so it looks correct until the one time it matters.
**What better looks like:** Update the project CLAUDE.md line to the `-sTCP:LISTEN -t` form. Any
documented command that selects a process should select exactly one.

### 2026-08-06 — Committing into a tree three other agents were editing

**What happened:** `ios/LFG/SessionStore.swift` had ~250 lines of other sessions' in-flight work, and
my 9-line change shared a diff hunk with an unrelated `busyFromJournal` → `busyStatedAt` refactor —
so `git add -p` would have staged a non-compiling commit. Had to build the blob by hand
(`git show HEAD:file` → patch → `git hash-object -w` → `git update-index --cacheinfo`). Then a
rebase in a scratch worktree hit a conflict in someone else's commit, and the commit hashes shifted
under me twice because another agent was running `pull --rebase` concurrently.
**Why this was still the right call:** Staging the whole file would have pushed another session's
half-finished refactor. The blob-level route touched nothing of theirs.
**What better looks like:** When a shared high-traffic file is dirty, go straight to the
`git show HEAD:<file>` → patch → `hash-object`/`update-index` route instead of trying hunk staging
first. And re-read `git log` immediately before any rebase in this repo — the branch moves.

### 2026-08-06 — Guessed the `/api/sessions` payload shape twice

**What happened:** Wrote two throwaway Python parsers against `/api/sessions` assuming it was a bare
list, then a list-or-dict, and both crashed (`'NoneType' object is not subscriptable`, then
`'str' object has no attribute 'keys'`). It is `{"sessions": [...]}`. Cost two round-trips.
**Why this was wrong:** The `probe-shape-before-scripting` memory says exactly this: run the probe

`python3 -c "print(type(d), list(d)[:5])"` — look at it, *then* write the parser.
