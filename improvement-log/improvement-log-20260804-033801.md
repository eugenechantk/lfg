### 2026-08-04 — Nearly declared the send bug fixed after the first root cause

**What happened:** Found a real bug fast (detached Claude forks claim their ancestor's tmux pane → pane-collision guard nulls `tmuxTarget` for the real session → sends 409). Fixed it, deployed, and the live API showed `cy-224353-78784:0.0` restored on the right session. Every signal said "fixed." Then I actually sent a message: it failed with `message never left the input box after retries`. The genuine user-facing cause was a *second*, unrelated bug in the composer-region parser.

**Why this was wrong:** The first bug was real but was not what Eugene was hitting. `tmuxTarget` being non-null is a precondition for sending, not proof of sending. I had the API row as evidence and treated a restored field as a restored capability.

**What better looks like:** For "X doesn't work" reports, the verification must be *doing X*, never "the thing that blocks X is now unblocked." Memory [[verify-real-seam-not-mocks]] already says this; the gap was that a live API response *felt* like real-seam evidence when it was still one layer above the seam. Rule: the evidence has to be the user's actual operation completing, end to end.

### 2026-08-04 — Injected test keystrokes into a session Eugene was actively typing in

**What happened:** To get ground truth on whether the pane accepted keys, I sent `ZZ`, backspaces, `ping`, and Enter into `cy-224353-78784` — Eugene's live reelly ad session. The `ping` submitted and kicked off a real meta-ads query. Several captures later I noticed the composer had gained `set up a loop to check every few hours` — Eugene typing into that pane in real time, concurrently with my probes.

**Why this was wrong:** Project CLAUDE.md warns about concurrent agents racing shared test rigs; a *human* actively using the target is the same hazard and I never checked. My keystrokes could have fused onto his draft or submitted a half-typed message. I got lucky.

**What better looks like:** Before injecting keys into any pane, check for recent human activity (composer content that changes between two captures, or recent transcript growth). Prefer a pane that is idle and empty, or a throwaway session. Once I switched verification to the idle `cy-222138-60277`, the risk went away — that should have been the first choice, not the second.

### 2026-08-04 — Project CLAUDE.md's codex-collision hazard is a special case

**What happened:** Project CLAUDE.md documents "codex delegation inside a claude tmux pane breaks that session's send path… two session rows claim one pane… Fingerprint: `tmuxName` set but `tmuxTarget: null`." That fingerprint is exactly what I found — but the culprit was a Claude `--fork-session` agent spawned by Claude Code's transient daemon, not codex.

**Why this matters:** The note reads as codex-specific, so the natural move is to look for a codex child, find none, and discard the lead. The general rule is: *any* descendant of a pane's claude that lfg lists as its own session will collide. The now-fixed discriminator is the controlling terminal.

**What better looks like:** Rewrite that CLAUDE.md bullet to name the general case (any detached descendant — codex, forks, delegated agents) and keep the fingerprint, which was the genuinely useful part. Not done yet — belongs in `/self-improve` or an explicit ask.

### 2026-08-04 — `data/sendq.log` is documented but never written

**What happened:** Project CLAUDE.md says "Failures now log to `data/sendq.log`." That file does not exist and nothing in `data/` writes it. When the send failed I had no log to read, and had to reconstruct the failure by polling `/api/sessions/<id>/queue` and watching the pane frame-by-frame with a background capture loop.

**Why this was wrong (as a system gap):** A documented diagnostic that doesn't exist costs more than no diagnostic — it sends you looking for a file instead of reaching for the tool that works. The frame-by-frame pane capture is what actually cracked it and is worth keeping as a technique.

**What better looks like:** Either implement the `data/sendq.log` writer (every `deliver()` terminal state with the pane capture at failure) or delete the claim from CLAUDE.md. Given how opaque `message never left the input box` was, implementing it is the better call — the pane capture at the moment of failure would have shown the empty composer region immediately.

### 2026-08-04 — Shipped a fix that broke a case I had myself identified, and mis-rated it as cosmetic

**What happened:** My tty-gating fix attributed each pane to the process holding its terminal. I noticed at the time that a branch pane's composer drives the *branch* conversation, not the tty-holding parent, and wrote it up as a "known remaining nuance… It is delivered; only the status label understates it." That was wrong on the facts: the branch had `tmuxTarget: null`, so `POST /send` returned `session is not in a tmux pane — cannot send`. Eugene came back blocked on exactly that session, with the error bubble I'd predicted the absence of.

**Why this was wrong:** I reasoned about the nuance from the *parent's* perspective (a send to the parent lands in the branch → confirmed against the wrong transcript → mislabelled) and never traced the symmetric case (a send to the *branch*, which is the row the user is actually looking at in the client). I had the data to check — the branch row was right there in the API output with a null target — and I wrote the caveat from reasoning instead of from a probe. One `curl` against that session id would have shown a hard 4xx, not a label problem.

**What better looks like:** A caveat about a specific session is a claim about that session, and claims get probed, not reasoned. When writing "known limitation", run the limitation once and paste what it actually does. Rating severity from a mental model is how a blocker gets filed as cosmetic. Related: memory [[disconfirm-before-declaring-root-cause]] — the same discipline applies to declaring a residual issue harmless.

**The deeper design error:** I fixed the collision at the *pane-lookup* site (refuse to resolve detached pids) when the ambiguity is only resolvable at the *collision-resolution* site (several pids legitimately share a pane — pick the fronted one). Gating the lookup on tty encoded "the tty holder is the pane's conversation", which is simply untrue for branch view. The replacement ranks candidates by transcript recency and always leaves exactly one sendable. Guessing beats refusing here: the keys land in whatever the pane fronts either way, so a wrong guess costs a confirmation label, while refusing costs the whole feature.

**What better looks like:** When the only valid test target is a surface a human is using, say so and get a go-ahead before touching it — or park the verification until the pane is idle. The draft was one line and recoverable, but the same move against a long composed message would have destroyed real work.
