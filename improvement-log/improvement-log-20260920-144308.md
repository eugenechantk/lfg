## Log

### 2026-09-20 — Bun sliced file stream hangs short of EOF

**What happened:** The new bounded reader used `file.slice(from, from+32MB).stream()`. Over the real corpus 24 workers hung at 0% CPU with 24 transcripts open. Every hung file was larger than the cap: Bun delivered exactly the sliced bytes and then never closed the stream.
**Why this matters:** The existing readers all slice to EOF, so the bug was latent in the repo until a byte cap short of EOF appeared. It will bite any future bounded head read.
**What better looks like:** Enforce byte budgets by counting and `break`ing (breaking out of `for await` returns at once). This is now in `allUserTurns` with a comment and a regression test. Candidate for a project CLAUDE.md hazard line.

### 2026-09-20 — Hypothesis inverted, probe settled it

**What happened:** I assumed the early `break` (stream cancel) was what hung. Instead of rewriting the reader on that guess, I ran a two-arm probe (break vs full drain over 217 files at concurrency 24). Break finished in 108 ms; drain hung 10 files. A third probe printed which files: all larger than the cap.
**Why this matters:** Acting on the first hypothesis would have replaced the streaming reader with FileHandle reads and "fixed" nothing about the drain-to-slice-end case elsewhere. Twenty minutes of probes beat an hour of rewrite.
**What better looks like:** Exactly what happened, and it is the memory [[disconfirm-before-declaring-root-cause]] applied. Keep doing it.

### 2026-09-20 — Stale corpus claim in a code comment

**What happened:** `LAST_USER_TEXT_SCAN_BYTES` is documented as "32 MB clears every Claude transcript in the corpus outright". The corpus now has Claude transcripts of 35–51 MB (fiftyworkout, Noto, lfg).
**Why this matters:** The comment is what made the sliced-stream bug hard to suspect — a reader who believes the cap is never hit does not look for cap-boundary behaviour.
**What better looks like:** Comments that state a measured corpus fact should carry the date, and a `find -size +32M` is a 1 s check before trusting one.

### 2026-09-20 — Fixture conflation

**What happened:** The "does not index meta/wrapper/tool-result lines" test failed twice, each time because the pre-existing title reader or last-text reader accepted a stray text block on a tool-result row — behaviour outside the change. Bracketing the noise with genuine prompts isolated the index.
**What better looks like:** When a test targets one reader among several that read the same file, arrange the fixture so the other readers cannot produce the asserted token. Note: the tolerance in `firstPromptTitle`/`lastUserText` for text blocks on tool-result rows is a real, small, pre-existing wart (a tool-result with a stray text block can become a title). Not fixed here.

### 2026-09-20 — The real corpus had a shape the fixtures did not

**What happened:** All unit tests were green, the dictate query worked, and still the adversarial pass over a random real transcript found that Claude Code's `[Request interrupted by user]` marker is a `type:"user"` row and had been indexed: `q=interrupted` returned 82 sessions previewed by the marker.
**Why this matters:** Fixtures encode the shapes the author knows. Synthetic user rows (`isMeta`, `<`-wrappers, tool results, the interrupt marker) are a family, and I had covered three of four. It cost a second version bump and a second server restart.
**What better looks like:** For any change that classifies transcript rows, run the classifier over a sample of the REAL corpus and eyeball the top distinct outputs before declaring done — the [[probe-shape-before-scripting]] memory, applied to the output side. Ten seconds of `python3` over 400 files found this.
