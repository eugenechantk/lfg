### 2026-08-06 — Third blind investigation of "iOS client disconnects"

**What happened:** Asked to diagnose cellular-only disconnects. Found three prior
diagnosis docs for the same symptom family
(`diagnosis-macbook-air-flakey-connection.md`,
`diagnosis-connection-instability-20260804.md`,
`diagnosis-pro-disconnect-banner-20260804.md`) plus a memory recording a
Surfshark theory that was asserted and later retracted. Every round — including
this one — reasons from a verbally-reported symptom plus server-side logs,
because the iOS client emits no connection timeline. The phone was on Wi-Fi
during this session, so the failing condition could not be observed at all.

**Why this is inefficient:** the code-reading is genuinely productive (three real
defects found), but nothing produced can be *confirmed*, so each round ends in a
plausible theory that the next round may have to retract. That is precisely the
failure mode [[disconfirm-before-declaring-root-cause]] and
[[ground-truth-before-hypothesizing]] exist to prevent, and neither can be
honoured here because the ground truth is not recorded anywhere.

**What better looks like:** when a symptom gets a *second* diagnosis doc, stop
diagnosing and build the observability first. Concretely for lfg: a rolling
in-app connection log (every `HostSignal`, `HostState` transition, `NWPath`
status + interface type + isExpensive/isConstrained, link state change, RTT)
viewable and shareable from Settings. Generalisable rule: **N-th investigation of
the same symptom ⇒ the deliverable is instrumentation, not another theory.**

Diagnosis artifact: `.claude/diagnosis-cellular-only-disconnects-20260806.md`.
**Acted on the same session** — `ConnectionLog` + Settings viewer shipped, so the
next 5G drop produces evidence instead of a fourth theory.

### 2026-08-06 — Two defects in new code were only visible in the artifact, not the tests

**What happened:** After implementing the connection log I had green unit tests
(persistence round-trip, rotation, rendering) and a working screen. Then I read
the actual log file the running app had produced, and found two real defects my
tests had not modelled: (1) batching meant only the launch banner reached disk
while ~30 entries sat pending — so an app kill would lose exactly the entries
describing a drop; (2) the same machine appeared as `localhost`,
`localhost:8766` and `Eugenes-MacBook-Pro` in one timeline, because three
components each reached for a mutable display name.

**Why the tests missed them:** both tests asserted the property I had *designed
for* (entries survive an explicit `flush()`; a rendered line contains a host
column) rather than the property the artifact needs (nothing is ever lost
without a flush; one machine has exactly one name). Unit tests inherit the
author's model of the problem; the produced artifact does not.

### 2026-08-06 — Archived a tree another agent was mid-edit in

**What happened:** Ran `deploy_testflight` from the main working tree. It failed
in `build_app` on a compile error in `ios/LFG/SessionDetailView.swift` — a file I
never touched. `stat` showed it modified at 10:34:49, i.e. *during* my archive:
another concurrent agent was mid-edit and the file was transiently uncompilable.
Recovered by creating a detached worktree at HEAD, copying in only my 12 files,
re-running the package tests there, and deploying from that. Second attempt
succeeded (`202608061039`, DoD PASS).

**Why this was avoidable:** the project `CLAUDE.md` says it outright — *"Before
archiving/deploying, snapshot the tree (worktree or stash) — never archive a tree
another agent is mid-refactor in."* I read that file at session start, checked
`git status` for concurrent work before *editing*, and then skipped the same
check before *deploying* — treating the deploy as a continuation of my own work
rather than as a fresh read of a shared tree. Cost ~6 minutes plus a stray
`CODE_SIGN_STYLE = Manual` mutation left in the main tree by the failed run
(repaired with `xcodegen generate`).

**What better looks like:** treat "snapshot first" as unconditional for any
archive/deploy in a shared repo, not as something to do when concurrency is
suspected — the whole point is that another agent's edit lands in a window you
cannot observe. Concretely: `git worktree add --detach <tmp> HEAD` + copy own
changed files + run tests there + deploy from there. It costs ~30 seconds and
removes the failure mode entirely. Also note the second-order damage: a failed
fastlane run leaves `update_code_signing_settings` mutations behind in whatever
tree it ran in, so a main-tree deploy failure is never clean.

**What better looks like:** for any feature whose output is a document a human
reads — a log, a report, an export, a generated file — **read the real output
end-to-end once before declaring done**, in addition to the tests. Budget one
explicit step for it. Both defects took under a minute to spot by eye and would
have survived indefinitely otherwise, in the one artifact whose entire purpose
is being trustworthy after a failure. Both are now regression-tested.
