### 2026-10-04 — The deploy gate checks that the bundled Access payload exists, not that it matches the current secret

**What happened:** Eugene rotated the Cloudflare Access client secret. `ensure_bundled_cloudflare_access!` in the Fastfile only runs the generator when `ios/PrivateResources/BundledCloudflareAccess.private.json` is missing or malformed. The main tree still had the old payload, so a plain `deploy_testflight` would have shipped the dead secret and passed DoD 1b (which compares hosts, not the secret).
**Why this matters:** A build with a revoked secret installs fine and then 403s every host. Nothing in the lane would catch it.
**What better looks like:** The lane should always regenerate the payload from the Keychain/fallback source before archive, or compare the payload's secret to the source and fail on a mismatch. Optionally probe one host with the payload's token (expect 200) before archiving.

### 2026-10-04 — Rotating the Access secret has no runbook; it lives in six places across two Macs

**What happened:** One service token is stored in: the Pro Keychain pilot item (`dev.omg.lfg.cloudflare-access.pilot`), two desktop-app Keychain items (`com.eugenechan.lfg-desktop.cloudflare-access`, Pro + Air accounts), `~/.cloudflared/lfg-access-service-token.private.json` on each Mac (also read by `~/.local/bin/lfg-cloudflared-ssh`, so `ssh air`/`ssh pro` break too), and the gitignored iOS payload. I had to rediscover this by grepping.
**Why this matters:** A rotation that misses one store leaves a silent 403 somewhere (desktop app, ssh aliases, the phone). The desktop Air Keychain item could not be read back by `security` (ACL), so its update is unconfirmed.
**What better looks like:** A `scripts/rotate-access-secret` that takes the new secret, probes it, updates every store on this Mac, regenerates the iOS payload, and prints the command to run on the other Mac. Document it in `docs/` next to the bundled-access feature.

### 2026-10-04 — Python urllib probes of the lfg tunnels return a false 403

**What happened:** After I updated the Air's token file, a `urllib.request` probe from the Air got 403 on both hosts with the new secret. The same id and secret through `curl` got 200 on both. Cloudflare rejects the default `Python-urllib` User-Agent, so the 403 said nothing about the token.
**Why this matters:** A 403 is exactly what a bad secret looks like. I almost re-debugged a correct rotation.
**What better looks like:** Probe lfg tunnels with `curl` only, or set a browser-like User-Agent in any Python probe.
